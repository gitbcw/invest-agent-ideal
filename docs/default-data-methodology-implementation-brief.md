# 默认可用数据与显式口径实施简报

> 状态：历史实施简报；Mastra 当前承接见 `context-and-prompt-architecture.md`，下文旧 ACP/Workspace 路径不再作为执行入口
> 上位原则：[证据边界内尽力回答设计](./best-effort-answering-design.md)
> 范围：用户问答、表格与报告生成、自动化任务、结果文件、Portal 呈现

## 1. 目标

将以下体验落实为全产品一致的默认行为：用户只说明想解决的问题时，Agent 先以可核验数据完成尽可能有用的交付，并在确有影响时简短说明数据来源、时间、覆盖范围和替代口径。用户无需先选择数据源、输出策略或“精确/近似”。

用户明确要求指定来源一致、逐项精确、完整名单、对账、审计、正式报送或可复算结果时，系统必须保留该约束；不能把其他来源静默替代成同等结果。

## 2. 非目标和硬边界

- 不降低真实性：不得猜测、补造或将搜索摘要伪装成已核验数据。
- 不将“默认可用”理解为所有数据都可混用：不同来源、日期、单位、样本宇宙或计算公式必须保留差异。
- 不通过服务层篡改最终自然语言回复；语义决策归 Workspace Agent，服务仍强制 scope、权限、确认、审计和文件提交。
- 不要求用户在创建自动化任务时选择“参考/维护”“输出策略”或精确级别。
- 不批量覆盖真实用户 Workspace 的模板、Skill 或方法；采用模板规则须遵守逐用户、逐文件确认和备份边界。
- 不为统一形式一次性改造全部数据工具；只处理真实用户场景证明的高频结构化缺口。

## 3. 当前基线

| 层级 | 已具备 | 主要缺口 |
| --- | --- | --- |
| 通用 Agent 规则 | `src/runtime/agent-instructions.ts` 要求部分覆盖、替代口径、严格请求和不编造 | 文件交付和自动化仍需按真实案例持续核对 |
| 普通问答 | Mastra L1 指令与当前方法 Skill 要求事实、推断和不确定性分开 | 长尾数据覆盖仍取决于已挂载工具 |
| 数据政策 | `docs/data-source-policy-decision.md` 已定义服务事实、公开证据与明确缺口的获取顺序 | 缺少将该顺序转化成用户可见方法说明的统一契约 |
| 定时复盘/简报 | `src/acp/mobile-prompt.ts`、`src/acp/scheduled-tasks.ts` 已要求来源、时效、缺失说明 | 各任务的措辞与输出结构不完全统一 |
| 通用自动化 | `src/services/generic-automation-runner.ts` 已允许 Agent 更新、新建或不改动文件 | 结构化结果只以 `summary` 表达，尚无稳定的用户可见口径字段 |
| Portal | 已有聊天文件、自动化运行和文件预览入口 | 不同入口对来源、口径、时间、覆盖说明的展示需要统一 |

## 4. 工作包与顺序

### WP0: 行为基线和场景样本

先固化最小验收样本与现状证据，不改代码。

- 样本一：未指定来源的行业/价格跟踪表。
- 样本二：要求 SMM 和 Mysteel 两套口径的碳酸锂去库表。
- 样本三：用户要求“必须与 SMM 一致”或“用于对账”。
- 样本四：自动化任务维护已有 CSV，数据不足时只报告、不改动文件。
- 样本五：自动化任务新建周度报告或 CSV。

每个样本记录用户输入、实际工具证据、最终交付、口径说明和是否错误追问。以此作为后续提示词与 UI 改动的回归基线。

验收：每个样本都能被判定为 `full`、`partial`、`proxy`、`representative`、`framework` 或 `refuse` 之一；不得以“系统能力建设草案”替代本轮交付。

### WP1: 通用 Agent 与模板规则收敛

修改目标限于模板和通用行为规则，不新增服务 API。

- 对齐 `src/runtime/agent-instructions.ts`、`templates/skills/` 与当前报告、研究、表格任务 prompt。
- 明确默认模式下应交付的最小方法信息：来源或来源类别、截至时间、覆盖范围、关键替代或缺失。
- 明确严格模式的识别词和语义：指定来源、对账、审计、正式报送、逐项一致、指定时点/单位/公式等。
- 明确表格规则：多来源数据必须可区分，不能静默合并；允许在文件首行或字段中给出数据说明。

验收：新建测试 Workspace 的普通问答和表格生成同时遵守原则；用户未指定精度时不追问，指定严格约束时不降级冒充完成。

### WP2: 自动化与报告结果契约

目标是让 Agent 继续自主决定“参考、更新、新建或不改动”，同时让结果说明稳定、可被 Portal 消费。

- 审核 `src/services/generic-automation-runner.ts` 的最终 JSON 约束，定义最小的用户可见结果字段，例如 `summary`、`methodology`、`dataAsOf`、`coverageNote` 与 `relatedAssetIds`。
- 允许字段缺省：没有外部数据或不会引起误解时，不制造空的口径说明。
- 保留当前受控文件提交与版本校验；结构化结果不得授予模型直接写入、删除或越权访问权限。
- 对日/周/月复盘、盘中简报审阅 `src/acp/mobile-prompt.ts` 和 `src/acp/scheduled-tasks.ts`，使其表达同一严格/默认分界。

依赖：若运行记录、Portal connector 或 API 返回体需要新增字段，先按 `service-api-change` 评审；若要存储新字段，再按 `db-migration` 评审。

验收：五个场景中自动化运行记录均能回答“做了什么、关联哪些文件、结果依赖何种数据边界”；无变更不是失败；严格任务不将替代数据写入目标文件。

### WP3: 文件、CSV 与报告交付规范

将方法说明放在用户实际使用文件的地方，而不只在聊天文字中。

- 为 CSV/表格生成约定可读的来源、口径、更新时间与字段差异表达；不强制每个小文件都增加冗余行。
- 报告与复盘沿用“数据来源与质量”小节，限制为用户可理解的信息，不含 endpoint、token、路径或工具名。
- 文件更新时保留原文件版本链与实际变更说明；不要把存储来源、文件来源和数据来源混为一谈。

验收：用户打开下载后的文件，仍能判断数据在哪个时间点、来自何处、两个口径如何区分；无数据时模板清楚标识为空表或待填充，而不是伪造零值。

### WP4: Portal 信息呈现

将 WP2 的用户可见结果在正确的界面呈现，避免增加用户操作负担。

- 聊天文件卡：在文件本身有数据说明时，提供简短摘要；点击预览仍遵循聊天右侧工作区交互。
- 自动化运行详情：以“运行结果”和“本次任务相关文件”为主；口径/覆盖说明仅在有意义时显示，不显示内部“输出策略”。
- 我的文件预览：显示文件版本和存储元数据；只展示文件附带的数据说明，不擅自推断内容可靠性。
- 不增加“精确模式”开关或要求用户选择来源；用户在自然语言任务中提出的严格约束应原样进入执行上下文。

依赖：Portal 与 Runtime 的字段契约必须先经 WP2 确认。Portal 变更在 `/Users/combo/MyFile/projects/invest-agent-portal` 实施并单独进行类型检查和交互验收。

验收：同一份自动化产物从聊天、运行详情和我的文件入口打开时，文件身份一致；必要的口径说明不互相矛盾，且表头、按钮、预览行为不回归。

### WP5: 工具覆盖元数据和产品缺口闭环

仅基于 WP0-WP4 的真实缺口推进。

- 对高频批量/列表类工具补充 `source`、`asOf`、`coverage`、`warnings`、`missingFields` 等结构化事实。
- 区分无数据、部分结果、临时故障、无权限和不支持，避免 Agent 将部分失败理解为完全不可用。
- 在人工回放稳定后，再设计脱敏的 capability-gap 聚合；不得将客户正文或内部工程协议回显给用户。

验收：一个真实高频数据缺口能触发最小的工具契约改造，Agent 能在部分成功时交付结果并正确声明边界。

## 5. 依赖与发布策略

```text
WP0 -> WP1 -> WP2 -> WP3
                   \-> WP4
WP0-WP4 真实证据 -> WP5
```

WP1 可独立先行，不需要数据采购或数据库迁移。WP2 与 WP4 是服务/Portal 联动点，必须先冻结字段契约再实现 UI。每个工作包完成后先在本地测试 Workspace 验收；生产发布只同步代码与构建输入，不得顺带替换真实 Workspace 文件。

## 6. 总体验收

1. 用户请求跟踪表但未指定来源时，系统直接给出可读模板或可核验结果，并仅在必要时说明口径。
2. 两来源任务保留来源差异；缺少一方不会取消另一方的工作。
3. 严格请求不会被替代数据伪装成已满足，系统说明具体未满足点。
4. 自动化任务不要求选择输出策略，能自主更新、新建或无变更完成，并报告相关文件与数据边界。
5. 聊天、微信、报告、CSV、自动化运行详情和文件预览均不泄露内部 URL、路径、token、工具名或工程协议。
6. 不因局部缺失产生“只报能力缺口、没有任何有用交付”的回复；也不因追求可用而出现虚构、混口径或错误全量表述。

## 7. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 规则只写进模板，现有用户不生效 | 按 Workspace 兼容流程逐用户、逐文件确认采用，不批量覆盖 |
| 提示词放宽后出现事实幻觉 | 真实性、来源、时间、覆盖和严格模式仍是硬约束；使用回放审计 |
| 结果字段膨胀成新的复杂表单 | 字段由 Agent 产生、可缺省；UI 只在有影响时展示 |
| Portal 和运行时口径不一致 | WP2 先冻结服务契约，再交由 Portal 消费；跨仓库验收 |
| 为统一而重构全部数据服务 | 仅以 WP0 真实场景中的高频缺口触发工具改造 |

## 8. 执行交接

执行时严格按工作包顺序进行。每个工作包先提供：涉及文件、现状证据、拟改行为、接口或迁移影响、测试方案；完成后提供实际输出、自动化测试、真实回放证据和未覆盖风险。审阅时优先检查两类反向错误：因局部缺失而整体拒答，以及把部分或替代结果表述为完整精确事实。

# 长任务响应时限与失败降级执行计划

状态：执行计划草案
日期：2026-08-07
适用范围：Invest Agent 微信、网页对话、自动化任务与统一推送链路

当前进度：阶段 0/1 的基础契约已落地；阶段 2 已完成首个可用闭环；阶段 3 已加入一次受限自动恢复；阶段 4 的失败通知分级已完成；阶段 5 已按用户体验调整为前台等待最终结果。新增共享时限计算与错误分类模块；ACP 响应返回稳定的错误类别和是否可重试标记；自动化运行记录已有执行截止时间、错误类别和重试属性，并在完成前检查执行截止时间。普通网页和微信对话不再在 15 秒时抢答“处理中”，而是在同一请求中等待最终结果；网页前端可显示已等待时长，微信保持连接等待。默认执行预算为 20 分钟，只有完成、最终错误或执行超时才返回。仅 `transient/timeout` 类错误且未超过执行截止时间时会自动重试一次；依赖不可用、权限、输入、校验和过期错误不会盲目重试。网页和微信的最终失败通知统一使用稳定的用户可见分类文案，并记录错误分类元数据，不暴露内部错误细节。

## 1. 背景与意图

当前系统同时存在三类“时限”问题：

1. 微信和网页端需要在较短时间内给用户一个可见响应。
2. ACP、外部数据、文件解析或表格维护可能需要数十秒到数分钟。
3. 微信投递和定时任务本身有独立的有效期、自动重试、租约和过期规则。

如果把这三类时限当成同一个请求超时，长任务会被误判为失败；如果只延长前端等待时间，微信连接、网页请求和用户体验都会变得脆弱。本计划将“交互响应时限”和“任务执行时限”分开，统一任务状态和错误降级，但保留现有发送队列的有效期语义。

## 2. 目标

- 交互请求保持等待直到最终结果、最终错误或执行预算到期；网页端展示等待时长，不插入“处理中”助手消息。
- 需要较长时间的工作仍受统一执行预算和一次受限自动重试保护，不因短响应窗口提前结束。
- 临时错误自动重试；硬错误立即停止并给出真实、可操作的失败信息。
- 只有最终产物校验和提交成功，任务才标记为 `succeeded`。
- 微信、网页、定时自动化任务共享同一套执行状态语义，但分别适配展示和投递方式。
- 保持现有微信投递有效期、自动重试和过期终止行为；不恢复“补发”提示。

## 3. 非目标

- 本阶段不改变模型、ACP provider 或外部数据供应商的选型。
- 不把所有普通对话都改造成任务记录；短请求仍可同步完成。
- 不为自动化任务增加用户确认或草案门槛。
- 不把发送失败当成生成失败，也不因为发送失败重复调用 ACP。
- 不设计任意 cron、工作流编排或跨任务依赖。
- 不在没有真实指标前承诺某个固定的用户可见秒数；时限应配置化并可观测。

## 5. 目标模型

### 5.1 两个独立的时限

每次用户请求或任务运行至少区分：

- `response_deadline_at`：仅供需要异步化的自动化/后台运行记录使用；普通网页和微信对话不再以它切断前台等待。
- `execution_deadline_at`：本次任务允许继续执行、重试和等待依赖的截止时间。到期后任务进入 `expired`，不得继续产生副作用。

发送消息另有已有的 `push_jobs.expires_at`，它决定消息是否还值得投递；不能用发送有效期替代任务执行有效期。

### 5.2 统一任务运行状态

在现有运行记录基础上统一以下语义：

```text
accepted -> running -> succeeded
                    -> failed
                    -> expired
                    -> cancelled
                    -> waiting_user
```

`waiting_user` 只表示缺少执行必需信息；用户补充信息后由系统恢复同一个逻辑任务或创建明确的新尝试，不能无限期保持。

对外展示至少包括：状态、开始时间、最近更新时间、预计/截止时间（如适用）、结果摘要、错误类别、是否自动重试中、产物引用和下一步操作。

### 5.3 交互入口行为

- 网页和微信均等待 ACP 最终结果；网页端由客户端显示经过时间，服务端只在最终结果、最终错误或执行超时时返回。
- 执行超时返回稳定的超时错误，不再转入普通对话的后台推送。
- 自动化任务仍可使用独立的运行记录和推送队列，不与普通对话等待路径混用。
- 完成、硬失败、过期等终态通过渠道适配器投递一次对应通知；通知自身失败只进入发送重试，不重跑任务。

## 6. 错误分类与降级策略

服务层应提供稳定的错误类别，不让 Agent 通过错误文本猜测是否重试：

| 类别 | 例子 | 默认动作 |
|---|---|---|
| `transient` | 网络错误、provider 5xx、429、短暂 WeChat API 错误 | 指数退避；每次重试前检查执行有效期和幂等产物 |
| `timeout` | ACP 单次调用或依赖调用超时 | 视为临时错误重试；达到总预算后转 `failed` 或 `expired` |
| `dependency_unavailable` | AI API 未配置、provider 明确不可用、凭据失效 | 不盲目重试；转 `failed`，说明依赖和恢复方向 |
| `invalid_input` | 时间、资产、格式或权限不合法 | 不重试；若可向用户补齐则转 `waiting_user`，否则 `failed` |
| `validation_failed` | 输出不是合法 CSV/XLSX、缺少必要字段、校验和不一致 | 有限修复尝试；未通过则不提交产物并转 `failed` |
| `scope_or_permission` | 跨用户资产、路径逃逸、权限不足 | 立即拒绝并审计；不得重试或泄露内部路径 |
| `expired` | 已超过任务有效期 | 终止运行；不再提示“补发”，由任务管理提供重新运行入口 |
| `cancelled` | 用户或运维显式停止 | 终止后续副作用；保留运行历史 |
| `unknown` | 无法可靠归类的异常 | 小次数上限重试；仍失败时按硬失败展示，保留 trace 引用 |

### 6.1 重试边界

- 生成/推理重试和消息投递重试必须是两层独立幂等流程。
- 每次 ACP 重试前先探测已有产物、版本和幂等键；如果副作用已完成，不再次调用 ACP。
- 失败响应不得包含“已完成”或暗示产物已成功写入。
- 部分产物只能标记为临时/失败产物，不能进入正式资产版本。
- 达到次数、总时间或业务有效期任一上限即停止。

## 7. 分阶段执行计划

### 阶段 0：基线与观测（先做）

1. 梳理当前普通对话、微信入站、ACP 调用、自动化运行和推送队列的实际超时点，形成调用时序图。
2. 为每个入口记录 `requestId`、`conversationId`、`taskId`、`runId`、`response_deadline_at`、`execution_deadline_at`、provider、错误类别和最终状态。
3. 统计同步完成率、超时率、自动重试次数、硬失败比例、过期比例和通知投递失败率。
4. 确认现有数据库迁移方式；优先复用已有运行表字段，只有无法表达时才新增列或独立尝试表。

交付物：时序图、现状指标、错误映射表、字段/迁移设计。

### 阶段 1：统一任务运行契约

1. 定义共享的运行记录接口和错误对象：`category`、`retryable`、`userMessage`、`internalReason`、`nextRetryAt`、`terminalReason`。
2. 普通对话保持前台等待并使用统一执行预算；需要独立生命周期的自动化任务继续使用 `automation_task_runs`，不要混入旧复盘表。
3. 持久化两个独立截止时间，并在领取、重试、完成、发送前统一检查。
4. 明确状态转移的服务层约束，禁止重复终态、过期后写入成功、失败后提交产物。
5. 为运行增加租约续期/过期回收，进程重启后可以恢复或按规则失败，不依赖内存 `Set`。

交付物：服务层运行契约、SQLite/Drizzle 迁移、状态转移测试、恢复说明。

### 阶段 2：普通对话长任务化

1. 在 `conversation-log`/ACP 入口使用执行预算等待最终响应。
2. 同步路径对临时错误最多自动重试一次；超过执行预算返回超时错误。
3. 等待路径复用当前 user/project/instance/conversation scope，禁止因为长等待扩大 MCP 或 Workspace 权限。
4. 完成和失败结果写回 canonical conversation log，并通过渠道适配器投递一次通知。
5. 用户发送新消息时，按运行状态决定是读取进度、等待结果，还是只询问必要缺失信息；不要重复启动同一 `idempotencyKey`。

交付物：微信与网页各一条长任务链路、断开连接后可完成的集成测试、重复消息测试。

### 阶段 3：错误降级与自动重试

1. 将 ACP provider、外部搜索、文件解析、微信发送错误映射到稳定类别。
2. 为生成阶段和投递阶段分别定义最大尝试次数、退避、总预算和过期行为，配置化而非散落常量。
3. 实现重试前产物探测和幂等保护；验证“ACP 超时但保存成功”不会重复写入。
4. 硬失败时生成面向用户的简短说明，附带可操作动作（检查凭据、补充信息、稍后重新运行、到任务管理处理）。
5. 删除或屏蔽任何把失败统一转换为“请补发”的旧分支；保留兼容读取但不再产生该提示。

交付物：错误分类器、重试策略、失败通知模板、失败/过期/恢复测试矩阵。

### 阶段 4：网页与微信产品表现

1. 网页显示任务运行状态、最近错误、重试中、产物和运行历史；浏览器刷新可恢复。
2. 微信使用短确认、完成通知、失败通知三类消息，控制通知频率，避免每次内部重试都打扰用户。
3. 对 `waiting_user` 只发送一次明确问题；用户回答后恢复原运行或创建新 attempt，并保留关联关系。
4. 自动化任务继续通过任务管理页编辑、暂停、删除或重新运行，不在聊天里隐式修改任务定义。

交付物：Portal/网页验收记录、微信真实或沙箱链路记录、通知去重测试。

### 阶段 5：灰度与回滚

1. 先对内部测试 scope 开启长任务模式，保留旧同步路径的开关。
2. 观察至少一轮真实的普通长任务、AI provider 故障、微信发送失败和进程重启恢复。
3. 若发现任务状态不一致，关闭异步入口开关；不得删除运行记录、产物或推送审计。
4. 完成迁移回写和文档更新后，再扩大到全部用户。

## 8. 验收标准

### 自动化验收

- 一个预计超过短响应窗口的请求仍能在执行预算内等待并返回最终结果。
- 浏览器断开、微信连接结束或服务进程重启后，任务仍可恢复、完成或明确失败。
- 临时 ACP/API 错误会在执行有效期内按策略自动重试；硬错误不会无限重试。
- 任务过期后不再调用 ACP、不再提交资产、不再创建新的投递副作用。
- ACP 超时但产物已成功保存时，恢复逻辑只保留一个正式产物版本和一个通知任务。
- 最终产物校验失败时运行是 `failed`，不会标记为成功。
- 发送失败只重试发送，不重跑生成；发送超过有效期后进入 `expired`，不提示用户“补发”。
- 跨 scope、权限、路径和凭据错误均硬失败并写审计，用户看不到内部路径或 token。

### 交互验收

- 微信和网页在短时间内都有可理解的状态反馈。
- 成功、处理中、等待用户、失败、过期五类状态文案可区分。
- 用户不需要发送确认、补发或重复原始长指令才能得到最终结果。
- 失败消息明确说明“没有完成什么”和“下一步能做什么”。
- 自动重试过程不会产生重复通知或重复资产版本。

### 工程验收

- `npx tsc --noEmit`、`npm run build`、相关单元/集成测试通过。
- 增加可控时钟和注入式 provider/sender 测试，不依赖真实等待或真实用户消息。
- 运行记录、审计和推送记录可按 `userId + projectId + instanceId` 查询。
- `npm run smoke:mcp-service-tools` 和本地运行时 `/health` 检查通过。

## 9. 风险与缓解

- **ACP 超时但副作用已发生**：使用产物探测、幂等键和提交后确认；未具备三者前不自动重跑生成。
- **后台任务泄露交互权限**：异步运行沿用原 scope，并使用明确的 scheduled/long-task MCP grant。
- **任务太多导致通知噪音**：仅在状态变化、最终结果或需要用户动作时通知；内部重试不逐次通知。
- **状态迁移破坏旧推送**：先复用现有 `push_jobs` 过期和重试逻辑，分阶段灰度，保留旧字段兼容读取。
- **用户等待期间缺少反馈**：网页端显示已等待时长；微信端保持原请求等待，只有最终错误或超时才打断用户。

## 10. 开放问题

1. 普通长任务的默认执行预算应该按任务类型配置，还是先统一一个保守上限？
2. 网页端是否需要实时进度，还是先提供状态轮询和运行历史？
3. 微信失败通知是否需要提供“到任务管理重新运行”的深链，还是先提供自然语言入口？
4. `waiting_user` 恢复是继续同一个 run，还是创建新 attempt 并关联原 run？建议保留原 run，创建新的 attempt。
5. 长任务是否允许用户主动取消？建议首期支持任务管理中的取消，并保证取消后不再提交产物。

请按本计划实施长任务响应时限与失败降级机制。先完成阶段 0 的现状核对和字段设计，再按阶段顺序实现；不得扩大到任意工作流编排，不得恢复“补发”提示，不得把发送失败当成生成失败。每阶段报告改动文件、迁移、测试和未解决风险。

### Reviewer prompt

请独立对照本计划的目标和验收标准审查实现。重点验证：交互响应截止与执行截止是否分离；进程重启/租约过期能否恢复；ACP 超时伴随副作用时是否幂等；硬错误是否停止重试；发送重试是否不会重跑生成；微信、网页和自动化任务是否保持 scope 隔离和历史可追踪。

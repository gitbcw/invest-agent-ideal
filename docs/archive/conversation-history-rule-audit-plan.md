# T-187 对话记录历史规则核验执行计划

> 归档说明（2026-07-28）：核验已完成；当前待执行工作见 `docs/conversation-history-repair-plan.md`，核验证据见同目录的 `conversation-history-rule-audit-report.md`。

## 背景与目标

用户怀疑投研助手 Portal 左侧的对话历史可能存在串话、错误归类或未正确拆分的问题。当前没有足够证据证明问题真实存在，因此本任务只核验现状，不修改代码、数据库、配置或生产数据，也不提前设计新的分流方案。

核验对象是两个独立仓库组成的同一条链路：

- `invest-agent-ideal`：本地 Runtime，拥有权威的 `conversation_sessions` / `conversation_messages`、Workspace ACP 执行和真实 Connector。
- `invest-agent-portal`：云端 Portal，拥有登录、左侧历史 UI、`conversation_mirror` / `conversation_message_mirror` 和 Relay。

最终产物是一份能够支持用户判断“现状是否有问题、是否需要继续做分流改造”的核验报告。

## 已确认的现状假设

以下是执行前通过静态阅读建立的假设，必须在核验报告中用代码、数据或实测证据确认，不能直接当作最终结论：

1. Runtime 不按主题、时间间隔或模型语义自动拆分会话；权威归类键是上游传入的 `conversationId`。
2. Web 点击“创建新聊天”后，在首次发送时使用新的 `web_<随机 id>`；继续打开已有聊天则沿用已有 `conversationId`。
3. 微信链路主要沿用 SDK 提供的外部会话/用户标识，因此同一微信联系人可能长期进入同一个权威会话，而不是按主题自动拆分。
4. Runtime 会话列表按 `userId + instanceId` 隔离，按 `updatedAt DESC` 排序；消息按 `createdAt ASC, rowid ASC` 排序。
5. Portal 先从 Runtime 拉取会话摘要写入镜像，再从镜像生成左侧列表；重命名、置顶、归档和删除属于 Portal 镜像的用户视图状态，不回写 Runtime 权威会话。
6. Portal 默认列表会将置顶项放在前面，其余按镜像 `updatedAt DESC` 排序；搜索只匹配标题和最后消息摘要。
7. 当前同步路径可能只拉取 Runtime 最新 50 个会话，而 Portal 本地分页依赖镜像。这可能造成首次登录、镜像丢失或长期离线后的旧会话补齐不完整，需要重点验证。

## 范围

### 本任务包含

- 描述 Web 与微信各自如何产生、续接和展示 `conversationId`。
- 描述 Runtime 权威日志、Connector 协议、Portal 镜像和左侧 UI 的职责及同步顺序。
- 核对用户、助手实例、渠道、会话和消息的隔离条件。
- 检查标题、摘要、消息数、排序、置顶、搜索、归档和删除的实际规则。
- 使用临时数据库或 mock 环境复现典型场景。
- 对既有真实数据做只读一致性检查，并在已授权登录态下观察现有生产页面。
- 判断问题是否存在、严重程度、影响范围及建议的下一步类型。

### 本任务不包含

- 修改任何产品代码、协议、数据库结构或生产配置。
- 在真实用户环境中新建测试对话、发送测试消息、重命名、置顶、归档或删除。
- 设计或实现新的主题分流、自动切会话或摘要算法。
- 修复核验中发现的问题。
- 将 Personal AI OS Cockpit 的会话逻辑混入本任务。

## 证据分层

报告中的每个结论必须标注证据类型：

1. **代码事实**：具体仓库、文件和行号，说明规则是如何实现的。
2. **数据事实**：只读 SQL 或只读 API 的聚合结果，不在报告中暴露用户消息正文、凭据或个人标识。
3. **隔离实测**：在临时 SQLite、mock connector 或数据库副本中执行，能够安全构造边界场景。
4. **生产观察**：仅查看已有页面和已有记录，不能为了测试写入新数据。
5. **推断**：由事实推导但尚未直接复现的风险，必须与已验证缺陷分开。

## 执行步骤

### 1. 固定核验基线

- 记录两个仓库的当前 commit、分支和工作树状态。
- 保留 Portal 仓库现有未提交改动，不运行格式化、构建生成或任何写入命令。
- 确认本地 Runtime、Portal 和生产 Portal 的访问入口；入口不可用时记录为环境缺口，不自行部署或重启生产服务。
- 确认实际数据库路径，但所有真实数据库仅以 SQLite 只读模式打开；需要复杂查询时先复制到临时目录。

### 2. 建立端到端规则图

逐层记录：

- Web 新对话 ID 的生成时机、首次持久化时机及继续会话条件。
- 微信 `conversationId` 的来源、稳定性及同一联系人多轮消息的复用规则。
- Runtime `ensureSession`、消息 append、标题生成、摘要刷新和消息计数规则。
- Runtime 列表和详情的 scope、排序及分页规则。
- Connector 对 `conversation.list/get/chat` 的 scope 注入和字段传递。
- Portal 镜像 upsert、离线读取、详情补齐、排序、分页、搜索和用户视图状态。
- Sidebar 的选中、新建、加载更多、日期分组和显示条数规则。

产出一张“渠道 -> Runtime 权威日志 -> Connector -> Portal 镜像 -> Sidebar”的规则表，明确每一层是权威、镜像还是纯展示。

### 3. 做真实数据只读一致性审计

对 Runtime 权威库和 Portal 镜像分别统计，不导出正文：

- 按 `user / instance / channel` 的会话数和消息数。
- 是否存在同一 `conversationId` 关联多个用户、实例、助手或渠道。
- 是否存在孤儿消息、空会话、消息 scope 与 session scope 不一致。
- session `message_count` 是否等于实际消息数。
- session `updated_at`、`last_message_preview` 是否对应最后一条消息。
- 会话内是否存在异常长时间跨度；这只能作为“可能需要拆分”的观察，不能直接判为串话。
- Portal 镜像是否缺少 Runtime 会话、消息或最新摘要；Portal 独有的重命名/置顶/归档/删除状态需单独解释。
- Runtime 超过 50 个会话时，Portal 镜像从空库开始能否补齐旧历史。

若生产库不能安全只读访问，则改用最新备份，并在报告中注明数据时间点和证据局限。

### 4. 在隔离环境复现典型场景

每个场景使用临时 DB/workspace 或 Portal mock，不接触真实用户数据：

| 场景 | 预期核验点 |
| --- | --- |
| 同一 Web 用户创建两次新聊天 | 产生两个独立 `conversationId`，历史不串消息 |
| 打开已有 Web 会话后继续发送 | 沿用原 `conversationId`，新消息追加并将会话移到最近位置 |
| 两个不同用户使用相同客户端输入 | scope 隔离，互相不可列表、读取或修改 |
| 同一用户切换不同助手实例 | `instanceId/assistantId` 隔离，左侧列表不混合 |
| 长对话超过详情分页上限 | 消息顺序稳定、分页不重不漏，UI 不把部分历史误认成完整历史 |
| 中断、失败后重试 | pending/failed/sent 状态和幂等键不产生重复用户消息或错误会话 |
| 相同时间戳的多条消息 | Runtime 的 `rowid` 次序与 Portal 镜像次序是否一致 |
| Connector 离线后查看历史 | Portal 从镜像可读；离线期间新增的 Runtime 历史在恢复后可补齐 |
| 超过 50 个 Runtime 会话 | 验证首次同步、分页和旧会话可发现性 |
| 微信同一联系人跨主题、跨日期消息 | 确认实际是否始终落入同一会话，并区分“设计如此”和“实现错误” |
| 标题重命名、置顶、归档、删除 | 只影响 Portal 镜像视图，Runtime 权威记录不被误删或错误覆盖 |

优先复用现有 `portal-conversation-log` smoke 和 Portal mock fixtures；现有脚本若会使用默认数据库，不能直接运行，必须先显式切到临时目录或数据库副本。

### 5. 做现有生产页面观察

- 使用已有账号和已有历史，观察左侧会话数、排序、标题、摘要、条数和详情内容。
- 抽取少量会话 ID，在浏览器响应、Portal 镜像和 Runtime 权威库之间做三方对照。
- 不点击会改变状态的重命名、置顶、删除、归档或发送按钮。
- 截图或记录时遮蔽用户名、消息正文、证券持仓和其他敏感内容。

### 6. 形成判断

每项 finding 使用以下字段：

- 现象与用户影响。
- 证据和可复现步骤。
- 所属层：渠道、Runtime、Connector、Portal 镜像或 UI。
- 类型：实现缺陷、协议缺陷、数据异常、产品规则不符合预期、仅观察项。
- 严重度：P0 数据越权/串用户，P1 历史丢失或错误归类，P2 排序/标题/分页可用性，P3 轻微展示问题。
- 是否需要后续任务，以及后续任务应是修 bug、数据修复还是重新设计分流。

不能把“同一微信联系人长期使用一个会话”直接写成缺陷。必须先证明它导致错误上下文、无法定位历史或明显违背用户预期，并区分渠道 ID 设计与 Portal 展示问题。

在本仓库生成 `docs/archive/conversation-history-rule-audit-report.md`，至少包含：

1. 执行摘要和最终判断。
2. 当前规则图和双仓职责边界。
3. 权威存储、镜像和 UI 展示规则。

5. 隔离实测场景、预期、实际和证据位置。

原始查询输出和截图仅在确有必要时放入不含敏感数据的临时证据目录；不提交数据库副本、token、日志全文或用户消息正文。

## 验收标准

- 报告能用明确规则回答 Web 和微信分别“何时新建、何时续接、按什么隔离、如何排序和展示”。
- 至少覆盖任务要求的同用户多次对话、不同用户、长对话和中断后继续四类场景。
- 每个问题均有代码、数据或隔离实测证据；推断与已验证问题分开。
- 能明确判断是否存在串用户、串实例、历史缺失、错误排序或不合理会话边界。
- 未修改产品代码、真实数据库、生产配置或真实用户会话状态。
- 用户能够据此选择关闭任务、创建具体 bug 任务或启动新的分流设计任务。

## 风险与控制

- **真实数据污染**：生产只观察；所有构造场景在临时环境执行。
- **双仓版本不一致**：报告记录两个 commit，并将跨仓不一致列为独立证据。
- **镜像被误当权威**：所有归类结论先回到 Runtime 权威日志，再解释 Portal 用户视图状态。
- **消息内容泄露**：查询默认只取 ID、计数、时间和哈希/长度，不输出正文。
- **旧文档误导**：只以当前 `AGENTS.md`、Portal current contract、协议和运行代码为准。
- **观察即结论**：时间跨度大、标题相似等只作为抽样线索，必须进一步验证。

## 执行交接

执行者应严格按本计划做只读核验。遇到需要写入真实数据、部署、重启生产服务或修改代码才能继续的情况，记录为阻塞或证据缺口并停止该路径，不扩大任务授权。完成报告后先交用户判断，不在本任务内实施修复。

## 验收交接

验收者需检查：证据是否覆盖双仓全链路；是否把 Portal 镜像操作误解为 Runtime 分流；是否真正验证 scope 隔离和超过 50 个会话的同步边界；是否违反只读约束；最终结论是否足以支持用户决定下一步。

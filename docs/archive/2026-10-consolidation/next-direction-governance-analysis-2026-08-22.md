## 一、总体判断

项目已经完成了“治理原则成文”和相当一部分“服务层护栏建设”，但还没有完成“治理证据闭环”。当前状态可概括为：

> **架构与安全边界已有基础，运行治理仍处于局部可观测、局部可验证、尚未形成正式放行门禁的阶段。**

因此近期不应以新增产品能力、售卖闭环或平台化建设为主，而应先把治理总纲变成项目日常工作的共同语言和证据系统。

“已实现”不等于“治理已达标”。例如：

- 会话连贯性真实长链逻辑已 9/9 正确，但仍出现 38.5–88.9 秒延迟，30 秒门槛未过；
- 外部 MCP observer、Mastra tool-call trace 和成本计价已有代码/测试证据，但尚无统一运行诊断视图的完整证据；
- 当前有 9 条经典回归用例，但治理基线要求 30–50 条版本化隔离样例；
- 迁移与并行部署已有验证，但 controlled rollout、正式观测窗口、故障注入和回滚演练证据仍不完整。

## 二、按五条治理原则评估

评估等级：

- **基础具备**：已有服务契约、代码和测试，但仍需持续复核；
- **部分落地**：局部链路可用，尚未形成统一门禁或覆盖面不足；
- **待落地**：原则已写入文档，但缺少可复核的工程/运营证据。

| 原则 | 当前等级 | 已有基础 | 主要缺口 |
| --- | --- | --- | --- |
| G1 先建反馈，再谈优化 | **部分落地** | 经典回归、连贯性探针、部分真实回放 | 30–50 条样例、统一 Bad Case、版本对照和固定放行标准未成体系 |
| G2 最小化模型职责 | **基础具备** | scope、确认、revision、幂等、调度和资产边界由服务/MCP 强制 | 需持续检查新功能是否把确定性逻辑重新塞回 Prompt |
| G3 假设每层失败 | **部分落地** | 超时、取消、重试、降级、排空和投递终态已有多项实现 | 四类隔离故障注入尚无完整执行证据；行情上游结构性失败仍未闭环 |
| G4 小步发布、可观测回退 | **部分落地** | `feat/mastra-migration`、并行端口、生产零触碰、快照/回滚纪律 | allowlist 灰度、观测窗口、回滚演练和发布证据尚未固化为统一模板 |
| G5 只记录必要且可关联的事实 | **部分落地** | `agent_traces`、MCP observer、tool-call 摘要、脱敏和成本计价 | 尚未证明一次运行可稳定串起 trace、审计、scheduler、push、artifact 和 delivery |

## 三、按 L1–L4 分层评估

| 层级 | 判断 | 评估 |
| --- | --- | --- |
| L1 确定性事实 | SQLite 投影、任务、规则计算、资产和投递状态由服务拥有 | **基础较强**；仍需用真实/隔离运行验证状态覆盖，而不是只看单测 |
| L2 Agent 智能 | Mastra 负责理解、规划、判断和工具选择 | **边界基本清楚**；长上下文性能和外部数据质量仍会影响用户结果 |
| L3 护栏与事务 | scope、权限、确认、revision、幂等、超时和降级 | **局部成熟**；需要故障场景矩阵证明所有终态一致 |
| L4 反馈与观测 | Trace、审计、评估、用户反馈、漂移和发布复盘 | **当前最弱**；观测数据存在，但还没有统一诊断与放行机制 |

治理工作的起点应是 **L4 反向牵引 L3，再校验 L1/L2**，而不是继续从 Agent Prompt 或产品 UI 开始调优。

## 四、当前治理缺口的优先级

### A 级：必须先补的治理基础

1. **治理证据台账**：把每条原则拆成“要求—证据位置—当前状态—责任边界—下一复核时间”。
2. **Bad Case 记录格式**：至少包括场景、输入、预期事实/状态、禁止行为、scope、trace/run/task、归因、修复、回归样例和回滚结论。
3. **运行诊断视图**：从一次 `traceId` 进入 conversation、model attempt、tool call、service audit、automation/scheduler、artifact 和 delivery；缺失关联也要显式显示。
4. **发布证据模板**：影响面、验证结果、灰度对象、观测窗口、回滚目标和未解决风险缺一不可。

### B 级：在 A 级之后补的治理能力

1. 将现有 9 条经典用例扩展为 30–50 条隔离样例，覆盖 happy path、边界、越权/对抗和历史 bad case。
2. 在隔离环境完成模型首字超时、外部 MCP 断连、Portal connector 断连、推送依赖失败四类故障演练。
3. 建立每周治理复盘：只看高影响 Bad Case、未收敛终态、重复副作用、scope 事件、超时/空响应和 trace 覆盖。
4. 对长链连贯性、行情重负载和推送失败分别建立“逻辑正确”和“性能/终态正确”两套判据，避免 9/9 逻辑正确被误读为可扩大灰度。

### C 级：暂不推进的方向

以下内容保留在项目文档中，不进入当前治理落地范围：

- 可演示/可售卖闭环；
- P-17 业务任务的执行拆分；
- 多租户、通用工作台、Portal 同仓和目录物理整理；
- 泛化模型体验、统计页面和与治理证据无关的新 UI；
- 以 LLM Judge 或单一总分替代安全、事务和服务契约验收。

## 五、治理落地顺序

这里的“阶段”是治理能力建设阶段，不是新的产品任务列表。

### 阶段 0：冻结口径，完成现状盘点

产出一份治理矩阵，逐条登记 G1–G5、L1–L4 的现状证据和缺口。盘点期间不扩大功能范围，不因 P-17 的日期压力跳过证据。

通过标准：每个治理要求都有明确的“已满足、部分满足或缺证据”结论；所有未决项有归属，不再用“已实现”作为唯一状态。

### 阶段 1：建立最小反馈闭环

先统一 Bad Case、运行诊断和发布证据三个格式，并选一条隔离链路贯通它们。首条链路应优先选择已经有真实问题和现成 trace 的复盘/推送链，但此阶段只建设治理证据，不承诺修完业务问题。

通过标准：一个失败样例可以被完整复盘、归因、登记、修复、回归，并能说明是否允许下一次灰度。

### 阶段 2：补韧性与回退证据

在隔离环境执行四类故障演练，确认重试、降级、取消、过期、排空和副作用幂等。同步固定发布快照和回滚演练的记录方式。

通过标准：每类故障都有预期终态、实际终态、差异解释和回滚结论；没有任何依赖失败会静默成功或无限重试。

### 阶段 3：形成治理放行门

把样例数量、Trace 覆盖、故障演练、性能门槛、灰度对象和回滚目标纳入统一 go/no-go 记录。治理门未通过时，系统保持隔离/allowlist，不进入更大范围使用。

通过标准：任何涉及 Prompt、模型、工具清单、MCP、服务契约、模板或 Portal 构建的变更，都能在同一套记录中完成评估和回退判断。

## 七、治理成熟度的阶段性目标

近期不追求“所有功能完成”，而追求以下治理状态转变：

| 当前 | 目标 |
| --- | --- |
| 原则已写成文档 | 原则能映射到代码、测试、审计和发布记录 |
| 有局部 trace 和测试 | 一次运行可以被完整诊断 |
| 有经典用例和专项探针 | 有版本化样例集和统一 Bad Case 闭环 |
| 有并行发布和局部回滚纪律 | 有固定灰度、观测窗口和回滚演练 |
| 依赖失败分别处理 | 四类故障有统一终态和人工处置路径 |

## 八、最终判断

你的下一步不是决定“先做哪个产品功能”，而是先回答：

> **我们有没有一套足以约束后续开发、验证后续变更、阻止半成品进入更大范围的治理系统？**

目前答案是：**原则和局部护栏已有，治理系统尚未闭环。** 因此第一着手点应是治理评估矩阵、Bad Case、运行诊断和发布证据四件套；P-17 的业务闭环、可售卖材料和具体执行任务，等治理门建立后再进入下一阶段。

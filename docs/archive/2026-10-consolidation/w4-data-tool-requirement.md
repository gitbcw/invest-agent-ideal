# 数据工具优化需求：重查询批量化与缓存（W4 剩余部分）

> 交付对象：market-data-tool（数据工具 Agent）。本文本可直接作为需求输入。
> 提出方：invest-agent 运行时侧（2026-08-17 真实数据回放摸底）。
> 运行时侧已完成的配套改造：MCP 连接改为进程级共享 + 3 次指数退避重连 + 失败降级（不再因连接抖动判死调用方轮次）。本需求解决的是工具侧的吞吐与重复查询问题。

## 背景（实测证据）

2026-08-17 用真实用户历史对话对 invest-agent 做了 164 轮全量回放，失败与慢的轮次全部集中在「盘中实时拉全市场数据」的重负载场景：

- 「复盘本周所有行业（申万口径）指数或相关 ETF 的资金流向」类问题：38 轮中 4 轮直接失败，成功轮普遍 2–4 分钟，p90 197s，最长 11 分钟；
- 日志证据：`market-data-tool` MCP 连接 3 秒超时（已由调用方重连机制缓解）、上游数据源偶发超时；
- 同一会话内多轮追问高度重复（同一批行业/ETF 反复取数），没有任何缓存命中。

## 需求

### R1 重查询批量化

行业/概念资金流、行业指数快照这类「全市场清单型」查询，必须一次工具调用返回完整清单（或在工具内部并发完成聚合），不允许调用方为单个问题发起几十上百次逐标的请求。

- 验收：单个「全行业资金流」类请求在工具内部的上游取数次数 ≤ 每行业 1 次，且对外暴露为 1 个 MCP 工具调用。

### R2 盘中缓存

- 行情快照（价格/涨跌幅/成交额）：TTL 60 秒，交易时段内生效；
- 资金流/板块排行类：TTL 300 秒；
- 日线及以上频率数据：交易日维度缓存（当日重复请求不再打上游）；
- 缓存键必须包含交易日与非交易时段标记，收盘后请求不得返回盘中中间态混杂数据。

### R3 部分失败语义

上游逐项失败时：返回已成功部分 + 明确的 `missing` 清单，不整体报错；整体失败时错误信息包含可重试标记（调用方有退避重连机制，可配合）。

### R4 观测

每次工具调用返回或日志中可见：上游取数次数、缓存命中率、耗时。供调用方的用量/成本统计页与韧性观测使用。

## 验收标准（端到端）

1. 「本周全行业资金流复盘」类问题，invest-agent 端到端 p90 < 60 秒（当前 p90 约 197 秒）；
2. 同一会话 10 分钟内重复的同类查询，第二次起缓存命中 ≥ 90%；
3. 上游部分失败时调用方拿到部分数据 + missing 清单，轮次不失败。

## 环境信息

- 部署：服务器 pm2 进程 `market-data-tool-mcp`（HTTP MCP）；
- 调用方：invest-agent-mastra 运行时（streamable HTTP MCP，30s 请求超时，3 次退避重连）；
- 当前数据源降级链（若沿用）：tencent → akshare → baostock。

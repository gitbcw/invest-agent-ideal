# 策略模拟 V1 实施设计稿

日期：2026-10-06  
状态：待工程评审，不授权部署、启动真实用户模拟或修改真实策略资产。

方向修订（2026-10-06）：先做 Agent-first 的方法理解与历史判断回放，不先建设用户维护的业务级结构化节点。Skill/方法负责判断语义；服务只在需要账本、审计、聚合或版本绑定时保存通用结果。

方向再收敛（2026-10-07）：日常模拟采用“自动化任务 + Agent Skill + 受控资产文件”作为主路径。Agent 负责调用数据工具、按策略判断和生成报告；服务负责任务调度、作用域、幂等、审计和文件保存。`strategy_simulation.dry_run` 降为历史复算/测试工具，不作为每日模拟的前置执行器。只有在需要严格可重放的批量回算时，才继续扩展确定性模拟引擎。

## 1. 目标

补齐“越用越好用”中尚未落地的反馈闭环：让一个已经确认的用户策略能够按固定日频规则进行模拟执行、留下可复核账本、形成日报和周报，并在证据足够时提出一个待用户确认的策略改进候选。

V1 的完成标准不是证明策略赚钱，而是证明以下链路可以正确、可重复、可回滚地运行：

```text
策略版本
  -> 执行规则确认
  -> 模拟运行
  -> 订单/成交/持仓/净值账本
  -> 日报与周报
  -> 一个进化候选
  -> 用户确认
  -> 新策略版本继续模拟
```

## 2. 范围

### 2.0 Agent-first 前置阶段

在严格回测或持续模拟之前，先使用现有用户 Skill、方法和固定历史证据做少量判断回放，验证 Agent 是否理解用户口径、能否区分事实/判断/未知、能否保留参考性和行动边界。回放结果不是收益回测，也不自动生成正式策略指标。

只有当这一步达到可接受质量，才继续把判断结果接入日报、周报和前向模拟。业务级节点不是 V1 前置条件；需要持久化时使用通用的判断记录（结论、证据、as-of、Skill 版本和未知项）。

### 2.1 V1 包含

- 单个用户、单个模拟实例、单个策略版本。
- A 股股票、只做多、日频、收盘后产生下一交易日信号。
- 初始净值为 `1`，使用归一化现金和仓位比例，不要求真实资金金额。
- 固定的买入、卖出、仓位、成本、未成交和数据缺失协议。
- 模拟订单、成交结果、持仓、每日净值和运行状态的服务端账本。
- 可重复的日运行入口，先支持 fixture/手动触发，再接自然调度。
- 日报、周报和一个待确认的进化候选。
- 用户确认后创建不可变的新策略版本；旧版本和旧账本保留。
- Portal 只读查看入口，事实源为服务端账本；管理动作回到对话完成。

### 2.2 V1 不包含

- 真实交易、真实账户资金或下单。
- 盘中触发、实时止损、盘口排队和逐笔撮合。
- 自动参数搜索、自动修改正式策略或自动采用进化建议。
- 多策略共用资金、组合账户、跨策略排名。
- 复杂公司行动、期权、基金、杠杆、卖空。
- 以短期收益宣传“策略有效”或保证盈利。

## 3. 已有能力与复用边界

以下能力可以复用，但不能被误认为模拟引擎已经存在：

| 已有能力 | V1 用法 | 不能替代的部分 |
| --- | --- | --- |
| `quant_backtest` | 作为部分量价数据/表达式能力探针，或 fixture 的输入参考 | 模拟账户、成交协议、持仓账本和持续运行 |
| `review_viewpoints` / 复盘处理 | 复用观点追踪和周报组织方式 | 订单、成交、净值和交易级归因 |
| `strategy_versions` | 绑定运行时策略快照、保存新版本、回滚 | 模拟运行状态和策略表现账本 |
| `method_changes.propose/apply` | 生成并经确认采用进化候选 | 周报证据生成、候选与模拟的关联 |
| `scheduled_task_runs` / automation runner | 复用租约、幂等和失败记录 | 不能用一条自由文本自动化任务代替模拟状态机 |

实施前必须核对当前 `main` 的实际 schema、scope 和调度接入，不按旧 ACP 或旧 Portal 仓库实现旁路。

## 3.1 Skill-first 产品形态

V1 采用“默认 Skill + 配套基建”的产品形态：系统默认提供一个 `strategy-simulation` Skill，用户可以在现有 Skill 管理能力中阅读、复制、调整和形成自己的模拟方法。

Skill 可以定制：

- 如何询问和解释策略规则；
- 使用哪些候选筛选条件和排序说明；
- 日报、周报和进化建议的表达结构；
- 哪些信号需要重点观察；
- 用户希望看到的指标和反例。

基建必须固定并强制执行：

- 可执行规则的结构校验和数据能力校验；
- 用户作用域、确认门和策略快照；
- 订单、成交、持仓、净值和报告账本；
- 交易日、时间因果、幂等、失败恢复和审计；
- 未确认不改正式策略，旧版本可读、可回滚。

Skill 不是安全边界，也不能直接编辑账本、跳过确认或调用未授权写入能力。Skill 输出的模拟意图必须转换为服务可识别的执行协议；无法识别或不支持的规则进入“待澄清/不具备能力”，不能静默降级成另一套规则。

### Skill、版本和模拟实例的关系

```text
用户 Skill 工作副本
        -> 发布的 Skill 版本
        -> 用户确认的策略/执行协议
        -> simulation strategy_snapshot
        -> 日常运行与周报
```

正在运行的模拟只绑定不可变的 Skill 版本、策略版本和执行协议快照。用户之后修改 Skill，只影响下一次发布或新建模拟；不会悄悄改变既有模拟的历史、当天订单或统计口径。用户确认采用变更后，才创建新版本并从新的有效日期继续运行。

因此，“用户可以定制模拟方式”和“运行结果可复核”同时成立：前者在 Skill 管理层完成，后者由服务端快照和账本保证。

## 4. 用户流程

### 4.1 开启

1. 用户在对话中指定一个已有策略版本。
2. 系统读取策略内容和版本号，检查执行缺口。
3. 缺少退出条件、仓位、候选排序、数据字段或日频适配时，进入澄清草稿，不允许开启。
4. 服务生成开启摘要：策略版本、标的范围、买卖规则、仓位、成本、成交时点、初始净值、开始日期和已知限制。
5. 用户确认精确摘要后，服务创建 `simulation` 和不可变 `strategy_snapshot`。
6. 返回模拟 ID、当前状态和 Portal 查看入口。

### 4.2 每日运行

每个交易日使用幂等键 `(simulation_id, trading_date, phase)` 执行：

1. 检查交易日、数据 as-of 和策略快照。
2. 结算前一日冻结、今日执行的订单。
3. 记录成交或未成交原因。
4. 按收盘数据估值持仓和现金，写入 `nav_point`。
5. 用当日收盘数据生成下一交易日信号和订单；订单在目标交易日前冻结。
6. 写入日报；没有信号也必须有一条“无操作”记录。

晚到、数据不完整或执行失败时，记录 `blocked/failed` 和具体缺口，不使用事后价格补写成交。

### 4.3 每周复盘与进化

周报必须回答：

- 本周执行了什么；
- 净值、收益、回撤、已平仓样本和数据完整性如何；
- 哪些具体交易或信号支持观察；
- 哪些反例、缺口或执行失败限制了结论；
- 是否提出一个“只改变一个条件”的候选。

进化候选固定采用：

```text
发现 -> 证据 -> 可能解释 -> 只改变一个条件 -> 下一轮验证方式
```

候选只进入 `proposed`，不改变当前运行规则。用户确认后调用现有策略采用链路创建新版本；新版本从确认后的未来交易日开始，旧版本只读保留。

## 5. V1 执行协议

### 5.1 默认规则

- 信号：D 日收盘后计算。
- 成交：D+1 日开盘价作为参考；没有交易状态或触及涨跌停时不假定成交。
- 成本：单边固定基线成本，具体数值在开启摘要中显示并绑定版本。
- 仓位：只允许确认范围内的仓位比例，总仓位不超过 100%。
- 现金：不得为负；先处理卖出，再处理买入。
- T+1：当日买入不可当日卖出。
- 未成交：订单仅对目标交易日有效，不自动追价或补成交。
- 估值：使用统一复权/未复权口径；缺失估值时标记净值不完整，不静默连线。

### 5.2 最小指标

- 当前净值、累计收益率、日/周收益率。
- 日频收盘最大回撤。
- 已完成交易数、未平仓数、未成交数。
- 已完成交易胜率；无已平仓样本显示“暂无已平仓样本”。
- 数据缺口、异常日期和运行状态。

V1 不主推年化收益、预测准确率或跨策略排名。

## 6. 服务端对象与状态

名称是领域对象建议，不直接等同于最终表名：

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| `simulation` | scope、status、strategyVersionId、startedAt、lastSettledDate | 同一 scope 可有多个，但 V1 先限制一个活动实例 |
| `strategy_snapshot` | sourceVersionId、contentHash、executionProtocol | 创建后不可变 |
| `simulation_run` | simulationId、tradingDate、phase、status、idempotencyKey | 同一阶段只能成功一次 |
| `signal_decision` | ruleSnapshot、candidates、selected、reason、dataAsOf | 保存完整候选和未选原因 |
| `sim_order` | side、symbol、targetDate、quantity/weight、status | 订单冻结后不可改写 |
| `sim_fill` | orderId、fillPrice、cost、evidence、status | 成交/未成交只能由执行协议产生 |
| `sim_position` | symbol、quantity/weight、averageCost、openedAt | 由成交事件更新 |
| `nav_point` | date、cash、positionsValue、nav、quality | 缺口和修订可追溯 |
| `simulation_report` | period、reportType、metrics、evidenceRefs | 报告失败不回滚账本 |
| `evolution_proposal` | sourceSimulation、sourceVersion、oneChange、evidenceRefs、status | 未确认不得改变运行版本 |

所有对象必须绑定 `user_id / project_id / instance_id`，并保留策略版本、数据来源和 as-of 时间。

## 8. 实施阶段

### 阶段 A：隔离 fixture 纵向切片

- 固定一个策略快照和两到三个交易日数据。
- 完成信号、订单、成交/未成交、持仓、净值和日报。
- 支持重复运行不重复写入。
- 生成一份跨周格式的周报 fixture。
- 生成一个进化候选，但不写正式策略。

### 阶段 B：服务持久化与查询

- 依据当前 Drizzle/SQLite 约定落表或扩展服务-owned 表。
- 接入 scope、审计、版本快照和失败恢复。
- 增加日报/周报查询接口。
- 通过隔离测试验证账本可重算。

当前原型已完成其中的第一步：默认 `strategy-simulation` Skill 模板已接入系统 Skill 播种，`strategy_simulations` 保存 scope、Skill/策略快照和可恢复的 fixture 账本状态。当前仍是单行 JSON 状态快照，尚未作为生产账本或自然调度事实源。

### 阶段 C：对话确认与版本承接

- 复用现有策略确认和回滚链路。
- 用户确认后创建新策略版本和新的模拟起点。
- 验证旧版本历史不变、确认重复消费不重复创建。

当前原型已补齐日报读模型：每日报告带有稳定 `reportId`，分别引用当日结算订单和下一交易日信号订单，并保存持仓快照与净值点；Skill 可以在不重新计算数字的情况下自定义呈现。

周报原型也已补齐：只聚合已完成的日报，证据不足时返回 `insufficient_evidence` 且不提出修改；证据完整时计算期间收益和最大回撤，并最多生成一个 `proposed` 进化候选。候选仍未接入正式策略采用链路。

当前已进一步接入既有 `method_changes` 候选账本：周报候选可登记为 `sourceType=strategy_simulation` 的 `proposed` 记录，并绑定周报证据；重复登记复用候选 ID。`method_changes.apply`、用户确认和新模拟快照仍是下一步，当前不会因周报自动改策略。

当前原型还可以把候选转换为既有 `method_changes.apply` 的精确确认载荷（候选 ID、策略 revision、strategy patch 和作用域）。该步骤只生成确认请求，不消费确认单，也不执行策略写入。

两轮确认的隔离链路已接通：第一轮调用 `confirmations.request(method_changes.apply)` 生成预览；只有在会话中出现明确的用户确认后，第二轮才调用 `method_changes.apply`。候选会变为 `confirmed`，策略投影和版本链路由既有服务负责。

采用成功后，原型会创建新的模拟实例：绑定新的策略版本和 Skill 快照，记录 `parent_simulation_id`，净值重新从 1 开始；旧模拟账本不改写，继续作为历史只读版本。

已新增只读工具 `strategy_simulation.dry_run`，支持指定 `startDate/endDate`。它要求输入可执行的声明式模拟方法和历史日线行情；缺少任一项时返回 `blocked` 与 capability gaps，不写入模拟账本、不修改策略。对本地镜像 `mg/invest-agent-mg` 的实际调用已验证：当前策略版本尚未声明式化，且本会话未挂载历史数据源，因此正确阻断。

### 阶段 D：Portal 只读页与受控调度

- 先接模拟列表、详情、日记录、周报和错误态。
- 再接交易日调度；自然运行前保留手动 dry-run 和暂停开关。
- 首次自然运行只允许隔离用户或明确授权的试点。

## 9. 验收标准

### 必须通过

1. 缺少退出、仓位或不支持数据能力时不能激活。
2. 开启必须绑定准确的策略版本和执行协议；旧确认、篡改确认和重复确认被拒绝或幂等处理。
3. 连续两个交易日可产生完整运行记录，即使无交易也有日报。
4. 已知 fixture 路径可以独立重算现金、持仓、成本和净值。
5. 重复运行、进程重启或报告重试不会重复订单、成交或日报。
6. 晚到数据、停牌/涨跌停、未成交和估值缺失均显式记录。
7. 周报引用具体运行记录和数据证据；证据不足时允许“不提出修改”。
8. 进化候选未确认前不改变当前策略；确认后产生新版本，旧版本可回读和回滚。
9. Portal 数字来自同一账本，能显示运行状态、最后成功日期和缺口。
10. 所有隔离证据与真实行情、自然调度、真实用户试点证据分开标记。

### 不作为 V1 通过条件

- 模拟收益为正；
- 胜率达到某个阈值；
- AI 自动修改规则；
- 真实交易可复制；
- 多策略组合效果。

## 10. 主要风险与处理

| 风险 | 处理 |
| --- | --- |
| 把轻量回测误当成持续模拟 | 以服务端账本和连续运行记录作为核心验收证据 |
| 数据能力不足却静默替代 | 激活前能力检查；运行中进入受阻并显示缺口 |
| 使用未来数据补成交 | 冻结信号时间、目标成交日和 data-as-of，禁止回看补写 |
| 进化建议过度自动化 | 候选、确认、采用三步分离；原版本继续运行直到确认 |
| 模拟规则与真实交易差异过大 | 页面固定展示“归一化日频模拟”及限制，不冒充实盘结果 |
| 调度失败污染账本 | 运行阶段幂等、账本与报告分阶段提交、失败可重试 |

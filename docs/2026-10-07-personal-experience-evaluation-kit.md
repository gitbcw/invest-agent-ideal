# 个人体验测评包

日期：2026-10-07  
对象：`mirror-mg` / 本地镜像  
目标：验证“越用越好用”的初步体验，不评价收益，不把一次体验当成生产结论。

## 测评原则

- 先按自然使用方式操作，不先看实现细节。
- 记录“我是否理解、是否信任、是否愿意继续用”，不追求每项都打分。
- 明确区分：Agent 判断质量、数据缺口、UI/交互问题、服务失败。
- 任何未知、冲突或未挂载能力都记录为 `Unknown/Partial`，不强行判通过。

## 建议流程

### 1. Agent/Skill 入口

- 能否看懂当前助手有哪些方法和 Skills？
- 能否分清“已安装、已启用、草稿、已采用、待确认”？
- 修改方法或 Skill 后，是否看得懂“保存”和“生效”的区别？

### 2. MG 核心工作流

让 Agent 做一次全持仓和关注对象只读复核，观察：

- 是否先说明本轮可用能力和实际证据；
- 是否区分事实、判断、行动状态、触发条件、失效条件和缺口；
- 是否把“继续观察”误说成买入建议；
- 是否在数据不足时降低结论强度；
- 结果是否足够让用户直接决定下一步。

### 3. 失败与不确定性

主动观察一次缺数据、冲突数据或工具不可用的场景：

- Agent 是否明确说“未知/无法核验”；
- 是否保留已经取得的中间结果；
- 是否把代理值当成当前事实；
- 是否给出下一步补证据路径，而不是空泛解释。

### 4. 改进与版本

让 Agent 根据一次具体摩擦提出改进候选：

- 候选是否来自真实问题；
- 是否说明影响范围；
- 用户确认前是否保持草案；
- 确认后能否回读新版本；
- 旧版本是否仍可查看和回滚。

### 5. 长期上下文感受

换一个新会话，继续询问同一方法或上一轮问题：

- Agent 是否记得已确认的方法和边界；
- 是否重复问已经明确的问题；
- 是否加载了正确的 Skill/方法版本；
- 是否把历史资料、当前事实和本轮推断混在一起。

## 每个场景只记录五件事

1. 我想完成什么；
2. Agent 实际做了什么；
3. 哪一步让我困惑、等待或不信任；
4. 哪一步明显比以前好；
5. 我希望它下一次怎么改。

## 结果标签

- `Pass`：可以自然完成，用户无需理解内部实现。
- `Pass with caveats`：主流程可用，但有明确缺口或摩擦。
- `Partial`：能完成部分工作，需要用户补救或解释。
- `Unknown`：证据不足，不能判断。
- `Fail`：误导、越权、状态错乱或主流程无法完成。

## 测评结束后的产物

- 3-5 条最明显的体验问题；
- 1-3 条真正改善使用的变化；
- 需要修 Skill/上下文的问题；
- 需要修服务/UI 的问题；
- 暂不处理的问题和原因。

# 自动化 Portal 列表、模板与批量管理设计

> 状态：设计提案，待确认后实施。
>
> 上位契约：[用户产物库与通用自动化设计](./user-asset-library-and-general-automation-design.md)。本文件只补充 Portal 的任务列表、全局运行记录、模板创建和批量管理体验，不替代任务执行、资产版本、投递、安全与兼容性契约。
>
> 参考输入：用户提供的 4 张自动化界面截图（任务/运行双视图、批量管理、列表工具栏、模板目录）。

## 一、结论摘要

参考图中最值得引入的是四个机制：

1. 用“定时任务 / 运行记录”双视图区分任务定义与执行事实。
2. 把任务列表从当前左右主从布局改成更适合搜索、扫描和批量处理的全宽列表。
3. 在“新建任务”之外提供“从模板添加”，用预填表单降低首次创建成本。
4. 提供显式批量管理模式，但将参考图中的“删除”收敛为可恢复、可审计的“归档”。

不照搬参考图的部分：

- 不把运行记录压缩成只有“成功/补跑完成”的单行状态；仍需保留失败原因、产物、投递结果和继续对话入口。
- 不允许模板一键创建并直接启用。模板只预填任务，用户检查后保存为 `paused`，真实运行验证后再启用。
- 不提供永久删除任务。任务定义、运行历史、产物版本和审计记录不能因列表整理被物理删除。
- 不把价格阈值、规则预警等确定性能力包装成普通 AI 自动化模板；它们继续走服务层已有的规则能力和确认边界。

## 二、现状与问题

### 2.1 已有能力

正式 Portal 仓库 `/Users/combo/MyFile/projects/invest-agent-portal` 已有 `/automations` 页面。已提交基线支持：

- 创建、编辑、暂停、启用和立即运行；
- 每日、工作日、每周指定日期和北京时间；
- 单任务运行历史、运行详情、产物下载和继续对话；
- 旧 CSV/XLSX 自动化兼容。

两个正式仓库的当前未提交工作树正在增加用户产物库、通用任务指令、可选输入资料、创建/更新产物和微信投递。Runtime 已有版本化任务、运行租约、scope 隔离、调度和审计基础。这些前置改动尚不能视为已验收上线能力，必须先完成独立验收；本设计在其上继续演进，不另建一套任务模型。

### 2.2 当前体验缺口

- 当前 `AutomationShell` 同时承担列表、详情、编辑器和运行详情，单文件状态和交互耦合较重。
- 左侧窄任务栏适合少量任务切换，但不适合搜索、筛选、比较和批量操作。
- 运行记录只能按单个 `taskId` 查询，无法形成用户级的全局运行时间线。
- `automation.list` 当前不接受筛选或分页，也没有最近运行摘要，列表增强会产生客户端全量过滤或 N+1 请求。
- 没有模板目录，用户必须从空白表单理解“指令、输入、输出、投递”的完整模型。
- 任务状态已有 `archived`，但 Portal 没有归档入口；参考图的“删除”不能安全地直接映射为物理删除。

## 三、目标与非目标

### 3.1 目标

- 用户进入自动化后 5 秒内能看懂：有哪些任务、哪些需要处理、何时再次执行、最近是否成功。
- 用户能在任务定义和运行事实之间快速切换，不必先选中某个任务才能查看最近失败。
- 新用户可从投资场景模板开始，仍能在创建前理解并修改全部配置。
- 多任务用户能批量暂停、启用或归档，并清楚看到部分成功和部分失败。
- 现有任务详情、运行详情、产物、微信投递和继续对话能力不丢失。
- 桌面端适合高频扫描，移动端保留完整核心流程且不出现横向溢出和控件重叠。

### 3.2 非目标

- 不增加事件触发、任意 cron、任务编排或第三方 webhook。
- 不开放任意服务写入、任意 Workspace 路径或任意 shell。
- 不在本设计中改变日/周/月复盘、market-watch、`price_cross` 规则和既有推送契约。
- 不做在线模板市场、用户分享模板或远程动态下发模板。
- 不物理删除任务、运行历史、产物版本或审计记录。

## 四、参考图取舍

| 参考机制 | 采用方式 | 调整原因 |
| --- | --- | --- |
| “定时任务 / 运行记录”页签 | 采用，做成 URL 驱动的一级双视图 | 浏览器返回、刷新、分享链接后仍能恢复视图 |
| 顶部搜索与筛选 | 采用，按当前页签切换搜索语义 | 任务和运行记录的字段、筛选项不同 |
| 全宽轻量任务列表 | 采用，替换左侧窄任务栏作为默认入口 | 提高扫描、比较和批量操作效率 |
| 批量管理模式 | 采用，支持暂停、启用、归档 | “删除”不符合审计、版本与资产留存要求 |
| 从模板添加 | 采用，模板卡片打开预填创建页 | 模板是起点，不是隐藏的执行权限 |
| 任务列表右侧“多久后执行” | 采用，同时显示绝对时间提示 | 只显示相对时间容易在跨天和长周期下产生误读 |
| 运行记录按日期分组 | 采用，使用北京时间自然日 | 符合用户查找“今天发生了什么”的心智模型 |
| “补跑完成”状态 | 有证据时才显示“恢复后成功” | 必须由 `attempt > 1` 或恢复记录证明，不能由 UI 猜测 |

## 五、信息架构

采用路由驱动的页面结构，视觉上仍表现为连续的页签和详情流：

| 路由 | 页面职责 |
| --- | --- |
| `/automations` | 定时任务列表、搜索、筛选、批量管理 |
| `/automations/runs` | 当前用户全部自动化运行记录 |
| `/automations/templates` | 模板目录 |
| `/automations/new` | 空白创建页 |
| `/automations/new?template=<templateId>` | 由模板预填的创建页 |
| `/automations/<taskId>` | 任务详情、编辑、启停、立即运行、任务级历史 |
| `/automations/runs/<runId>` | 单次运行详情、产物、投递状态、继续对话 |

桌面和移动端使用相同路由。桌面可把运行详情表现为覆盖列表的侧抽屉，但 URL 必须落到具体 `runId`；移动端使用完整页面。任务详情首期统一使用完整页面，避免在窄抽屉中塞入任务定义、资料和历史。

## 六、页面与交互设计

### 6.1 公共页头

页头分为两行语义，视觉上保持紧凑：

- 左侧：返回聊天、页面名“自动化任务”。
- 主导航：`定时任务`、`运行记录` 两个分段页签。
- 右侧：当前视图搜索、筛选、`批量管理`、`从模板添加`、`新建任务`。

按钮优先级：

- `新建任务` 是唯一黑色主按钮，使用 `Plus` 图标。
- `从模板添加` 和 `批量管理` 为次级按钮，分别使用 `FilePlus2`、`ListChecks`。
- 筛选使用图标按钮和 tooltip；有生效条件时显示数量标记。
- 刷新不常驻为文字按钮。正常重新进入页面或窗口恢复焦点时刷新；手动刷新放入更多菜单。

### 6.2 定时任务列表

默认页采用无外层卡片的全宽列表。桌面单行稳定网格：

```text
任务名称/说明            执行规则          最近一次        下次执行          状态   更多
每日行业重要信息推送      每天 09:00         今天 08:58 成功   明天 09:00        运行中  ...
```

字段规则：

- 任务名称是主信息，说明最多两行；不展示内部任务 ID 和 revision ID。
- 执行规则显示“每天 / 工作日 / 每周一、三 09:00”，时区不在每行重复显示，页级说明固定为北京时间。
- 最近一次显示运行状态、完成时间；失败时显示可识别的红色状态文字，不只依赖颜色。
- 下次执行同时提供相对时间和绝对时间；例如主文案“22 小时后”，hover/focus 提示“2026-08-07 09:00”。
- 状态使用 `需要处理`、`定时执行中`、`已暂停`、`已归档`。归档任务默认不出现在当前列表，需筛选查看。
- 点击行进入任务详情；更多菜单提供编辑、立即运行、暂停/启用、归档。

默认排序：

1. `needs_attention`，最近失败优先；
2. `active`，`nextRunAt` 升序；
3. `paused`，`updatedAt` 降序；
4. `archived` 仅在显式筛选后出现。

列表分组仅在确有数据时显示：`需要处理`、`当前任务`、`已暂停`。不为只有一两项任务强行制造多个空分组。

搜索范围：任务名称、任务说明。筛选项：状态、频率、是否微信推送、是否读写产物。筛选条件写入 URL query，返回页面时可恢复。

### 6.3 全局运行记录

运行记录视图按北京时间自然日分组：`今天`、`昨天`、`周三（8/5）`，更早显示完整日期。

每条记录展示：

- 任务名称；
- 触发来源：计划运行或手动运行；
- 面向用户的结果/错误摘要，最多两行；
- 实际完成时间；运行中则显示开始时间和动态状态；
- `成功`、`失败`、`运行中`、`已跳过`、`已取消`；只有存在恢复证据时显示 `恢复后成功`；
- 微信投递状态和产物标记仅在存在时显示，不用空占位。

点击记录进入运行详情。详情保留现有能力并补齐：

- 计划时间、开始/结束时间、触发来源和任务版本；
- 结果摘要或可操作的失败原因；
- 输入/输出产物及版本入口；
- 微信投递状态；
- `在对话中继续`；
- `查看任务`。

搜索范围：任务名称、运行摘要。筛选项：运行状态、触发来源、日期范围、是否产生文件、投递状态。

### 6.4 批量管理模式

点击 `批量管理` 后进入同页模式，不跳转到独立管理后台：

- 每行左侧出现复选框，页头动作区变为 `全选当前结果`、已选数量、`暂停`、`启用`、`归档`、`退出管理`。
- “全选”只选择当前已加载且符合当前筛选的项目；不暗中选择未加载分页。
- `暂停` 只影响未来调度，不取消正在执行的 run。
- `启用` 前弹出汇总确认：任务数量、执行频率、其中多少会更新产物、多少会微信推送。确认代表对这些已声明行为的持久化授权。
- `归档` 前说明：停止未来调度，保留运行历史、产物版本和审计，可在筛选中查看；首期不提供恢复启用，恢复能力另行设计。
- `needs_attention` 不能直接批量启用；需先进入任务详情修复或保存新 revision。
- 正在运行、revision 冲突或权限失配的项目返回单项失败，不回滚已经成功的其他项目。

批量动作采用非原子逐项结果：完成后显示“成功 8 项，失败 2 项”，并把失败项留在选中状态，提供错误原因和重试。禁止用一个笼统 toast 掩盖部分失败。

### 6.5 模板目录

模板页沿用参考图的轻量三列网格：桌面三列、平板两列、移动端一列。卡片是可点击的重复对象，不再套入额外页面卡片。

每个模板展示图标、名称、1 至 2 行结果导向说明和必要条件。首批只放经过端到端验证、与当前能力一致的模板：

| 模板 | 默认计划 | 默认输出/投递 | 创建时仍需用户确认 |
| --- | --- | --- | --- |
| 每日市场重要信息推送 | 工作日 08:30 | 不保存产物；条件微信推送 | 关注范围和“重要”的判断标准 |
| 行业重大动态跟踪 | 每天 09:00 | 不保存产物；条件微信推送 | 行业/主题 |
| 持仓公司公告摘要 | 工作日 18:30 | 不保存产物；微信摘要 | 是否以当前持仓为运行时范围 |
| 每周观察池复盘 | 每周五 17:30 | 创建 Markdown；微信摘要 | 输出名称和复盘侧重点 |
| 定期更新投资跟踪表 | 每天 20:00 | 更新已有 CSV/XLSX；不推送 | 必须选择目标产物和维护规则 |
| 每周研究资料汇总 | 每周五 17:00 | 创建 Markdown；不推送 | 输入资料与汇总结构 |

不进入普通自动化模板目录的能力：价格穿越、止盈止损、服务配置修改、持仓/策略写入和一次性预约提醒。它们要么属于确定性规则，要么超出当前 schedule 合同。

模板实现为 Portal 内版本化静态目录，例如 `src/lib/automation-templates.ts`：

```ts
interface AutomationTemplate {
  templateId: string;
  version: number;
  name: string;
  summary: string;
  icon: LucideIconName;
  category: "information" | "review" | "asset";
  preset: Partial<AutomationCreateRequest>;
  requirements: Array<"wechat" | "input_asset" | "update_asset">;
}
```

模板不进入 Runtime 数据库，也不作为执行时权限凭证。用户点击模板后，Portal 将 preset 填入普通创建表单；最终仍提交完整 `automation.create` payload。模板更新不改变已创建任务。

### 6.6 创建页

空白创建和模板创建复用同一编辑器，改为完整页面而非长表单弹窗，分为四个不嵌套的区段：

1. 基本信息：任务名称、任务说明。
2. 执行时间：频率、星期、时间，固定显示北京时间。
3. 输入与结果：可选输入资料；不保存、创建产物或更新已有产物。
4. 投递：不推送、微信摘要、满足条件时推送。

模板创建时：

- 顶部显示“基于：模板名称”，但所有字段均可编辑。
- 未满足的必要条件就地显示，例如“请选择要更新的表格”，不使用内部能力名。
- 提交按钮仍为 `创建任务`，创建结果始终是 `paused`。
- 创建成功后进入任务详情，主操作为 `立即运行一次`，运行成功后再突出 `启用定时执行`。

## 七、响应式与可访问性

### 7.1 响应式

- `>= 1024px`：完整列表列、页头动作和三列模板。
- `640px - 1023px`：隐藏独立“最近一次”列，把最近结果放到任务副信息；模板两列。
- `< 640px`：任务列表使用稳定两行布局；搜索独占一行；`新建任务` 保留，模板和批量管理进入更多菜单；模板一列。
- 移动端批量动作使用固定底部操作条，必须为页面内容保留安全区和底部 padding。
- 长任务名和最长中文按钮不得撑破容器；任务名最多两行，重要状态和下一次时间不截断。

### 7.2 可访问性

- 页签使用真实链接并提供当前页语义，不用不可聚焦的装饰文字模拟。
- 列表行主入口与行内菜单是独立可聚焦控件，不能嵌套 button。
- 复选框有可读 label；状态同时使用图标和文本。
- 图标按钮使用 lucide 图标、`aria-label` 和 tooltip。
- 弹窗/抽屉具备焦点锁定、Escape 关闭和关闭后焦点恢复。
- 点击目标至少 40 x 40 CSS px；颜色对比达到 WCAG AA。

## 八、状态与错误设计

必须覆盖以下页面状态：

| 状态 | 页面行为 |
| --- | --- |
| 首次空列表 | 显示“从模板开始”和“新建空白任务”两个入口 |
| 搜索无结果 | 保留筛选条件，提供清除搜索/筛选，不显示首次引导 |
| 无运行记录 | 说明运行会在任务执行后出现，提供返回任务列表 |
| Connector 离线 | 列表保留最近已加载内容，顶部显示可重试错误；禁止伪造成功 |
| revision 冲突 | 刷新对应任务，保留用户选择并提示重新确认动作 |
| 批量部分失败 | 展示成功/失败数量和逐项错误，失败项保持选中 |
| 任务正在运行 | 列表展示运行中；暂停只影响未来调度；立即运行按钮禁用 |
| 任务需要处理 | 排在列表顶部，提供进入详情查看错误的明确入口 |
| 已归档 | 默认隐藏；只读展示历史，不允许立即运行或启用 |

## 九、服务与协议增量

Portal 不能通过读取本地 SQLite 或 Workspace 实现上述列表。所有查询和写入继续经过认证 Portal API、Relay 与注册 scope 的 connector。

### 9.1 扩展任务列表

向后兼容扩展 `automation.list`：

```ts
interface AutomationListQuery {
  query?: string;
  statuses?: Array<"paused" | "active" | "needs_attention" | "archived">;
  frequencies?: Array<"daily" | "weekdays" | "weekly">;
  deliveryModes?: Array<"none" | "wechat_summary" | "wechat_on_condition">;
  cursor?: string;
  limit?: number; // 1..100, default 50
}

interface AutomationTaskSummary extends AutomationTask {
  latestRun?: Pick<AutomationTaskRun,
    "runId" | "status" | "origin" | "finishedAt" | "resultSummary" | "errorMessage">;
}

interface AutomationListResult {
  items: AutomationTaskSummary[];
  nextCursor?: string;
}
```

- `{}` 保持兼容，不接受浏览器传入的 scope 字段。
- Cursor 使用稳定排序键并做不透明编码，不能让 Portal 自行拼 SQL 游标。
- 搜索在服务层完成，至少覆盖当前 revision 的名称和说明。
- 最近运行摘要由服务查询返回，禁止 Portal 对每个任务再请求一次运行列表。

### 9.2 扩展全局运行列表

将现有 `automation.runs.list` 的 `taskId` 改为可选；带 `taskId` 时保持现有单任务语义，不带时查询当前注册 scope 的全部任务运行：

```ts
interface AutomationRunListQuery {
  taskId?: string;
  query?: string;
  statuses?: AutomationTaskRunStatus[];
  origins?: AutomationTaskRunOrigin[];
  deliveryStatuses?: string[];
  from?: string;
  to?: string;
  cursor?: string;
  limit?: number;
}

interface AutomationRunSummary extends AutomationTaskRun {
  taskName: string; // 来自该 run 绑定的 revision，不取当前可能已改名的 revision
  attempt: number;
}
```

- 新增 Portal `GET /api/automations/runs`；已有 `GET /api/automations/<taskId>/runs` 保持兼容。
- 日期边界由 Portal 传 ISO 时间，服务按绝对时间查询；“今天/昨天”只在 Portal 按 Asia/Shanghai 分组。
- `taskName` 必须来自 run 的 revision 快照，历史记录不能因任务后来改名而失真。

### 9.3 新增批量生命周期动作

新增 `automation.batch_action`，服务内部复用已有单任务状态转换，不复制启停语义：

```ts
interface AutomationBatchActionRequest {
  action: "pause" | "activate" | "archive";
  items: Array<{ taskId: string; expectedRevision: number }>;
  idempotencyKey: string;
}

interface AutomationBatchActionResult {
  results: Array<
    | { taskId: string; ok: true; task: AutomationTask }
    | { taskId: string; ok: false; error: { code: string; message: string; retryable: boolean } }
  >;
}
```

约束：

- 每次最多 100 项，去重 taskId，拒绝 payload scope 字段。
- 逐项 scope 校验和 revision 校验，整体非原子。
- `archive` 写入 `task.archived` 审计并清空未来 `nextRunAt`；不删除 revision、run、资产或产物版本。
- 每项审计 `details` 写入同一 batch correlation id；无需新增表。
- `activate` 不能绕过 `needs_attention` 修复、资产存在性、微信绑定和现有授权校验。
- 已归档任务首期不可批量恢复；后续如增加恢复，需单独定义状态机。

### 9.4 不需要的服务改动

- 模板目录首期不需要 Runtime API 或数据库表。
- 不新增 MCP tool；这些是 Portal 管理面能力，不是 Workspace ACP 需要主动调用的能力。
- 不改变 scheduler 的触发、租约和幂等模型。
- 不改变自动运行不进入普通会话列表的约定。

## 十、安全、审计与隐私

- 所有 taskId、runId、assetId 仍按 connector 注册的 `userId + projectId + instanceId` 强制隔离。
- 搜索和筛选不能成为跨 scope 侧信道；不存在的 ID 与其他 scope 的 ID 按现有错误策略处理。
- Browser 响应继续清除绝对路径、lease token、内部 workspace 路径和 scope 列。
- 批量启用是高影响但可恢复操作，必须二次确认；批量暂停无需二次确认；归档需要确认。
- 模板文案不得承诺无法验证的数据来源、实时性或投递成功率。
- 模板预填指令不能授予服务写权限，任务启用只授权其明确声明的产物和投递策略。

## 十二、验收标准

1. `/automations` 与 `/automations/runs` 可通过页签、浏览器前进后退和刷新稳定切换。
2. 任务列表能搜索和筛选，并在一个响应内得到最近运行摘要，不产生逐任务 N+1 请求。
3. 全局运行记录按北京时间日期分组，能定位失败、打开运行详情、查看产物/投递并继续对话。
4. 历史运行使用当时 revision 的任务名称；只有存在 attempt/recovery 证据时才显示“恢复后成功”。
5. 用户从任一模板进入创建页后看到完整可编辑配置；创建结果为 `paused`，不会自动运行或启用。
6. 六个首批模板的 preset 均通过 Portal schema，缺少必要资产或微信条件时能给出可操作提示。
7. 批量暂停、启用、归档支持部分成功；revision 冲突和任务忙不会被误报为成功。
8. 归档任务停止未来调度，但任务 revision、运行历史、产物版本和审计仍可按 scope 查询。
9. 批量启用前明确汇总任务数、产物更新数和微信推送数；服务仍逐项执行原有授权校验。
10. 用户 A 不能通过列表过滤、全局运行、批量动作或猜测 ID 读取或修改用户 B 的任何对象。
11. 现有任务详情、立即运行、单任务历史、下载、继续对话、旧表格任务和普通聊天列表行为保持可用。
12. 390 px 移动视口无横向滚动、控件重叠或不可达批量动作；桌面长任务名不挤压状态和操作列。
13. 所有核心操作可用键盘完成，状态不只依赖颜色，图标按钮有可读名称和 tooltip。
14. Portal 类型检查、测试、构建，Runtime 自动化合同与完整 verify 均通过。

## 十三、风险与默认决策

| 风险/问题 | 默认决策 |
| --- | --- |
| 任务数量很少，完整筛选显得过重 | 过滤按钮常驻；没有条件时不展开筛选面板 |
| 模板过多导致选择困难 | 首期固定 6 个，经真实运行验证后再增加；超过 12 个再加分类页签 |
| 批量启用造成意外推送或资产修改 | 提交前汇总授权影响，服务逐项复验，默认不预选任何任务 |
| 归档后用户想恢复 | 首期只读保留，不做恢复；避免未设计的重新授权语义 |
| 全局运行查询变慢 | scope + createdAt/taskId 索引评估放入 WP1，以真实查询计划决定是否新增 migration |
| 当前两个仓库有未提交的通用自动化改动 | 本设计在其验收后实施，执行 Agent 不覆盖或回退现有工作树 |

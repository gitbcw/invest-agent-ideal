# Skill 与 Agent UI 产品方向

日期：2026-10-04
状态：产品方向草案，供 owner 评审；本稿不授权代码改造或生产发布

## 1. 结论先行

当前“技能管理”页面把服务层对象模型直接暴露给了普通用户：安装、停用、卸载、升级、编辑版本、新建 Skill 和找回 Skill 都成为一等操作。这个方向适合开发者或运营人员，不适合作为投资助手的主用户体验。

“技能管理”这个入口名称可以保留。成熟产品通常直接使用“技能”这一用户语言，而不是把英文 `Skill` 暴露给用户。首期不建设技能市场，也不要求普通用户理解内部 Skill 对象；用户看到的是技能名称、详细说明和适用场景，系统内部才使用 Skill、版本和依赖等技术概念。

## 2. 对 Agent UI 的工作定义

“Agent UI”目前不是一个边界完全统一的标准术语。本项目采用一个可执行的工作定义：

> Agent UI 不是把传统设置页做得更复杂，而是让用户以目标、上下文和结果为中心与 Agent 协作；系统把能力选择、工具调用、状态变化和必要确认隐藏在合适的交互节点，并在用户需要时解释。

因此，本项目的 Agent UI 应满足四点：

1. 用户先表达目标，不先选择 Skill、工具或方法。
2. Agent 自动选择适用能力，并在必要时说明“我将使用什么、为什么使用”。
3. 影响运行行为的改变必须显式确认，但不要求用户理解版本、安装和 scope。
4. 高级信息按需展开，不把内部对象模型塞进首屏。

## 2.1 双投影规则：Agent 语言与用户语言分离

同一个对象可以同时服务 Agent 和用户，但不能直接复用同一套展示文案：

| 信息层 | 给 Agent / 服务层 | 给用户 |
|---|---|---|
| 对象身份 | Skill、slug、versionId、scope、release | 技能名称和用途 |
| 生命周期 | draft、approved、installed、superseded、pinned | 待确认、已启用、已禁用、已删除、随当前技能更新 |
| 运行关系 | dependency、asset binding、method、run basis | 使用哪些资料、会产生什么结果 |
| 创建流程 | SKILL.md、私有版本、审批凭证 | 保存为技能、确认后生效 |
| 失败信息 | error code、trace、system status | 发生了什么、影响是什么、下一步做什么 |

检查规则：用户可见页面、弹窗、按钮、空状态、Toast、对话引导和错误提示都不得直接出现 `Skill`、`SKILL.md`、slug、scope、versionId、release、draft、pinned 或原始 error code；除非该页面明确是 owner/运营高级控制面。

## 3. 当前问题诊断

### 3.1 信息理解成本高

当前卡片主要展示名称、slug、简短 description、版本、来源和安装时间。用户仍然不知道：

- 这个能力解决什么实际问题；
- 什么时候会被使用；
- 使用后会改变什么；
- 它是否会读写文件或影响自动化任务；
- “已安装”“已启用”和“本次会话实际使用”有什么区别。

悬浮提示只能补充局部文字，无法承担完整的决策说明，也不适合移动端和键盘操作。

### 3.2 管理动作暴露过早

页面直接提供“新建 Skill”“找回 Skill”“升级”“停用”“卸载”和“编辑新版本”。大多数用户没有必要理解这些动作，也没有能力判断 Skill 正文、版本和依赖是否正确。

### 3.3 展示语言偏工程化

“技能管理”作为中文入口没有问题，但页面中的英文 `Skills`、英文技能名、slug、版本和安装术语会增加理解成本。当前真实价值是“技能能帮我做什么”和“我能让助手长期记住什么做法”。

## 4. 产品结构建议

### 4.1 普通用户默认入口：技能管理

保留普通用户可见入口“技能管理”，但把页面从工程对象管理改成用户可理解的技能说明和状态页。首屏只展示：

- 已具备的技能；
- 每项技能的一句话用途；
- 适用场景；
- 当前状态：可用、已暂停、需要确认；
- 对用户的影响：读取资料、生成结果、更新自动化等。

不在首屏展示英文技能名（例如 `macro-analysis`）、slug、版本号、安装时间、release、scope 和内部状态码。

### 4.2 技能详情：从“正文预览”改为“用户说明卡”

点击技能后进入详情，而不是依赖 hover。详情至少包含：

- 它能帮你完成什么；
- 什么时候会使用；
- 它会参考哪些资料；
- 它会产生或修改什么结果；
- 它不会做什么；
- 一个真实示例；
- 当前是否启用，以及停用后的影响。

高级信息可折叠展示：来源、版本、关联自动化、最近变更和审计记录。

### 4.3 “新建 Skill”改为对话式沉淀

普通用户不填写 Skill 表单，也不编辑 SKILL.md。用户可以在对话中说：

> 以后每次做行业复盘，都按这个顺序检查。

Agent 先判断这是否值得长期沉淀，再用人话总结：名称、适用场景、步骤、边界和可能影响。用户确认后，系统生成一个待确认的私有能力草案；用户只需要确认“以后按这个方式做”，不需要理解版本发布。

现有 `guide=skill-create` 对话入口可以保留为后台能力，但首期应由自然语言触发，或在结果反馈中提供“以后都这样做”的入口。

### 4.4 系统能力与用户能力分层

普通用户页面统一显示“技能”列表，内部仍区分：

- 系统基础能力：不可删除，只显示“系统提供”；
- 产品预置能力：可由产品升级，用户通常只可查看和暂停；
- 用户沉淀技能：由用户确认生成，可查看、修改或停用；
- 实验/草案技能：默认不参与运行，只有确认后才生效。

这套内部状态继续由服务层强制，不能把隐藏 UI 当作安全边界。

## 5. 不建设 Skill 市场时的边界

首期明确不做：

- 面向普通用户的公开 Skill 市场；
- 第三方 Skill 搜索、评分、购买或导入；
- 用户之间共享 Skill；
- 让用户从目录中自行挑选一组 Skill 组装 Agent；
- 让用户直接编辑 Skill 正文作为日常配置方式。

“找回 Skill”不应继续作为普通用户的一等入口。底层保留卸载后可恢复的能力即可；必要时在“已停用/已移除能力”页或 Agent 对话中提供恢复。

## 6. 推荐用户流程

### 流程 A：首次使用

用户直接描述想完成的投资工作。Agent 自动使用适合的系统能力，必要时用一句话说明，不要求用户选择 Skill。

### 流程 B：用户想知道助手技能

用户进入“技能管理”，看到按用户语言描述的技能列表。点击后查看用途、示例、影响和状态；不需要阅读 Skill 正文。

### 流程 C：用户想改变默认做法

用户在对话中提出“以后都这样做”。Agent 生成可读的变更摘要，用户确认后保存为待确认能力草案；启用前展示影响范围。

### 流程 D：用户遇到结果不满意

在结果或失败事项旁提供“调整这个技能”或“以后都这样做”。这比让用户主动进入 Skill 管理页更符合 Agent UI 的自然入口。

### 流程 E：高级用户或运营人员

通过低频的高级入口查看版本、来源、任务引用和审计；该入口可以保留，但不作为普通用户主导航。

## 7. 对现有实现的处理建议

### 保留

- 服务层 Skill 版本、安装、启停、卸载和 scope 强制；
- 任务对 Skill 版本的固定引用；
- 草稿、批准、生效和停用的状态区分；
- `guide=skill-create` 作为受控的对话式创建能力；
- 详情页中“保存草稿不等于生效”的安全语义。

### 首期调整

- 页面标题保留“技能管理”，正文和卡片统一使用“技能”；
- 移除首屏“新建 Skill”和“找回 Skill”按钮；
- 将 hover 详情改成点击打开的能力详情抽屉或详情页；
- 用“用途 / 适用场景 / 会影响什么 / 示例”替代 slug、安装时间等首屏信息；
- 将停用、卸载、升级收进“更多设置”或高级入口；
- 对系统能力隐藏不可执行的管理按钮，只显示原因和状态。

### 暂不调整

- 不改变 Agent Space 的底层对象模型；
- 不把 Skill 正文复制进普通用户的设置或 onboarding；
- 不把用户自然语言偏好直接写成运行中版本，仍需确认和版本生效；
- 不因 UI 隐藏而放松服务层授权、scope、依赖和审计约束。

## 8. 分阶段路线

### P0：降低理解成本

- 重新命名入口和页面；
- 重写每个能力的用户说明；
- 用点击详情替代 hover 作为主要了解方式；
- 首屏只保留查看、启用/暂停等低风险动作；
- 验收三用户是否能回答“这个能力帮我做什么、什么时候生效”。

### P1：接入 Agent UI 工作流

- 在聊天结果、失败事项和自动化详情中提供“调整以后做法”；
- Agent 生成能力变更摘要并请求确认；
- 保存草案、确认生效、运行采用保持不同状态；
- 能力详情展示实际关联的任务和资料。

### P2：高级控制面

- 面向 owner/运营的高级 Skill 版本和审计入口；
- 版本比较、恢复和依赖冲突解释；
- 只有在真实用户确实需要跨用户能力复用时，才评估市场或共享目录。

## 9. 验收标准

普通用户不阅读 Skill 正文，也能在 30 秒内回答：

1. 这个能力解决什么问题；
2. 它什么时候会被助手使用；
3. 它会读取或修改什么；
4. 当前是否生效；
5. 我如何让助手以后调整这种做法。

另外：

- 普通用户不需要创建、安装、升级或卸载 Skill 才能完成核心投资工作；
- 高级操作仍可追溯、可确认、可回滚；
- 三用户之间的能力和状态不串读；
- 任何“保存”“确认”“生效”文案不会互相混淆；
- 不建设 Skill 市场不会阻断首期产品上线。

## 10. 待 owner 决策

1. 普通用户入口是否保留“技能管理”。建议保留。
2. 对外是否统一使用“技能”，不显示英文 `Skill` 和英文 slug。建议统一使用。
3. 是否在首期完全隐藏“新建 Skill”，只保留对话中的“以后都这样做”。建议隐藏普通用户的直接创建入口。
4. 是否保留一个高级入口给 owner/运营查看技术细节。建议保留，但不放主导航。

## Handoff

执行方应先按 P0 实现可理解性改造，再由 owner 进行三用户人工验收；未经 owner 对“技能”展示语言和高级入口范围确认，不扩展 Skill 市场或共享能力。

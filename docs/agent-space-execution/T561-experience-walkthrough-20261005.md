# T-561：任务式体验走查记录

日期：2026-10-05  
环境：本地 `production-mirror`，用户 `mirror-111`，OFFLINE 模式  
范围：新建自动化任务 → 运行结果 → 文件预览 → 失败事项 → 问题处理会话

## 走查目标

本轮不只检查页面是否可访问，而是用一个用户目标走完整链路，观察：

- 用户是否知道下一步；
- 保存、暂停、运行、投递和失败是否容易区分；
- 结果是否符合任务范围且没有内部实现泄露；
- 从失败事项进入问题会话后，是否能得到可理解的解释。

## 执行夹具

创建本地任务：`体验夹具｜每日行业信息整理`。

- 说明：每天整理当天的行业动态，输出三条最重要变化，并说明可能影响；
- 初始状态：已暂停；
- 结果投递：不推送；
- 手动运行：成功一次；
- 随后通过本地 runner 注入一次失败：`体验夹具：模拟数据源暂时不可用`；
- 未触碰生产 DB、真实微信或生产 Workspace。

## 需要修订的体验问题

### P1：结果范围和内部修复信息泄露

任务描述限定为行业信息，但运行结果包含多个泛行业主题，并出现“修复本轮输出”“暂存目录”等内部措辞。用户无法判断这是任务偏题、模型扩展还是系统修复痕迹。

建议：

1. 运行结果展示前增加任务范围一致性提示或校验；
2. 用户正文中移除暂存目录、修复轮次、内部重生成描述；
3. 若结果未完全符合任务范围，明确标记“部分符合/需要复核”，不要直接标记成功。

### P1：投递状态不能写成“微信提醒已发送”

本地镜像为 OFFLINE 模式，待处理页仍显示“微信提醒已发送”。这会把“创建提醒 job”“投递尝试”“真实送达”混成一个事实。

建议至少区分：

- 未请求；
- 已创建提醒；
- 投递尝试失败/离线跳过；
- 已确认送达。

### P1：问题处理 CTA 与实际交互不一致

“让 Agent 解释并处理”点击后只创建会话和系统指令，没有自动生成解释；用户还需要再次发送消息。

建议二选一：

- 点击后自动触发一次只读解释，并把回答直接展示；或
- 将按钮改成“在会话中继续处理”，明确这是打开会话而非立即得到回答。

### P2：助手建议的操作必须与产品动作一致

问题会话建议“彻底删除”测试任务，但任务详情提供的是“归档”。

建议：

- 首期统一使用“归档/暂停”；或
- 真正提供删除动作，并明确删除的范围、可恢复性和审计影响。

### P2：结果投递文案需要统一

详情页的“结果通过对话交付”与“结果投递 不推送”并列出现。建议明确拆成：

- 结果保存在哪里；
- 是否发微信；
- 是否会创建文件；
- 是否需要用户继续处理。

## 暂不判为缺陷的观察

- 任务列表初次加载短暂显示“全部 0”，随后加载出 5 条任务：目前更像加载态表达问题，需再做一次慢网络或首次登录观察；
- 运行结果中的新闻事实未独立核验：这属于真实模型/数据源质量问题，不能仅凭本地夹具决定最终根因；
- 问题解释中提到正式任务运行正常：当前夹具环境确实存在该任务，但应继续确认跨任务引用是否始终有证据。

## 下一步

1. 先修 P1 的三项用户误导：结果范围/内部措辞、投递状态、问题处理 CTA；
2. 再补 P2 的结果投递文案和归档/删除动作口径；
3. 修订后重复本流程，并增加一次“创建后返回列表再进入详情”的慢加载观察；
4. 通过后再走 Skill 管理和文件关联流程。

# T-562：mg 投资工作流验证计划

日期：2026-10-05  
用户样本：`mg`（本地隔离镜像，不接触生产 Workspace、生产 DB 或真实微信）  
目的：验证重构后系统是否真正接住 mg 的投资工作，而不是只验证页面和产品操作

## 一、验证对象

mg 使用系统的目的，是把自己的投资方法放进一个可以反复执行、记录、复盘和改进的工作循环中：

```text
市场/行业信息
  → 行业与资金复盘
  → 按控盘度、量价、趋势等规则筛选候选
  → 个股验证与风险判断
  → 加入观察池或形成持仓/次日预案
  → 盘中观察与提醒
  → 收盘反馈
  → 周/月复盘
  → 调整策略或数据口径
```

所以本轮要验证的是：系统能否帮助 mg 完成一次投资判断，并把判断带入后续验证；不是验证“能不能创建任务”。创建任务、查看文件、设置通知，只是承载这些业务工作的手段。

## 二、mg 的主要业务工作流

### 主线 A：收盘复盘到次日预案

这是 mg 最稳定、最重要的日常闭环。

```text
收盘数据与行业信息
  → 行业复盘/持仓复盘
  → 发现重要变化与风险
  → 形成次日关注股票和条件
  → 保存为可追溯的复盘与预案
```

验证重点：

- 复盘是否同时使用持仓、自选、行业、资金流和已有策略上下文；
- 事实、推断、风险和待核验项是否分开；
- 结果是否能明确说明“为什么关注”“什么条件下失效”；
- 复盘结果是否真的能承接到次日预案，而不是一篇孤立报告；
- 行业复盘表是否按既定 17 列、按月、表尾追加且不破坏历史；
- 数据不完整时是否明确 `partial`，不以少量行业结果冒充全市场结论。

### 主线 B：策略选股到观察池

这是 mg 高频的手动工作，目标是减少重复查数和重复筛选，但最终判断仍由 mg 完成。

```text
提出选股目标
  → 读取控盘度/量价/趋势规则
  → 初筛候选
  → 对候选做基本面、技术面和风险验证
  → 展示候选理由、数据时点和缺失
  → mg 选择是否加入观察池
```

验证重点：

- 系统是否复述当前有效策略，而不是混入旧规则；
- 候选是否有逐项依据、数据时间和覆盖范围；
- 代理指标是否明确标为代理，不冒充同花顺或真实主力口径；
- 数据缺失是否降低结论强度，而不是默认为满足；
- “候选”“观察”“买入建议”三种语义是否清楚；
- 未经 mg 确认，系统不得自动加入观察池或持仓。

### 主线 C：个股验证到交易预案

这是把候选或持仓转为可验证计划的工作，不是自动交易。

```text
选择一只候选/持仓
  → 读取当前行情、历史和策略版本
  → 判断趋势、支撑压力、风险与条件
  → 起草加仓/减仓/观望预案
  → mg 确认后保存
  → 次日按条件观察
```

验证重点：

- 策略版本和数据截至时间可追溯；
- 预案区分事实、判断、动作、验证条件和失效条件；
- 不把单日涨跌直接当成策略被验证；
- 确认前只是草案，确认后才形成正式预案；
- 系统不直接执行交易，也不把观察建议说成已买入/卖出。

### 主线 D：盘中提醒到收盘反馈

这是检验系统是否真正形成反馈闭环的工作流。

```text
预案中的条件
  → 盘中行情/事件触发
  → 提醒说明触发原因和与预案的关系
  → mg 选择观察、忽略或补充判断
  → 收盘后标记命中、误报、漏报或不确定
```

验证重点：

- 提醒是否能说清触发条件、数据时间和与昨晚预案的关系；
- 没有值得提醒时是否保持安静，而不是制造噪音；
- 提醒生成、投递尝试和真实送达是否分开；
- 收盘后是否能回看提醒并形成反馈，而不是提醒即结束；
- 本地 OFFLINE 结果不得被表述为微信已送达。

### 主线 E：周/月复盘到策略改进

这是“越用越好用”的核心，不是自动改策略。

```text
汇总周期内复盘、预案、提醒与反馈
  → 统计命中/误报/漏报/不确定
  → 判断是策略问题、执行偏离还是数据缺口
  → 生成策略调整候选
  → mg 确认后形成新版本
```

验证重点：

- 系统能否把过去的判断和结果关联起来；
- 能否区分策略错误、执行偏离、数据不可得和尚未验证；
- 调整建议是否来自证据，而不是模型自行发明规则；
- 新规则在确认前不影响现行策略；
- 版本变更有旧版、新版、理由和回滚线索。

## 三、验证执行顺序

不一次性跑完所有流程，每条流程都由用户观察并给出体验判断。

### 第 1 条：收盘复盘到次日预案（主线 A）

使用本地隔离的 mg 工作区和明确标记的历史交易日数据，执行一次完整复盘。先不要求真实微信、不写生产资产。

用户需要观察：

1. 系统是否理解 mg 的复盘目的，而不是只返回一篇泛泛市场摘要；
2. 是否使用了正确的持仓、策略和行业上下文；
3. 结果是否能直接支持“明天看什么、为什么、什么条件失效”；
4. 缺数据时是否诚实降级；
5. 复盘结果和次日预案是否形成连续上下文。

执行后暂停，由 mg 判断“这是不是我平时真正要做的复盘”，再决定修复、继续或换下一条。

### 第 2 条：策略选股到观察池（主线 B）

使用 mg 已有的控盘度、量价和短期趋势规则，生成少量候选，用户人工选择是否加入观察池。

### 第 3 条：个股验证到交易预案（主线 C）

选择一只候选或持仓，走完事实读取、策略判断、预案草案、用户确认和保存，再检查次日是否能回读。

### 第 4 条：盘中提醒到收盘反馈（主线 D）

使用历史行情回放触发一次符合条件、一次不符合条件和一次数据不足的场景，检查提醒和反馈语义。

### 第 5 条：周/月复盘到策略改进（主线 E）

使用前四条流程产生的隔离记录，生成改进候选，验证系统是否能帮助 mg 迭代而不擅自改动正式策略。

## 四、特殊设计工作流

特殊流程不是产品菜单边界，而是对上述投资闭环的压力测试：

| 编号 | 特殊工作流 | 重点观察 |
|---|---|---|
| S-01 | 行业资金数据只有部分覆盖 | 是否缩小结论范围并标记 `partial` |
| S-02 | 筹码/控盘历史数据存在缺口 | 是否区分代理、缺失和真实值 |
| S-03 | 复盘文件绑定版本变化 | 是否阻止静默使用旧口径，并保留来源 |
| S-04 | 候选符合量价但基本面数据缺失 | 是否降低结论强度，不直接推荐 |
| S-05 | 预案条件触发后价格又回落 | 是否能标记失效或不确定，而不是事后合理化 |
| S-06 | 提醒生成但投递失败/离线 | 是否能看到提醒记录，不声称已送达 |
| S-07 | 用户要求“直接改策略”但未确认 | 是否只生成候选，不写正式策略 |
| S-08 | 同一日重复复盘或重复追加 | 是否幂等，不覆盖、不重复污染历史 |
| S-09 | 旧规则与当前规则冲突 | 是否以当前确认版本为准并指出冲突 |
| S-10 | 跨用户读取持仓、策略或文件 | 是否由服务层拒绝，而非只靠页面隐藏 |

## 五、每条流程的记录格式

每次记录业务结果，不只记录按钮点击：

- 用户当时想完成的投资工作；
- 系统拿到的上下文、数据时点和策略版本；
- 系统给出的事实、判断、动作、风险和缺口；
- 用户是否认为结果贴合 mg 的真实工作；
- 哪一步减少了重复劳动，哪一步仍需手工补足；
- 是否产生正式写入、观察池变化、预案或提醒；
- 失败属于产品流程、数据能力、模型质量、投递还是生产未知；
- 结论：`Pass`、`Partial`、`Fail`、`Unknown`，以及下一步。

## 六、通过标准

只有同时满足以下条件，才称为“mg 业务闭环在本地镜像中可用”：

1. 主线 A 至 E 能串起一次可追溯的投资判断，而不是五个孤立功能；
2. 每个关键判断都能看到数据时点、策略版本、缺失和来源边界；
3. 系统减少重复查数、计算、筛选和解释，但不替 mg 做最终确认；
4. 正式写入、观察池变更、策略变更和提醒投递都有明确确认与状态；
5. 失败、部分完成、未验证和投递未知不会被伪装成成功；
6. 用户能复述下一步，以及这次结果如何进入后续复盘。

本计划不能证明真实模型质量、自然调度可靠性、微信真实送达或生产兼容窗口关闭；这些另行记录。

# T-565 Agent 上下文与决策体验治理基线

日期：2026-10-05  
状态：第一阶段基线，尚未修改代码  
适用对象：`mirror-mg` 工作流验证及后续 Agent 产品化改造

## 1. 背景与问题定义

当前系统已经具备运行时上下文分层：L1 常驻系统指令、L2 状态类上下文、L3 会话历史、L4 用户方法论。但用户在实际使用时仍会同时遇到候选、观察、预案、买入确认、规则、数据缺口、代理值、命中/误报等多个概念。

问题不是信息绝对过多，也不是所有概念都应该隐藏，而是系统没有根据“当前用户要做的决定”控制上下文的适合度。Agent 同时表现为助手、审计员、规则解释器和产品说明书，导致用户需要先学习系统，才能完成投资判断。

本基线定义后续判断依据：先确定当前决定和风险，再确定需要展示的上下文；不通过逐页修补或单纯删减概念解决问题。

## 2. 目标

- 用户在每个工作流阶段都能明确知道“现在要决定什么”；
- Agent 默认提供完成当前决定所需的最低充分信息；
- 重要风险、证据冲突和不确定性不被隐藏，但按风险比例展示；
- 用户可以主动展开更深证据，而无需一开始理解完整方法论；
- 已确认事实、当前推断和未知状态保持分离；
- 后续代码改动能够对应到明确的上下文契约和验收条件。

## 3. 非目标

- 本阶段不修改 Portal、服务、Skill、正式策略或推送规则；
- 不建立新的用户可见状态体系来替换现有资产模型；
- 不把所有解释压缩成二极管式的“买/不买”结论；
- 不以隐藏数据缺口换取表面上的简洁；
- 不让一次对话中的推断自动进入长期用户上下文。

## 4. 上下文四层模型

### 4.1 长期用户上下文

回答“这个用户是谁、已经确认了什么”。包括用户的投资方法、风险边界、已确认的策略版本和持仓资料。只有用户明确确认的内容才能进入长期资产；Agent 推断必须标记为推断，临时信息不自动升级。

### 4.2 当前工作流上下文

回答“现在正在完成哪一步”。当前只激活一个主工作流：收盘复盘、次日预案、候选筛选、盘中提醒/收盘反馈、周期复盘/策略改进之一。其他工作流的内容只能作为明确引用的背景，不应默认全部注入。

### 4.3 当前对象上下文

回答“这次具体在讨论谁”。包括标的、当前身份（持仓/关注/预案/候选）、当前阶段、已有条件和上一状态。对象身份不同，允许的建议不同；例如持仓风险和关注股观察不能使用同一条用户表达。

### 4.4 证据上下文

回答“这句话凭什么、能说到多确定”。包括数据日期、来源、可复算性、冲突、缺失和代理属性。证据上下文控制结论强度，不应直接以内部状态枚举替代用户语言。

## 5. 四个解释深度控制旋钮

上下文展示深度由以下四项共同决定，而不是由“回答长短”决定：

| 旋钮 | 低值 | 高值 |
|---|---|---|
| 任务阶段 | 探索/了解 | 形成预案/复盘验证 |
| 决策风险 | 可撤销观察 | 可能影响持仓或建仓 |
| 证据可靠度 | 来源清晰且新 | 冲突、过期或缺失 |
| 用户熟悉度 | 首次使用/已表现困惑 | 已确认并反复使用 |

默认规则：阶段越接近行动、风险越高、证据越不稳定，越需要展示依据和边界；用户越熟悉，越可以减少基础解释，但不能减少关键风险事实。

## 6. 五步工作流决策契约

### WF-01 收盘复盘

- 用户决定：今天哪些变化值得关注？
- 默认展示：事实变化、持仓影响、需要留意的对象、数据是否足够。
- 需要展开时展示：关键数据来源、前后对比、计算依据。
- 不默认展示：全部策略定义、全部规则清单、内部运行步骤。
- 完成判据：用户能说出“明天最需要看什么”，而不是只能复述指标名称。

### WF-02 次日预案

- 用户决定：明天观察什么，以及什么情况使观察失效？
- 默认展示：对象、观察条件、失效条件、风险和待确认项。
- 需要展开时展示：条件对应的证据、数据日期、来源冲突。
- 高风险门槛：涉及建仓或加仓时，必须明确哪些条件尚未验证。
- 完成判据：用户能区分“观察”“准备行动”“暂不处理”，无需理解内部评分公式。

### WF-03 候选筛选

- 用户决定：哪些对象值得进入下一步观察？
- 默认展示：最多少量候选、每只一个主要理由、当前不适合行动的原因。
- 需要展开时展示：候选排序依据、证据质量、对象身份和缺口。
- 不默认展示：完整候选池、所有被排除对象的内部评分。
- 完成判据：用户能选择保留、忽略或要求进一步核验。

### WF-04 盘中提醒与收盘反馈

- 用户决定：这次提醒是否值得处理，收盘后是否仍成立？
- 默认展示：发生了什么、与预案的关系、当前是否只是观察信号、下一次确认时间。
- 必须分开：提醒是否发送、收盘后是否命中、数据是否足够、投递是否成功。
- 不默认展示：规则 ID、完整冷却配置、内部事件流水。
- 完成判据：用户不会把“消息已送达”误认为“判断正确”，也不会把数据缺口误认为静默正确。

### WF-05 周/月复盘与策略改进

- 用户决定：哪些经验值得保留，是否接受一项改进候选进入草案。
- 默认展示：已验证、未验证、无法判断三类结果，以及最多少量改进候选。
- 需要展开时展示：样本、反例、副作用、版本和回滚线索。
- 变更门槛：建议永远先作为草案，用户确认后才进入新版本。
- 完成判据：用户能判断“接受、继续观察、暂不采用”，而不是被迫直接修改策略。

## 7. 输出层级规则

每次面向用户的输出按以下顺序组织：

1. 当前结论或当前需要用户决定的事情；
2. 一到三个最关键的理由；
3. 必须知道的风险或不确定性；
4. 可展开的证据与内部细节；
5. 一个明确的下一步选择。

“候选、代理、Partial、P0/P1/P2”等内部词汇只有在它们直接帮助当前决定时才出现，并在第一次出现时用人话解释。内部审计记录可以保留完整术语，但不应成为默认用户答案。

## 8. 当前系统的初步错位清单

- WF-02/WF-03 同时展示评分、数据状态、规则覆盖和资产写入边界，用户难以识别当前决定；
- WF-04 把观察信号、硬风控、投递状态和收盘质量放在同一语义通道，容易误读；
- WF-05 将策略改进候选、版本治理和数据能力缺口同时交给用户，超出一次决策所需范围；
- P0/P1/P2 是内部验证路线，不应成为用户工作流的主导航；
- 现有 L1-L4 技术分层没有对应到“当前决定需要哪些内容”的产品层选择器。

这些是待后续逐条验证的产品假设，不在本阶段直接判定为代码缺陷。

## 9. 后续执行计划

### 阶段一：基线（本文件）

- 固定五步工作流的用户决策和上下文边界；
- 不改代码；
- 用现有 `mirror-mg` 会话继续验证错位是否复现。

### 阶段二：上下文装配与输出草案

- 为每个工作流定义最小上下文包和展开条件；
- 设计一轮同一案例的“默认回答/用户追问后展开”样例；
- 先由用户人工确认语言和解释深度。

### 阶段三：最小实现

- 优先修改 Agent 上下文装配和输出指导；
- 再评估是否需要服务层字段或 Portal 展开交互；
- 不扩大到策略、规则、推送和生产数据。

### 阶段四：验收

- 用同一组 MG 工作流分别验证首次使用、熟悉使用、高风险和数据缺口场景；
- 检查用户是否能在不学习内部术语的情况下完成当前决策；
- 检查关键证据和风险没有被默认层隐藏；
- 检查追问后能展开，而不是只能重新跑一遍完整分析。

## 10. 验收标准

- 每个工作流都有唯一的当前用户决策；
- 默认回复不要求用户先理解内部状态枚举；
- 高风险或证据冲突时，必要依据自动出现；
- 低风险且证据稳定时，不输出无关的全量上下文；
- 用户追问可获得更深证据，且不改变原始事实边界；
- 任何长期上下文变更仍需用户明确确认；
- 五步之间能形成连续决策链，而不是五份互相独立的报告。

## 11. 开放决策

以下问题在进入代码实现前由用户体验验证决定，不在本阶段擅自冻结：

- MG 用户默认属于哪种熟悉度档位，是否允许系统根据交互动态调整；
- 观察信号、预案条件和硬风控在用户语言中的最终命名；
- 哪些数据缺口必须立即告知，哪些只进入记录；
- 用户是否需要显式的“展开依据”入口，还是通过自然语言追问即可；
- 周/月复盘默认展示几条策略改进候选。

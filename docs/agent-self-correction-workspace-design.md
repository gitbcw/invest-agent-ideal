## 1. 问题定义

### 1.1 纠错闭环缺了运行时这一半

运营环九段（REALITY→TRACE→SIGNAL→DIAGOSIS→FINDING→EVAL→IMPROVEMENT→REGRESSION→PRODUCTION）目前完全住在**开发侧**：信号来自巡查与用户反馈，诊断、归因、改进由开发 Agent 在本仓库的代码、提示词、模板和文档中完成，经发布周期生效。生产 AI 是**被改进的对象**，不是改进的参与者。

近期事故呈现出同一个模式——知识已经存在（人已诊断清楚），但落进运行时的通道只有两条：

| 事故 | 已知纠错知识 | 落地通道 |
| --- | --- | --- |
| 筹码过时方法条款（BC-20260913-001，9-8 误答 9-13 定因） | 方法文件旧事实压过工具数据，应先查工具 | 把查询指引句写进**用户方法文件**（line 167）——借用户资产承载系统纠错知识 |
| glm 空回复静默放弃（9-14 复现 3/3） | 受挫后静默放弃的签名与处置（重试/换挡/显式报错） | 服务层兜底代码 + 等待发布 |
| 空壳 summary 照推（BC-20260904-001） | summary 应有质量下限 | 服务层质量下限代码（T-473） |
| dyk 幽灵个股（8-31） | 模型会跳过 portfolio.read 编造持仓 | 服务端注入持仓宇宙（58252d6） |

两条现有通道各有代价：**服务层硬代码**精确但重（每条知识都要开发+发布+回归）；**提示词/模板/方法文件**轻但随发布周期走，而且写进用户方法文件会混淆所有权。缺的是第三条通道：**运行时 AI 自有、可按规则演化、不要求发版的知识层**。

### 1.2 为什么现有容器不够

- **用户 workspace（L4）**：是用户资产，语义是"用户的投资方法"。chips 事故把系统纠错知识写进去，是权宜之计；用户资产层不应该承载服务侧纠错事实（透明化重构 §2.1 也是这个立场）。
- **`review-memory-store`**：已存在的服务层记忆原语（复盘资源键控、幂等写入），但只服务复盘域的状态续接，不是错误知识库。
- **仓库文档（bad-cases、failure-taxonomy、ED 参考）**：生产 agent 运行时读不到。
- **会话历史（L3）**：会话内 24 条、跨会话即焚。同类错误下一个会话重犯。
- **L2 状态注入**：只有初始化提示、复盘上下文等任务态，没有"教训"的位置。

context-and-prompt-architecture.md §5 早已留坑："越用越好用"跨会话记忆层暂不设计，待产品验证后立项。本设计是对这个坑的**窄切面回应**：只做纠错知识，不做通用个性化记忆。

## 2. 概念与定位

**定义（提案）**：Agent 自有工作空间 = 服务层拥有的、按场景契约注入到 agent 上下文的、agent 可在受控契约下读写的一组结构化逻辑资产。**不要求物理目录**——它是 Mastra 架构之上的一个逻辑层，存储形态是待裁决问题（§7.1）。

**在两层模型中的位置**：透明化重构把系统分成"用户资产层 / Agent 运行层"。本设计把 Agent 运行层中**可显性化、可演化**的部分（错误知识、运行教训、修正意图）升格为 agent 自有资产，与用户资产同级的另一类 service-owned asset——用户资产的用户是 owner，agent 自有资产的"用户"是 agent 自己，但治理都在服务层。

**三个"不是"**（范围控制的第一道墙）：

1. 不是替代开发侧运营环：FINDING→EVAL 的归纳与验证仍由人+开发 Agent 完成，本设计只把**已裁决知识**送进运行时、并让运行时能**回灌候选记录**。
2. 不是通用记忆：不存用户偏好、不存个性化画像（那是另一条线）。
3. 不是自治权限：agent 自有空间内的一切写入走服务层 schema 校验、scope、审计；它永远不能成为绕过确认流的通道。

## 3. 设计支柱（提案）

### S1 纠错知识条目（记录与表征）

结构化条目，字段草案：

```ts
type AgentLesson = {
  lessonId: string;
  scope: { taskType?: string; toolName?: string; channel?: string; scenarioSignature?: string }; // 何时适用
  trigger: string;            // 什么现象出现时该想起它（含错误签名）
  guidance: string;           // 纠正指令（建议性，非权限）
  evidence: string[];         // traceId / BC 编号 / 复现记录引用
  status: "draft" | "active" | "retired" | "rejected";  // draft=agent 记录未裁决；active=已裁决注入
  origin: "owner_promoted" | "agent_recorded" | "ops_promoted";
  createdAt / expiresAt?: string;
};
```

- `guidance` 是提示层建议，服务层不因它改变任何行为边界（对照 §4）。
- 矛盾处理：同 scope 两条 active 条目冲突时服务层注入时显式标注冲突，由巡查/owner 裁决退役一条，禁止静默择一。

### S2 场景注入（消费）

- 服务层在组装 L2 状态上下文时，按当前任务类型/工具调用/通道匹配 `status=active` 的条目，注入为一段带预算上限的"运行教训"块（提案：≤1500 token，按优先级与新鲜度排序，超出丢弃）。
- 注入决策权沿用 thinking-depth-router 的哲学（模型裁判优于硬规则）：v0 可先用最简单的规则匹配（taskType/toolName 精确命中），复杂化留到有证据之后。
- 每条注入留 trace（lessonId 进当轮 trace_payload），使"注入了哪条教训"可诊断——这是诊断链既有口径的自然延伸。

### S3 修正提议（行动）

- agent 在发现方法/规则/任务定义的问题时，走**拟议版本**而非直接修改——直接对接透明化重构已定义的 candidate→asset version 模型（不是再造一套）。
- 对 agent 自有知识库（S1）本身，写权限可以更宽：`draft` 条目 agent 可自由 append（服务层 schema 校验+幂等），但 `draft→active` 的晋升必须经 owner/巡查裁决——这是防"错误知识自我强化"的关键门（§8）。

## 4. 安全与范围控制（红线）

1. **记录自由、生效受裁**：append draft 无需确认（内部状态，非用户资产）；任何进入注入层（active）或影响用户资产/运行行为/外部效果的动作，仍走既有确认与审计。
2. **注入是建议层**：不修改 L1 系统指令、不扩大工具权限、不绕过 scope/确认/幂等。用户文件与 agent 知识都不能覆盖 L1（既有红线原文照搬）。
3. **服务层强制**：schema 校验、scope、审计、并发、过期全部在服务层，prompt/知识文本不是安全边界（AGENTS.md 红线）。
4. **明确不做（本期）**：
   - 不做全自动 prompt/方法进化（agent 记录→人裁决→生效，环里永远有人）；
   - 不把 agent 自有资产放进用户 workspace 目录（避免备份/模板/迁移复杂化，所有权清晰）；
   - 不做通用跨会话个性化记忆；
   - 不改动交易、推送、调度、资金动作的确认边界。

## 5. 与现有机制的关系

| 现有机制 | 关系 |
| --- | --- |
| L2 状态注入 | S2 复用同一通道，新增"运行教训"块 |
| review-memory-store | 证明服务层键控幂等记忆原语已存在；S1 是其推广（域从复盘扩到纠错），实现上可同库不同表 |
| method_changes / 透明化拟议版本 | S3 直接对接，不另造候选机制 |
| 运营环 FINDING/EVAL | 新增一条 IMPROVEMENT 子通道：除改代码外还可"喂知识"；巡查报告增加 draft 条目清单 |
| bad-cases / failure-taxonomy | 它们的**运行时出口**：BC 关闭时顺手产出一条 candidate lesson（提案，作为 BC 模板的可选字段） |
| T-519 系统进化机制研究 | 本设计是其运行时侧落点；T-522 投资进化闭环是客户侧对偶 |

## 6. 分阶段（提案）

- **AC0 设计冻结（本任务）**：owner 讨论本草案，裁决 §7 问题，冻结 v0 范围。
- **AC1 只读注入最小闭环**：人工挑选 3-5 条已裁决高价值知识（候选：glm 空回复处置、summary 质量意识、筹码先查工具、持仓宇宙不编造）建 active 条目，接入 1 条链路（建议自动化任务优先，会话短、可对照），验证注入管道、token 成本与效果对照。
- **AC2 append 记录**：agent 在明确失败/纠正场景写 draft 条目（schema 校验、幂等、进巡查可视）。
- **AC3 修正提议**：agent 经 S3 发起对方法/规则/任务定义的拟议版本（依赖透明化重构落地进度）。
- **AC4 晋升与退役例行化**：巡查/周报例行消费 draft 清单，裁决晋升/退役，形成节奏。

AC1 先于 AC2 的理由：先证明"喂进去有用"（注入管道+效果），再谈"自己记"（记录质量不可控，风险在后）。

## 7. 待裁决问题（owner 讨论清单）

1. **存储形态**：独立服务层 DB 域（如 `agent_lessons` 表族）vs workspace 隐藏子目录（`.agent/`）vs 扩展 review-memory-store？——**建议 DB 域**：不进用户 workspace 目录（§4.4），备份/模板语义干净，且与"逻辑层而非物理目录"的定位一致。
2. **用户可见性**：agent 自有条目在 Portal 工作空间显示吗？——建议"高级详情只读可见"（透明但不打扰），与透明化重构"路径放高级详情"同姿态。
3. **注入准入的门**：draft 条目是否允许任何自动晋升路径（如带 verified evidence 的白名单场景），还是一律人工裁决？——建议 v0 一律人工，AC4 后再议。
4. **v0 链路选择**：自动化任务 vs 对话？——建议自动化（可对照、可复现、成本低）。
5. **与"越用越好用"通用记忆的边界**：本设计窄切面只做纠错；通用记忆何时立项是独立决策，不要在此顺带做。

## 8. 开放风险

| 风险 | 应对 |
| --- | --- |
| 错误知识自我强化（agent 记错教训并放大） | draft 不注入；晋升必经人裁决；条目带 evidence 可追溯 |
| 注入挤占 context 预算、token 成本上升 | 硬预算上限 + 优先级丢弃 + trace 记录实注入量，AC1 实测后再定常设额度 |
| 知识过期失效（如 glm 通道已修复，教训变噪音） | expiresAt + 巡查例行退役 + 失效信号（同场景错误消失） |
| 与透明化重构的时序耦合（AC3 依赖其落地） | AC1/AC2 无依赖可先行；AC3 挂 T-521 进度 |
| 范围蔓延成"通用记忆系统" | §7.5 边界写死；任何超纠错语义的需求另立任务 |

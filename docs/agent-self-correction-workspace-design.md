# Agent 自有工作空间与持续变好用：设计稿 v2

状态：**产品原则及审查修订已与 owner 对齐；工程细节由执行时核实；未实施。**

任务：T-524

依据：本次完整讨论及逐项确认的审查结论。原会议记录未保存，本文不把早期草案中的推断当作会议原话。v2 取代 v1 的执行指导；本次授权仅为文档修订，不包含实现或生产启用。

本稿只定义 Agent 如何在已授权能力范围内，按用户持续积累状态、复用有效经验、兑现承诺并接受用户控制。它不实现代码、不改变生产状态，也不替代后续的 Workspace 用户侧透明化设计。

## 1. 背景与目标

当前系统已经具备对话历史、会话工作状态、用户方法与文件、偏好和业务状态、自动化任务、运行 trace、复盘记忆和工具授权等零件，但这些零件没有形成一个以用户为边界的长期 Agent 工作状态层：

- 会话历史及 conversation working state 主要服务当前会话；历史落库不等于跨会话自动取用，读取还受上下文预算限制；
- 用户方法和规则是用户资产，不应承载服务侧错误知识；
- 自动化任务可以运行，但不天然知道它在兑现哪一项用户承诺；
- 开发侧已经诊断出的错误，缺少受控的运行时出口；
- 系统已有 Workspace 读写、Skills 加载和跨运行资产版本更新；缺少的是有效做法的可靠提取、批准、检索、版本绑定和效果反馈，不是从零提供文件持久化能力。

本设计的目标是建立一个**每用户独立、服务层拥有、可检索、可审计、可回退的 Agent 工作空间**，使系统逐步具备“越用越好用”的能力：

1. 客观事实自动沉淀；
2. Agent 在明确事件触发时提出经验或工作流候选；
3. 用户批准后，候选在明确适用范围内自动复用；
4. 用户承诺可持久化，并与实际自动化或其他执行方式关联；
5. 结果和反馈回流，支持修订、停用和回退。

## 2. 已确认的设计原则

以下原则来自本轮 owner 讨论，后续执行不得默认改写：

### 2.1 授权能力优先

首版只允许 Agent 在现有服务层已授权的工具、数据、调度和资产接口内选择、组合和保存工作流。暂不允许 Agent 自行生成或执行新的代码型工具。

### 2.2 用户控制生效

客观事件由服务记录；Agent 的归纳由用户批准后才能进入 `active`。批准绑定具体内容版本和适用范围，不是“自主学习”的永久总开关。

- 用户明确要求“把刚才的流程保存下来，以后这样做”，可直接构成批准；保存并生效后说明具体内容和范围，不再重复询问。
- Agent 主动提出的新经验或工作说明，必须等待用户批准。
- 存在多个候选、内容或范围不明确时，只澄清歧义；不要求照抄固定确认句。
- 服务记录用户身份、来源消息/操作、候选版本和范围；模型声称“用户已批准”不能代替可核对的授权依据。批准后内容被修改，不能沿用旧版本的批准。

采用许可与证据可信度分别记录：`active` 表示允许使用，不代表归因已被证明。经验可能仍是假设、单次验证通过、后续有效或出现反例；记录证据来源，不把这些标签当成自动置信评分。用户批准不应自动提高证据等级。

### 2.3 按任务检索，不整库注入

任务开始时按场景与用户范围生成小型 `State Packet`，只注入相关有效经验、工作说明、承诺和待处理事项。执行中发现新工具需求或明确报错时允许按需补查；起始检索与补查共用硬预算并去重，不整库注入。

### 2.4 事实与经验分离

任务创建、工具结果、运行成功或失败、用户批准或拒绝、承诺到期等客观事件由服务层自动记录。Agent 对事件的归纳只能形成候选经验，不能直接成为事实或规则。工具返回是“该来源在该时间返回了此内容”的事实，并不保证内容永远正确或最新；来源、时效与质量信息需要保留。

### 2.5 明确事件触发提议

不要求 Agent 每轮强制自省。触发包括发现并纠正自身错误、收到用户纠正、失败后找到可复用处置、发现承诺风险，以及用户明确要求记住/复用成功做法、Agent 发现值得保存的成功重复流程。成功做法与纠错经验适用相同批准规则。候选需说明来源、适用范围和预期改变；重复候选应合并提示，拒绝后不在无新依据时反复打扰。

### 2.6 有范围的自动复用

批准后的经验在声明范围内自动复用。经验采用许可不能替代用户资产变更、自动化创建/修改或其他外部动作的执行授权；但本轮明确指令或既有有效授权已经覆盖动作时，不重复询问。只有新增范围、影响或真实歧义才补充确认；既有服务约束始终有效。不能仅因引入本设计而给原有明确授权的操作增加审批步骤。

### 2.7 可退役、可回退

有效状态不是永久真理。所有经验和工作流都必须支持被替代、过期、停用或恢复到前一版本，且保留历史依据。

### 2.8 版本与冲突

每次运行记录实际使用的 `lessonVersionId`、`workflowVersionId`、用户资产 `versionId` 和 `commitmentId`（及其约定版本）。同一运行已加载的版本保持固定，后续版本变化由下次运行取用；按需补查只补充尚未加载的相关条目，不偷偷替换已绑定版本。

版本固定不授予权限：每次动作仍检查当前授权和任务取消状态。当前权威事实、用户本轮明确指令优先于旧经验，且不能越过服务边界。冲突时停止沿用冲突做法并留痕；两条经验冲突或依赖资产已变化而无法确认适用性时，暂不使用，必要时提出修订。不将一次冲突自动变成永久新规则。

## 3. 概念模型

Agent 工作空间是服务层的**逻辑资产层**，不要求使用物理目录，也不等同于用户 Workspace。

### 3.1 四类核心对象

#### A. 事实事件 `AgentFact`

服务层直接观察到的事件。优先引用现有 message、trace、audit、task/run、asset version、delivery 记录，只保存新增关联及必要摘要，不另建一份可漂移的业务事实库。引用带范围、来源和时间；来源不可用时明确标记不可核验，不能用模型回忆替代。

#### B. 经验候选/经验 `AgentLesson`

对事实的可复用归纳，例如“在某类实时数据任务中，应先查当前工具结果，再参考旧方法文件”。候选由 Agent 提交，`active` 必须经过用户批准；系统级经验另走 owner/运营审批，不因单个用户批准而全局生效。

建议字段：

```ts
type AgentLesson = {
  lessonId: string;
  lessonVersionId: string;
  scope:
    | { domain: "user"; userId: string; projectId: string; instanceId: string }
    | { domain: "system" }; // system 写入/批准必须走 owner/运营权限
  applicability: { taskType?: string; toolName?: string; scenario?: string };
  trigger: string;
  guidance: string;
  evidenceRefs: string[];
  status: "draft" | "active" | "superseded" | "expired" | "rejected" | "disabled";
  evidenceState: "hypothesis" | "verified_once" | "supported" | "counterexample";
  origin: "agent" | "owner" | "ops";
  approvedBy?: string;
  approvedAt?: string;
  approvalRef?: string; // 绑定本版本及适用范围；active 必须有可核对依据
  expiresAt?: string;
  supersedes?: string; // 前一版本 ID
  createdAt: string;
};
```

#### C. 可复用工作流 `AgentWorkflow`

首版确定为**可保存、可批准、由现有 Agent 执行的工作说明**。内容包括适用场景、输入要求、推荐步骤、预期产物、结果检查、失败处置和引用的能力/资产。Agent 根据实际情况选择已注册且已授权的工具，偏离说明时保留原因。

它不是代码插件，也不是服务逐步执行的 DAG/编排语言；本期不新建参数映射、分支调度、工作流重试或续跑引擎。需要持续执行时复用现有自动化。与 lesson 共享 scope、不可变内容版本、批准证据、采用状态和生命周期，运行使用 `workflowVersionId` 绑定。

#### D. 长期承诺 `AgentCommitment` 与每次履约

承诺表达 Agent 对用户答应的持续性结果；自动化任务是承诺的一种执行器，不等于承诺本身。

承诺保存用户约定，每次履约引用既有 task/run/result/delivery；二者分别记录：

```text
承诺：proposed → active ↔ paused → cancelled / completed
单次履约：pending → running → satisfied / failed_needs_attention / skipped
```

承诺至少保存 scope、约定版本、授权依据、内容、一次性/周期性类型、触发条件/时区/截止时间、完成判据、执行器关联、状态和下一步动作。`active` 要有授权且执行器已可用；创建执行器失败时保留未就绪/待处理原因，不声称已经安排。需要重议也记录原因，不能静默修改约定。

周期承诺第一次履约成功后仍保持有效；每期独立标记结果，直至约定终点或用户暂停/取消。一次性承诺只有完成判据满足才 `completed`。单次履约关联约定版本、到期窗口、run、产物与投递证据；检查完成但未触发提醒可以 `satisfied`。报告生成但发送失败不能标记“已发送”，发送成功也不能声称用户已阅读。

任务/承诺创建与关联需幂等并能恢复部分失败；用户直接暂停或删除关联任务时同步对账，避免孤立承诺。共享任务不能因取消一项承诺误停其他承诺的执行；无法安全分离时展示待处理原因。状态名称是工程建议，以上业务语义是已确认边界。

### 3.2 用户级与系统级分域

- **用户专属状态**：只服务一个用户/项目/实例，内容可包括该用户批准的经验、工作流和承诺。
- **系统级状态**：服务于多个用户的通用故障知识或运行规则，必须经过 owner/运营侧审批；用户批准不能直接升级全局。

两类状态必须在存储、审批、检索和上下文注入上分域，避免互相污染。

## 4. 运行时闭环

### 4.1 读取闭环

```text
收到任务
  → 识别 user/project/instance 与任务语义
  → 检索匹配的 active lessons/workflows，以及有效或待处理承诺
  → 组装有预算的 State Packet
  → Agent 选择已授权工具和工作流执行
```

执行中按需补查相关条目，共用预算；记录检索命中、实际注入、预算裁剪及冲突跳过原因。承诺按自身有效/待处理状态选取，不套用 lesson 的状态枚举。`State Packet` 只作为运行时上下文，不是权限边界；真实权限、scope、确认、审计和写入仍由服务层强制。

### 4.2 学习闭环

```text
出现错误/纠正/失败/承诺风险或值得复用的成功做法
  → 服务层记录事实
  → Agent 提交结构化候选（draft）
  → 用户查看、批准或拒绝
  → approved candidate 进入 active
  → 后续匹配任务自动复用
  → 结果反馈支持保留、修订、过期或回退
```

用户明确要求保存复用时，服务可在一次操作中保存版本、登记授权并激活，不再额外问一次；必须能核对该指令确实覆盖内容和范围。证据评估与批准分开，反例可触发修订提议，不由模型自动覆盖 active 内容。

### 4.3 承诺闭环

```text
用户请求或 Agent 提出持续性工作
  → 登记约定与授权依据（Agent 自己说答应不构成用户授权）
  → 幂等关联现有工作说明/自动化执行器，核对真实就绪状态
  → 每期执行并关联 run/result/delivery
  → 按本期完成判据记录履约，保留长期约定
  → 报告结果或待处理事项；变更范围才补授权
```

承诺对象必须能回指实际执行记录，不能只保存一句聊天文本。

### 4.4 停用、恢复与关闭 Beta

| 动作 | 生效边界 | 不承诺撤销的内容 |
| --- | --- | --- |
| 停用经验/工作说明 | 后续检索排除；当前运行保留已加载版本记录，动作仍检查当前权限 | 已完成写入、已发送消息 |
| 恢复旧内容 | 明确选择旧版本内容，生成可追溯的恢复版本；核对当前范围、授权与依赖 | 历史运行记录，不静默改写历史 |
| 暂停/取消承诺 | 同步处理其关联任务，记录实际执行结果；在途动作按现有取消能力处理 | 已不可撤销的外部结果，不假称已全部取消 |
| 关闭学习 Beta | 停止新增学习提议及经验/工作说明注入，保留历史、承诺查询与履约对账 | 已授权自动化仍运行，不能默默停止履约 |

承诺履约所需的关键输入与授权在建立任务时绑定到现有执行器，不应仅依赖可关闭的检索层。关闭前须验证任务仍有足够执行依据；否则说明具体影响并处理，不能把“可回退”当作无条件保证。

## 5. 首版 Beta 范围

首版采用**横向 Beta**，而不是只打通一个任务链路。目标是尽快让已同意配合的真实用户在多类现有任务中反馈，暴露兼容、检索和状态污染问题。

### 5.1 Beta 必须包含

1. 用户级 Agent 状态存储与 scope 隔离；
2. `AgentFact`、`AgentLesson`、`AgentWorkflow`、`AgentCommitment` 的最小可用 schema；
3. 多类任务共享的起始检索、按需补查、去重及总预算控制；
4. Agent 在明确触发事件下提交 lesson/workflow draft；
5. 用户批准/拒绝单条具体版本，支持明确指令直接构成批准；
6. 批准后的候选在声明范围内自动复用；
7. 长期承诺、每期履约与现有 automation task、run、result、delivery 的关联；
8. 经验/工作流/承诺的生命周期、审计、失效和回退；
9. 可关闭的 Beta feature flag、观测指标和快速回退路径；
10. 用户可理解的最小反馈入口：看见候选、批准/拒绝、看到是否已被使用和执行结果。

### 5.2 Beta 明确不包含

- Agent 生成、注册或执行新的代码型工具；
- Agent 在没有对应用户授权依据时把候选升级为 active；
- Agent 自动把用户专属经验升级为系统级规则；
- 仅凭经验采用许可自动修改用户方法、规则、持仓、交易或其他业务状态；本轮明确指令已授权的既有操作仍走原有服务路径；
- 新建工作流编排引擎；
- 用新状态替代 `conversation_messages`、现有业务表或既有 automation 事实源；
- 把 Agent 状态直接塞进用户 Workspace 目录；
- 在没有证据的情况下每轮自动生成反思或经验；
- 本任务内完成用户侧 Workspace 全量透明化 UI。

## 6. 与现有系统的关系

| 现有能力 | 本设计的使用方式 | 不能被替代的部分 |
| --- | --- | --- |
| `conversation_messages` / conversation working state | 作为当前会话事实和短期上下文来源 | 不是跨会话 Agent 经验库 |
| 用户方法、规则、文件与版本链 | 可被工作流引用；涉及修改时走既有候选/版本/批准 | 仍是用户资产，不变成 Agent 状态 |
| `review-memory-store` | 可复用其服务层幂等和 scope 原语，需明确域边界 | 不把复盘记录直接当作 lesson |
| automation tasks/runs | 作为承诺执行器和事实来源 | 不替代 commitment 语义 |
| trace、audit、bad case、failure taxonomy | 为事实和候选提供证据引用 | 开发侧诊断仍需独立维护 |
| service/MCP tool registry | 提供 Agent 可选择的授权能力 | State Packet 不得扩大权限 |

### 6.1 已核对的代码入口与兼容约束

以下为设计审查时的静态代码事实，执行前复核，不代表生产实测结果：

- `src/mastra/workspace-registry.ts`：Skills 加载与 Workspace 读写已存在，命令执行禁用；复用持久化基础，不能以本设计为由开放代码执行。
- `src/services/conversation-working-state*.ts`：已有会话级 decisions、pendingQuestions、权威引用及 scope；长期状态引用来源，不把派生会话摘要再复制成权威事实。
- `src/mastra/tools/tool-specs.ts`：`automation.create/update` 当前无需额外确认；本设计补齐授权依据与经验生效语义，不新增一律二次确认。
- `src/services/generic-automation-runner.ts`：已有 fixed/latest 资产绑定、资产版本提交和单轮输出修复；普通自动化使用独立 run 会话，必须显式接入检索。自动化执行轮没有创建/修改自动化的权限，失败后需要调整任务时路由到有权限的交互/管理入口。
- `src/services/automation-tasks.ts` 与现有 push/delivery 路径：复用任务、运行、租约和投递事实；不能将运行成功映射为发送成功。
- [Workspace 透明化方案](./workspace-user-asset-transparency-refactor-plan.md)：复用资产版本与明确意图语义，保持 Agent 状态和用户内容所有权分开；该隔离实验的功能不能未经当前分支/运行时核实就视为已部署依赖。

## 7. 执行计划

执行 Agent 应按以下阶段推进，阶段之间保留可运行和可回退状态：

### P0：代码与数据边界盘点

- 确认现有用户 scope、trace、automation、review-memory 和资产版本的权威表/服务；
- 明确新状态不得重复写入已有事实源；
- 确认 Beta feature flag、隔离测试数据库和回退开关；
- 输出字段映射和不变量清单；检查交互、通用自动化及其他定时入口的覆盖，未覆盖入口明确列出，不能笼统宣称全覆盖。

### P1：状态域与服务契约

- 实现四类逻辑对象的最小 schema、scope、幂等键、审计和生命周期转换；事实和履约优先引用既有记录，不要求一对象一新表；
- 实现用户级与系统级分域；
- 为 lesson/workflow 提供创建候选、按版本批准/拒绝、停用和恢复操作；采用许可与证据状态分开。承诺按长期约定与每期履约建模，不复用 lesson 状态机；
- 复用现有 automation task/run，不另造执行器。

### P2：运行时读取与写入

- 在交互和自动化任务中按任务上下文检索 active 状态；
- 生成有总预算的 State Packet，支持去重补查、冲突排除和来源引用；
- 将实际加载的状态/资产版本及承诺关联写入 trace，运行中不悄悄换版本；
- 在纠错和成功做法触发时开放 draft 提交，支持明确保存复用指令直接登记批准，不额外发明确认步骤；
- 保证 draft 不参与 active 注入。

### P3：承诺关联与用户反馈

- 将长期承诺、每期履约与 workflow/automation task/run/result/delivery 建立可查询关联；验证部分创建失败、重复请求、任务暂停/取消后的对账；
- 实现用户批准/拒绝单条候选的最小入口；
- 展示候选影响范围、证据和后续行为；
- 展示承诺状态、每期执行/产物/投递结果和失败待处理状态；反馈入口自动关联运行与状态版本。

### P4：横向 Beta 与观测

- 在多类现有任务上启用 Beta，默认可快速关闭；
- 选取已同意配合的真实用户进行短周期试用；
- 记录检索、注入、行为证据和结果的区别；以同类错误、重复说明/纠正、每期履约及用户接受程度评价效果；命中率、批准率、token 和延迟仅作机制/成本指标；
- 发现污染、误用或高影响异常时可关闭注入、停用相关状态；按 §4.4 保持已有授权任务与承诺对账，不用回退静默取消承诺。

## 8. 验收标准

### 8.1 自动检查

- 不同 user/project/instance 之间无法读取、批准或复用对方的用户级状态；
- draft lesson/workflow 不会进入 State Packet；
- 未经批准的候选不会改变后续行为配置；
- 起始检索及补查共用硬预算并去重；模拟中途报错可取到相关经验，记录注入版本和跳过原因；
- 过期、拒绝、退役和 superseded 状态不会被检索；
- 明确保存复用指令可直接生效且有授权依据；模糊指代不能批准错误候选，修改候选不能复用旧批准；用户批准不改变证据状态；
- 两条冲突经验、当前指令/实时事实冲突、引用资产变化时按 §2.8 处理；运行中版本更新不替换已加载内容；
- 周期承诺多期履约后仍保持有效；未触发提醒但完成检查可满足本期约定；产物生成、发送成功与用户阅读不混同；
- task/run/result/delivery 关联可追溯；执行器创建失败不显示已安排，重复请求不创建重复任务，直接暂停任务能对账；
- State Packet 或 lesson 文本不能扩大工具权限、scope 或确认边界；
- 验证停用、恢复、承诺暂停及关闭 Beta 的不同效果；关闭后原有交互、自动化及用户资产路径仍可运行，已有承诺仍可查询、对账，历史不被删除。

### 8.2 真实运行验证

- 至少覆盖跨会话交互、不同 run 的自动化、失败/纠正以及成功做法复用；记录具体入口和实际覆盖范围；
- Agent 提交一条候选，用户拒绝后验证它不生效；
- Agent 提交一条候选，用户批准后验证后续匹配任务实际复用；
- 验证周期承诺至少两期履约、一例投递失败和一次暂停的链路；隔离环境可控时间推进证明机制，真实周期证据单列；
- 验证同一用户的状态不会污染另一用户；
- 通过 feature flag 关闭 Beta 后，确认可回退且不删除历史事实。

### 8.3 用户反馈验证

- 配合测试用户能够理解一条候选总结的内容、依据、适用范围和影响；
- 用户能够明确批准或拒绝，而不需要输入隐含指令；
- 用户能够判断某条批准内容是否被后续任务使用；
- 用户能够判断承诺是否兑现、失败在哪里、下一步是什么。

### 8.4 效果证据与 Beta 完成判定

不把批准、检索命中、注入次数或 Agent 自述“已使用经验”当作变好用的证明。分别记录：检索候选、实际注入版本、可观察行为（工具选择/结果检查/产物差异）、用户结果。行为证据不足时标记未知，不能仅靠模型自报归因。

- 同类错误：保留有可比任务条件的前后案例，记录复发与反例；没有足够机会时不声称复发率下降。
- 重复说明/纠正：关联用户的具体重复输入和反馈，不仅统计聊天数量。
- 履约稳定性：按到期的每期义务核对完成判据；区分执行、产物、投递失败及未触发提醒。
- 工作说明效果：核对后续行为与用户可接受产物；明确是否同时更换了模型、工具或数据条件，避免把所有改善归因于经验。
- 用户反馈支持“没记住、用错场景、过时、答应未做”等原因及自由反馈，自动关联 run/版本，用户不需要自行找日志。

首版保留少量可比较的实际案例与反馈，不先建复杂评分模型，也不虚构提升百分比门槛。技术机制通过、真实用户已试用、效果已有证据是三个独立状态。缺少反馈或样本时可继续 Beta，但不能宣布“越用越好用”已经验证。

## 9. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 错误经验被自我强化 | 批准与证据分离；当前事实优先；draft 不注入；反例与停用/修订可追溯 |
| 用户专属经验污染系统级规则 | 分域、分审批、分注入；用户批准不能全局晋升 |
| 状态注入挤占上下文 | 硬预算、相关性筛选、trace 成本指标 |
| 旧系统事实源冲突 | P0 先做权威源映射；新域只存新增语义，不复制事实 |
| 承诺创建后无人负责 | commitment 必须关联执行器、完成判据和结果状态 |
| 横向 Beta 影响现有任务 | feature flag、兼容适配；关闭学习不静默停任务；验证承诺对账保留 |
| Agent 越权修改用户资产 | 服务层继续强制 scope/确认/版本/审计；状态文本不是权限 |
| 经验过期后继续误导 | expiresAt、结果反馈、退役入口和定期巡查 |

## 10. 后续决策与暂不冻结项

产品原则已对齐，不再以反复确认技术细节作为开始条件。执行方根据代码事实确定存储布局、接口命名、预算数值和简单可解释的检索排序，并记录理由；独立语义、事实引用和批准边界不可改变。

批准入口必须承接对话中的明确指令及单条候选决定；最小查看/停用入口可复用已有 Portal 或对话能力，具体落点由执行方检查现有界面后选择。完整 Workspace 信息架构继续由透明化任务处理。

生产启用前仍需核对具体 Beta 用户、任务范围和发布授权。用户已表达尽快让配合用户试用的方向，不等于本文授权全量生产开启。名单不阻塞本地实现与隔离验证。只有影响目标、授权或关键产品取舍的未知项才回到 owner，常规工程选择自主完成。

## 12. 执行 Agent 交接提示

> 在获得实现授权后，按 v2 的 P0-P4 实现横向 Beta。工作流采用可批准的工作说明，不建编排引擎；复用既有事实、资产、自动化与投递机制。明确用户指令可直接批准具体版本，不重复确认；采用许可与证据分开。实现起始检索与预算内补查、版本绑定、成功做法与纠错积累、长期承诺和每期履约。核验停用/恢复/暂停/关闭 Beta 的区别，关闭学习不得静默停止已有授权任务。自主处理普通工程选择，只为范围/授权/关键取舍的真实阻塞提问。完成本地与隔离验证后分别报告生产启用条件、真实试用和效果证据；不把本文当作发布或修改真实 Workspace 的授权。

## 13. 验收 Agent 交接提示

> 对照 v2 §8 独立验收，若有后续契约一并核对。重点验证明确指令不重复确认、批准不冒充真理、成功做法也能积累、运行中补查与版本固定、周期履约与送达区别，以及关闭 Beta 后原有任务/承诺仍有真实执行依据。核对 scope、状态版本和现有事实源兼容。分别标记自动测试、隔离运行、生产运行、真实用户反馈和效果未知项；注入或模型自述不能替代行为证据。不要以任务测试数或新增机制数量证明越用越好用。

# 用户资产管理与失败告知产品设计

状态：已确认需求后的正式设计，未授权实现、部署或数据迁移。  
前置：[需求确认书](./agent-space-user-product-requirements-confirmation.md)。  
关联：T-536、T-524 Agent Space、现有 `/automations`、`/assets` 与 T-479 自动化失败通知。

## 1. 产品定位

本设计不是向普通用户公开 Agent Space 控制面，也不是恢复旧 Workspace 文件容器。它在既有对象、版本、scope、授权和审计底座之上，提供用户能够理解和管理的 GUI：

- 长期资料与产物；
- 正式方法/投资策略；
- 私有与已安装 Skill；
- 持续授权的自动化任务；
- 自动化或交付失败的可靠告知与问题处理入口。

对话仍是完成工作、解释问题和提出改进的主入口。网页承担资产管理、版本比较、任务设置和失败发现；微信承担同一失败事项的简短提醒。

## 2. 不变量

1. 一个业务对象只有一个主管理入口；同一内容版本可被多个对象引用，但不形成多处可编辑入口。
2. 内容版本与运行生效分离。保存内容不会静默改变运行、交付、权限或任务；采用、安装、启用、改绑和任务 revision 是明确动作。
3. GUI 不能扩展服务层权限。scope、版本固定、授权、审计、幂等与写入边界仍由服务层强制。
4. 用户不管理 Agent Space 拓扑、run-basis、checksum、工具授权、队列或跨 scope 数据。
5. Agent 可形成改进候选，但候选不等于生效规则；未经用户批准不得改变后续默认行为。
6. 成功、产物、投递和用户已读是不同事实，页面不可把其中任一项写成全部完成。

## 3. 信息架构

侧栏保持对话优先，新增或保留以下直接入口：

```text
创建新聊天
搜索聊天

待处理                  失败告知与问题处理入口，显示未处理数
自动化任务              现有 /automations，升级任务详情
我的文件                现有资料库，补关联信息
工作空间                新完整页面
  ├─ 我的方法            默认 Tab
  └─ 我的 Skills

会话与标签
设置                    通知偏好等低频配置
```

聊天右侧旧只读“工作空间”文件面板不参与新设计，另立移除与替代预览实施任务。新工作空间只是一张 GUI 页面，不是物理文件根、数据容器或权限边界。

## 4. 工作空间

### 4.1 我的方法

默认展示方法体系列表，而非长文本编辑器。

每张卡片显示：名称、用途摘要、当前采用版本或未采用、最近变更时间、使用该方法的自动化数量、是否存在待确认版本。

详情页提供：

- 当前采用版本和采用状态；
- 版本时间线、Diff 与恢复入口；
- 待确认的修改及其影响；
- 被哪些任务以何种版本使用；
- 关联资料的只读跳转；
- 创建或编辑入口。

编辑形成新内容版本。用户明确采用后才影响默认运行；已有任务保持其固定绑定版本，直到用户明确改绑。多方法体系可以并存。

### 4.2 我的 Skills

#### 4.2.1 产品分类与六个现有模板的处置（2026-09-23 owner 补充裁决）

“预置”指来源，不等于同一种用户权限。按内容和治理权分两类：

| 模板 | 分类与默认行为 | 内容审查重点 |
| --- | --- | --- |
| `automation-task-designer` | 系统基础能力；默认可用，用户不见也不能停用/卸载 | 仅在创建、修改、检查自动化任务时使用；确认与写入边界仍由服务强制 |
| `candidate-screening` | 用户可管理的预置 Skill；默认安装并启用 | 只作候选与等待条件框架，不把筛选结果变成交易命令 |
| `fundamental-analysis` | 用户可管理的预置 Skill；默认安装并启用 | “近 5 年”“同行前三”是可得且可比时的参考，不是所有请求的硬门槛 |
| `macro-analysis` | 用户可管理的预置 Skill；默认安装并启用 | 宏观分析只在相关问题中使用，时间与来源必须可核查 |
| `technical-analysis` | 用户可管理的预置 Skill；默认安装并启用 | 模板中的均线周期、月周日层级和双线判断属于示例/方法偏好，发布前应去除对所有用户的强制性 |
| `risk-control` | 用户可管理的预置 Skill；默认安装并启用 | 仓位上限、回撤、禁令和“默认不动”不能冒充用户确认的个性化硬规则；缺参数时先询问或标注未知 |

五个投资类模板是通用 Skill 初始版本，不是已获用户采用的“我的方法”；用户自己的方法和已确认硬风控仍由方法资产及服务层契约管理。预置发布前逐项审核具体内容及触发条件，修订过度规定的文字并形成独立版本；不能把当前目录文件直接复制到每个真实 Workspace 后宣布“已安装”。

#### 4.2.2 用户界面和状态

单助手首屏只显示“助手已安装的 Skills”：其中包含启用、停用的用户可管理项，标明来源、固定版本、用途、状态和关联任务；私有 Skill 也在安装后进入此列表，私有草稿/编辑历史通过其详情管理，不另设与安装状态并列的首页。系统基础 Skill 虽供运行时使用，不在列表、搜索、可管理目录或计数里出现，也不提供用户操作。

| 当前状态 | 用户可执行动作 | 后续运行语义 |
| --- | --- | --- |
| 未安装（含从未安装、已卸载） | 从简洁的“查找 Skills”目录安装/找回 | 不进入助手的可用 Skill 集 |
| 已安装且启用（默认） | 停用、卸载、查看详情/升级 | 仅在适用场景可被使用；不代表每轮强制注入全文 |
| 已安装但停用 | 启用、卸载、查看详情 | 保留安装版本与历史，但不能用于新运行 |

安装或重新安装默认启用，固定一个正式版本；升级是用户显式动作，不静默跟随发布。停用不等于卸载，保留固定版本和可恢复状态；卸载保留审计历史，但退出已安装列表。目录首版只供发现可安装的系统公开版本及本 scope 可安装的私有正式版本，并显示已卸载项以便找回；不是推荐流、开放市场或跨用户共享机制。系统发布版本不能直接编辑；编辑私有 Skill 形成新版本，保存草稿不自动升级当前安装。项目目录中的 `skills/*/SKILL.md` 仅是待核对的旧文件，不能标成已安装；其逐项复制草稿入口只是过渡工具，发布/迁移完成后不作为常设第三分类。

系统基础能力也须固定发布版本、受审计与运行装配约束；“不可见”只是不暴露给普通用户的管理界面，不是绕开版本、scope 或服务权限的隐式文件加载。开发者可以通过系统发布更新它，用户不能覆盖或卸载。任何 Skill 内容均不能授予工具、数据、跨 scope 或后台执行权限。

#### 4.2.3 依赖与生效边界

服务层必须对交互会话和自动化入口统一判断该 Skill 对此 Agent 是否可用。新运行只能使用已安装且启用的用户可管理版本，或开发者治理的系统基础版本；停用/卸载后，即使任务依赖固定了旧 `versionId`，也不得绕过状态继续使用。已有 run-basis 和历史产物仍指向原版本，不追溯改写。关联任务的停用/卸载动作应先显示影响并明确处理：任务不可悄悄丢失依赖后继续执行；若仍有必需依赖，阻止停用/卸载并引导用户先调整或暂停任务，或者在后续单独设计经确认的级联暂停。本轮选择前者；服务层也必须强制，UI 提示不充当边界。

“安装即生效”是默认开启适用能力，不等于每轮将所有 Skill 内容注入模型。运行装配应基于场景选择，并留下选中版本的可追溯依据；无相关请求不调用投资分析模板。系统基础模板可用于任务设计流程，但不能因此扩展自动化任务的执行授权。

#### 4.2.4 新用户与存量用户

新 Agent 的默认清单由开发者治理的正式发布版本组成；初始化一次性安装五个可管理模板，并配置系统基础模板为不可管理的默认可用能力。默认集合为空时必须如实显示和报告，不能把目录文件数量冒充安装数量。已初始化 Agent 不会因发布默认版本自动补装；不能重置初始化标记以强制重播。

存量用户按 scope 核对已安装行、移除记录、真实 `skills/` 文件、方法资产、任务依赖和版本血缘后生成差异清单。保留用户的编辑和已作出的停用/卸载选择，不以同名 slug 覆盖私有版本；未能证明的历史意图标为待判定，不能解释成“用户未选择所以可覆盖”。候选新增安装逐项提供原文/发布版差异与任务影响，先在隔离副本演练，再经对应用户/owner 的具体采用决定、备份和审计执行；本设计不是生产数据迁移或 W7 D8 的追溯改判。

#### 4.2.5 当前底座差距与实施验收

当前 `agent_space_agent_skill_installations` 只有 `installed/superseded/removed`，`getInstalledSkillManifest` 只取 `installed`；需要可审计的停用/启用状态与状态转换 API、授权和幂等规则。`applyDefaultSkillManifest` 仅初始化执行一次，不能承担存量补装。交互会话读取安装清单，而任务按声明依赖装配，固定版本目前可绕开安装状态；必须统一服务端可用性检查，并按固定/当前策略保留版本边界。Portal 当前把私有与已安装分块，读模型亦只查安装行；需按单助手列表、停用状态、找回目录调整。

后续实现按以下顺序验收：

1. 审核并发布六个版本，验证基础/可管理分类及投资模板的非强制规则，记录版本 checksum 和发布来源。
2. 服务端覆盖新 Agent 默认配置、存量逐 scope 采用、停用/启用/卸载/重装、显式升级与关联任务约束；核对审计、幂等、scope 和历史 run-basis。
3. 分别用交互会话、无依赖任务、当前版本依赖任务和固定版本依赖任务验证适用时生效、停用/卸载不绕过、系统基础能力仍可用；失败必须是明确状态，不可静默降级为不完整执行。
4. 浏览器验证已安装列表只展示五个可管理预置项及实际安装的私有项，停用项仍可恢复、卸载项从目录可找回，系统基础项不展示；隔离副本和生产结果分别报告，不用本地镜像冒充生产迁移证据。

## 5. 我的文件

保留现有资料库的上传、预览、下载、重命名、归档、来源与版本能力。只新增面向用户的关联信息：

- 来自上传、对话还是自动化；
- 被哪些自动化任务读取或更新；
- 报告或产物关联哪次任务结果；
- 若是方法/Skill 内容来源，跳转到其主管理页面。

文件页不能提供方法或 Skill 的第二套编辑入口。方法/Skill 可以复用 asset version 的内容和存储链，但不因此退化为普通文件语义。

## 6. 自动化任务

`/automations` 是任务的唯一主管理入口，保留现有创建、编辑、暂停、恢复、运行历史和 scope 校验。任务详情新增四个用户信息区：

1. **任务目标**：用户为什么设置它。
2. **依赖与产物**：关联方法、Skill、输入资料、输出资料及跳转。
3. **最近结果**：分别显示执行、产物和投递的事实与时间。
4. **需要注意**：关联失败告知的摘要，以及进入待处理或问题对话的入口。

服务层的 Commitment 继续表达“对用户约定是否履约”，但首版不让用户维护平行的承诺对象；在任务和失败说明中以“本次结果/尚未交付”等用户语言展示。

## 7. 待处理与失败告知

### 7.1 首版范围

全局 `待处理` 首版只展示失败告知，不向用户展示事项状态机、技术分类、收口流程或改进队列。

失败卡片固定展示：

- 失败的任务或交付；
- 发生时间；
- 用户可理解的直接影响；
- 当前系统状态，例如仍将按计划尝试或任务已暂停；
- `让 Agent 解释并处理`。

不展示错误码、trace、重试次数、工具调用、版本 ID 或内部授权信息。用户可以处理，也可以暂不处理；去重、恢复、保留和归档由服务端维护，不构成用户操作。

### 7.2 跨端投影

网页保存完整失败告知。微信是同一失败语义的简短提醒，提供回到问题处理入口的路径。微信投递失败不得让网页失败告知消失。

自动恢复和成功默认不主动提醒。现有 T-479 的恢复微信通知需要在实现时调整为与此规则一致，并用回归测试证明未改变失败事实、任务状态或重试语义。

### 7.3 问题处理对话

点击失败卡片后创建或打开一条可追溯的问题处理对话，携带失败、关联任务、最近运行与投递事实的受限引用。它不混入普通闲聊，也不把原始内部日志直接显示给用户。

Agent 在该会话中解释原因、影响和现有恢复状态，提出重试、修改任务、暂停、补资料或保存改进候选等方案。所有持久修改仍走对应对象的版本与授权契约。

## 8. 通知偏好

设置页管理事项提醒，而不是业务事实：

- 微信失败提醒开关；
- 静默时段；
- 可提醒的失败类别。

任务结果交付配置与全局失败提醒偏好分离。关闭提醒不删除网页告知，也不暂停任务、改变运行事实、修改重试或撤销授权。

## 9. Agent 自纠错闭环

### 9.1 能力边界

Agent 在已有、受 scope 和授权约束的交互会话或自动化任务运行中，可因明确触发选择形成 `lesson` 或 `workflow` 草案。失败后找到了可复用处置，是合法触发；每轮强制反思不是。

Agent 不得脱离会话或既有任务，另起全局的自我诊断/反思运行。草案不直接修改方法、Skill、任务、通知偏好、权限或工具范围，也不自动改变未来默认行为。

### 9.2 用户体验

| 来源 | 用户看到的位置 | 提醒规则 |
| --- | --- | --- |
| 当前对话 | 当前对话的候选卡片 | 当前会话内展示 |
| 自动化失败 | 同一失败问题处理会话 | 不额外发送第二条微信 |
| 正常运行、无当前影响 | 低优先级网页待确认改进 | 默认不微信提醒 |

候选说明适用范围、事实依据、预期改变和影响。用户批准具体版本后，才由对应对象的服务契约生效；用户拒绝后，除非出现新事实或候选内容/范围实质变化，不得重复打扰。

### 9.3 当前实现缺口

Agent Space 已有 Fact/Lesson/Workflow/Commitment 的服务、版本与批准机制，但模型工具注册表尚未暴露 state candidate 的创建/修订能力。实现必须新增一条受 scope、入口类型、事实引用和候选内容校验约束的端到端路径；仅存在领域服务函数或隔离测试不算 Agent 已具备该能力。

## 10. 实现分期

### P0：设计与契约基线

- 确认本设计与 T-524/W1-W7 对象边界的一致性，记录需修订的底座契约。
- 定义失败告知的服务拥有事实、去重、恢复、审计与网页/微信投影，但不把内部状态机暴露为用户分类。
- 定义问题处理会话的上下文引用、scope 校验和敏感字段脱敏边界。

### P1：导航与资产 GUI

- 在 Portal 增加工作空间入口与方法/Skills Tab；升级现有文件页关联信息。
- 新增方法与 Skill 的认证、scope 强制读模型和页面；不直接读取运行时内部表给浏览器。
- 页面实现版本、Diff、采用/启用/安装等明确动作及其终态错误提示。

### P2：自动化整合与失败告知

- 升级 `/automations` 详情的目标、依赖、分层结果与关联失败信息。
- 建立全局待处理入口和失败卡片，接入 T-479 终态钩子。
- 以同一服务事实驱动网页告知和微信投影；调整恢复通知策略。

### P3：问题对话与纠错候选

- 实现失败事项到问题处理会话的受限上下文绑定。
- 为 Agent 提供创建/修订 lesson/workflow 草案的受控能力；验证自动化运行可选择提议但不能自动生效。
- 将候选审阅、批准、拒绝连接到方法、Skill、任务或 Agent 状态各自的主管理入口。

### P4：旧面板退出与验收

- 独立替代或移除旧聊天右侧工作空间面板，保留需要的报告/附件预览体验。
- 进行隔离迁移和浏览器验收；不批量改写真实用户资产。

每个分期都应成为独立任务契约。P0 识别出影响已有重构不变量的问题时，可提出定向底座修订，不能隐式绕过。

## 10.1 本地 111 验证与生产发布门槛

本设计采用“先 111 本地真实对象验证，后生产发布”的路径。这里的“111 本地”是从经授权的 111 scope 数据取得**隔离副本**后，在独立 DB、独立文件根、独立 Portal 配置和假投递通道中运行；不是打开生产 DB、直接复用真实 Workspace 根、真实会话凭据或真实微信状态。

### 本地 111 验证

1. 从可验证备份或只读导出生成仅含 111 scope 的隔离输入，记录来源时间、scope、文件/版本映射和校验摘要；源数据保持零写入。

## 11. 验收

### 产品验收

- 用户从侧栏能进入待处理、自动化任务、我的文件和工作空间；工作空间默认方法并可切换 Skills。
- 用户能在各自主管理入口查看、编辑或配置对象，且页面清楚区分内容已保存与运行是否已生效。
- 方法和 Skill 不以普通文件重复编辑；任务、文件、方法和 Skill 的关联可跳转追溯。
- 失败在网页可靠可见，微信只是提醒投影；用户能进入问题处理对话获得人话解释和方案。
- 用户不需要理解或看见内部 scope、checksum、run-basis、工具授权或队列状态。

### 服务与安全验收

- 浏览器永远不可信任地指定 scope；所有读写由登录会话派生 scope 并在服务端复核。
- 方法/Skill/任务的版本、生效与引用严格固定；跨 scope、未批准草案、未安装 Skill 和版本漂移都被拒绝或明确降级。
- 失败告知与微信投影可幂等重放，通知失败不影响任务终态；失败事实、执行、产物、投递分别可核对。
- 纠错候选必须绑定实际会话或任务运行与事实来源；无授权批准不得成为 active，且不存在无任务/无会话的自主反思调度。

### 证据边界

隔离测试、fixture 和本地浏览器验证只能证明实现契约，不能替代真实用户采用、真实微信送达、生产迁移或长期自纠错价值。上述证据需分开报告。

## 12. 风险与缓解

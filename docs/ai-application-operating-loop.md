# AI 应用运营环（方法论文档）

状态：**v0.2 草稿，待 owner 审定**（owner 2026-09-03 提出环框架，同日 Agent 依当日评估成稿）

## 一、定位与双重身份

本文档是服务客户的、具备一定规模的 AI 应用的**运营环方法论文档**。虽然此类环通常描述中大型 AI 应用，但任何有真实用户、真实任务、模型行为与工具编排混合的系统都在其适用范围。

本文档有双重身份，两者同等重要：

1. **操作手册**：指导日常开发与运维——我们在环上的位置、每段的职责与目标、计划如何挂环；
2. **实验对象**：本项目（P-33）以自身为样本运行此环，实践不断修正文档细节；**项目开发稳定之日，文档收敛之时——届时它就是经过验证的方法论**（方法论抽取沉淀由 P-35 承载，对应月度目标 T-345）。

因此本文档的稳定性本身就是方法论可行性的证据：如果它需要无休止地大改，说明环的抽象不对；如果它逐渐只剩细节微调，说明抽象经受住了实践。

## 二、环总览

```text
REALITY    真实用户与真实任务
   │
TRACE      记录系统真正发生了什么
   │
SIGNAL     发现异常、纠正、失败
   │
DIAGNOSIS  解释为什么发生
   │
FINDING    形成可泛化 Failure Pattern
   │
EVAL       把认识变成可重复测量的问题
   │
IMPROVEMENT 修改 Prompt / Code / Context / Tool / Architecture
   │
REGRESSION 证明没有破坏已有能力
   │
PRODUCTION 上线
   └─────────────→ 新证据回流 REALITY
```

环的学习速率 = 错误被发现的速度 × 诊断质量 × 修复吞吐。**未被发现的错误学习量为零**——信号层断掉时，其后所有段全部饿死。这是环的第一优先级判据。

## 三、逐段定义、现状与目标

现状评级为 2026-09-03 首次评估结果，随实践修订。

### REALITY —— 真实用户与真实任务

- **职责**：确保系统服务的是真实使用，而非演示场景。
- **当前承载**：3 个真实用户（111/mg/dyk），日均 20+ 自动化 run，微信/Portal 真实投递。
- **现状**：真实且持续。
- **缺口**：用户直接反馈通道弱（点赞点踩连续数周为 0），REALITY 层的验证信号主要靠间接获取。
- **目标态**：用户主动反馈非零且被采集（S6 信号激活）。

### TRACE —— 记录系统真正发生了什么

- **职责**：任何一次执行事后可重构「模型当时真正看到了什么、做了什么」。
- **当前承载**：agent_traces（完整 prompt/reply/模型/tokens/首字）+ runs + 审计 + push/delivery + 资产版本链；六入口诊断关联（EV-017）。
- **现状**：中上。
- **缺口**：①工具调用载荷不落盘（tool_calls 仅存元数据）；②任务定义编辑无来源审计（17 次修订无法归因，配置漂移会复发）。→ T-459。
- **目标态**：任意 run 可完整重构运行时 context；任何配置变更可归因到入口。

### SIGNAL —— 发现异常、纠正、失败

- **职责**：让错误进入环。分两个子层：**程序信号**（失败/超时/投递死信）与**语义信号**（成功但产出错误/用户受阻）。
- **当前承载**：程序层——19:15 每日巡查（S1-S6 聚合）；语义层——rubric 周评（T-457，9-3 首轮跑通）+ 受阻信号采集设计（T-442 草案待裁决）。
- **现状**：程序层成熟；**语义层初生**——环最薄弱处。实证：9 月行进 8 月表错误持续两天零报警，靠 rubric 首轮人工评分才发现。
- **目标态**：错误产出的发现延迟 ≤1 个评估周期；受阻清单日级产出；judge（ED-P3）启用后内容抽检自动化。语义信号延迟从周级压到日级是本环当前主攻方向。

### DIAGNOSIS —— 解释为什么发生

- **职责**：竞争性因果假设 + 最小验证实验，降低根因不确定性；先还原世界，再解释行为。
- **当前承载**：ai-application-diagnosis skill（2026-09-03 立为项目级，Context First 为先验而非教条）+ audit-driven-diagnosis skill；实战案例：幽灵个股、复制风暴、确认死锁、跨日补发、9 月行进 8 月表。
- **现状**：方法论当日成形，未经过多轮实战迭代。
- **目标态**：诊断走 skill 流程产出 Diagnosis Record 归档（Reproduction/Intervention/Counterfactual 因果三证），不再依赖 owner 人肉追问驱动。

### FINDING —— 形成可泛化 Failure Pattern

- **职责**：个案收敛为类别，成为失败知识的单一入口。
- **当前承载**：failure-taxonomy.md v1（五层 14 类），维护纪律：新失败先归类，归不进再开新类。
- **现状**：起步（9-2 建）。已识别待入库：上下文矛盾类（stale binding × instruction conflict）、边界显形歧义（漂移精确落在未指定字段）。
- **目标态**：新失败 100% 先归类再处理；每类登记防线现状与复发观察。

### EVAL —— 把认识变成可重复测量的问题

- **职责**：程序性断言 + 效果测量两层，让「认识」变成可重复执行的检验。
- **当前承载**：程序层——EV-014~033（32 条 executable）+ 回放样例 + 变更门；效果层——双 rubric 周评（T-457，校准样本 8/20）。
- **现状**：程序层扎实；效果层当日出生，owner 复核未开始。
- **目标态**：校准样本 ≥20 且经 owner 复核分歧标注 → 启用 judge（ED-P3）；rubric 周评连续运转无中断。

### IMPROVEMENT —— 修改 Prompt / Code / Context / Tool / Architecture

- **职责**：把已确认的因果认识转化为系统修改；修改必须直接作用于已确认的因果变量。
- **通则**：
  - **最小因果干预**：在能作用于因果变量的候选中选最小者；加法与减法同为合法手段，按因果契合度选择，不按默认偏好；
  - **层级匹配**：修复层级与缺陷类别对应——Context 缺陷修 Context、Instruction 缺陷修指令清晰度、Capability 缺陷才动模型侧、Reliability 缺陷才上确定性机制；向更高层级升级须有证据（低层修复失败或同类摩擦重复）；
  - **摩擦驱动**：修改由真实摩擦触发，不做投机性重构；
  - **成本与通用性成比例**：为个案写机制或代码，需要问题重复出现或属于通用类别的证据。
- **当前承载**：五类手段齐备；诊断与修复纪律详见 ai-application-diagnosis skill（AGENTS.md 索引）。
- **现状**：成熟。
- **目标态**：方案评审的默认问题 = 是否直接作用于因果变量、层级是否匹配。

### REGRESSION —— 证明没有破坏已有能力

- **职责**：程序性回归（测试/边界/发布流程）+ 语义回归（语义变更的验证步骤）。
- **当前承载**：程序层——npm run verify（621 测试+边界 7 项）+ release 快照/健康检查/known-good/回滚链 + 变更门；语义层——下一个自然 run + 巡查兜底（非阻塞）。
- **现状**：程序层成熟；**语义层无阻塞门**（rev18 类修复靠当晚 run 验证）。
- **目标态**：语义变更有记录的验证清单（影响面→验证方式→观察窗口），judge 启用后可部分自动化。

### PRODUCTION —— 上线与新证据回流

- **职责**：安全发布；生产证据回流环首。
- **当前承载**：白天部署偏好 + release 流程 + DR 备份 + 巡查日报 + 周一受阻清单 + rubric 周评。
- **现状**：闭环存在。程序环周期小时级，语义环周期周级。
- **目标态**：回流延迟可度量且收敛；两速环的速度差逐步缩小。

## 四、双速环

程序可靠性闭环（小时级）与语义可靠性闭环（周级）目前速度差约两个数量级。**当前阶段主攻语义环提速**，手段按依赖序：受阻信号上线（T-442）→ rubric 周评+owner 复核持续（T-457）→ 校准样本攒够启用 judge（ED-P3）→ 语义信号日级化。

## 五、维护纪律（实践 → 文档的回流规则）

本文档不是静态规范，按以下事件触发修订：

1. **新 Failure Pattern 入库**（taxonomy 新增类）→ 同步更新对应段的现状与缺口；
2. **环断点被发现**（某段失守导致错误滞留）→ 在对应段登记实证与修复；
3. **阶段毕业判据达成或变更** → 更新目标态；
4. **owner 裁决变更方向/优先级** → 更新双速环主攻方向；
5. 至少随每周错误分析（ED-P1，周一）核对一次文档与现实的偏差。

修订流程：Agent 起草 → owner 确认 → 版本号 +1 并在版本历史留一行。禁止无确认的静默改写（与任务定义同纪律）。

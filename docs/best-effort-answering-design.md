# 证据边界内尽力回答设计

> 日期：2026-07-29  
> 状态：设计提案，尚未实施  
> 适用范围：普通投资问答、市场复盘、行业题材研究、选股研究和长尾数据请求

## 1. 背景

Invest Agent 面向的客户请求天然多样，不可能为每一种请求预先建设完整的数据源、确定性接口和专用工作流。如果系统把“具备完整能力”作为回答前提，就会频繁出现以下错误体验：

```text
用户提出一个范围较大的分析请求
  -> Agent 发现不能完整覆盖
  -> 停止分析
  -> 向用户展示数据缺口或系统能力申请
```

这在事实纪律上看似谨慎，但没有优先解决用户问题。用户通常更需要一份有边界但有用的答案，而不是一份内部建设申请。

本设计确立新的默认原则：

> Invest Agent 应在可验证证据边界内尽最大努力完成任务。数据不足时降低覆盖范围、精度或结论强度，不降低真实性；先交付有用答案，再简要说明不足。

## 2. 当前问题

### 2.1 两个维度被错误绑定

当前 Workspace 模板容易把以下两个独立问题合并处理：

1. 本轮对话能够为用户完成多少；
2. 平台是否拥有完整、持久、自动化的系统能力。

`capability-extension` 当前要求在 `one_off_analysis`、`workspace_extension`、`supported_service_configuration` 和 `system_capability_request` 中“只选择一个结果”。当一次性分析缺少部分服务数据时，Agent 容易直接选择系统能力申请，跳过仍然可以完成的研究部分。

`service-capability-policy` 当前强调工具缺失时说明不能取得的内容，但没有同等强度地要求：继续使用其他已授权事实能力和公开证据，完成不依赖缺失字段的子任务。

### 2.2 完整性和真实性被混淆

当前行为隐含了一个错误二分法：

```text
要么完整精确回答
要么不回答
```

实际上应该分别判断：

- 真实性：具体事实是否有可靠证据；
- 完整性：是否覆盖用户要求的全部范围；
- 精确度：是否能给出确定数字和严格排名；
- 时效性：是否是目标日期或当前时点的数据；
- 可执行性：是否能持久化、调度或自动重复运行。

真实性是底线；其他维度可以明确降级。

### 2.3 内部产物替代了客户答案

`system_capability_request`、字段清单、状态枚举和接入草案是内部工程资产。除非用户明确要求设计或建设能力，否则它们不应成为普通投资问答的主要回复。

“同花顺全概念日终复盘”案例中，系统识别数据缺口是正确的，但应先提供公开数据口径下的主要概念复盘，再在末尾说明无法覆盖同花顺完整目录。直接展示能力申请属于产品路由错误。

## 3. 目标与非目标

### 3.1 目标

1. 只要存在可信且与用户目标相关的证据，就交付实质性内容；
2. 将大型请求拆成可回答、可近似、需说明和不可回答的子问题；
3. 默认采用当前可达到的最高覆盖等级，而不是因局部缺口终止整项任务；
4. 对覆盖范围、替代口径和关键缺失做简短、清晰的用户告知；
5. 将重复出现的数据和服务缺口沉淀为内部产品信号，不占据客户回复；
6. 保持现有投资红线、数据审计、scope、确认和写入边界不变。

### 3.2 非目标

- 不允许模型编造价格、排名、资金流、成分股或来源；
- 不把搜索摘要冒充结构化全市场数据；
- 不把代表性样本描述为完整市场扫描；
- 不绕过 MCP、scope、权限、确认或服务 API；
- 不要求为每一种长尾问题开发新的专用 Skill；
- 不通过服务层重新引入普通消息意图分流或上下文包装；
- 不允许“尽力回答”突破投资建议、自动交易和收益承诺红线。

## 4. 核心原则

### 4.1 降低范围，不降低真实性

允许降级：

- 从全部概念降为主要活跃概念；
- 从严格同花顺口径降为公开数据口径；
- 从全市场严格排名降为已覆盖样本排名；
- 从精确资金数字降为成交额、广度和代表股表现的方向判断；
- 从确定趋势结论降为情景判断和待验证信号。

不允许降级：

- 虚构缺失数字；
- 隐藏样本范围；
- 使用旧数据却声称是今日数据；
- 把新闻推断写成资金事实；
- 把个股资金流和 ETF 净申购相加；
- 把未执行的筛选描述为全市场扫描结果。

### 4.2 用户要求的范围默认是目标，不是失败门槛

用户说“所有”“完整”“全市场”时，默认把它理解为期望范围。若无法完全达到，Agent 应返回当前可覆盖结果并说明差额。

只有用户进一步明确“必须严格一致，否则不要结果”“必须用于对账/审计”或任务本身要求精确交易事实时，完整性才成为硬门槛。

### 4.3 一次性回答与能力建设双轨运行

一个请求可以同时产生两个结果：

```text
客户轨：本轮尽力回答
内部轨：记录缺失能力，供产品后续补全
```

二者不能互相替代。即使需要新的数据适配器，Agent 仍应先完成现有证据允许的分析；即使已经给出部分答案，内部仍可记录高频缺口。

### 4.4 先回答，后说明边界

普通用户回复默认顺序：

1. 一句话口径说明；
2. 核心发现和用户可采取的观察动作；
3. 必要的事实、推理和风险；
4. 末尾列出关键覆盖缺口。

不得先用大段能力限制消耗用户注意力。限制说明应与可能误解的程度成比例。

## 5. 通用任务处理流程

### 5.1 任务拆解

Agent 在内部将请求拆成原子子任务，例如：

```text
请求：复盘同花顺全部概念、相关 ETF、领涨股、资金流和趋势原因

子任务 A：概念目录和范围
子任务 B：概念当日表现
子任务 C：概念内领涨公司
子任务 D：个股资金活跃度
子任务 E：相关 ETF
子任务 F：多日趋势
子任务 G：政策、产业、业绩和事件原因
```

每个子任务标记为：

- `verified`：有结构化或正文级证据，可直接回答；
- `compatible`：有替代来源或不同口径，可带说明回答；
- `representative`：只能提供代表性样本，不能声称完整；
- `framework_only`：只有分析框架或待验证条件；
- `unavailable`：没有可信证据，不输出事实结论。

至少一个子任务达到前三档时，普通分析请求不得整体退化为纯能力说明。

### 5.2 证据获取顺序

保持当前数据源政策，但改变最终路由：

```text
本地可靠服务事实
  -> 已授权的公开证据检索
  -> 可解释的替代指标或代表性样本
  -> 明确缺口
```

“明确缺口”是某个子任务的结果，不是默认终止整个请求的信号。

### 5.3 覆盖等级

每次复杂回答内部计算一个覆盖等级：

| 等级 | 含义 | 用户表达 |
| --- | --- | --- |
| `full` | 请求范围和关键字段基本完整 | 不需额外强调覆盖不足 |
| `partial` | 同一口径下覆盖部分范围 | “以下覆盖目前可核验的主要部分” |
| `proxy` | 使用明确替代口径 | “以下采用公开数据/替代指标口径” |
| `representative` | 仅能提供代表性样本 | “以下是代表性方向，不是完整排名” |
| `framework` | 无足够动态事实，只能给验证框架 | 明确没有当日事实结论 |
| `refuse` | 无可信证据或触及产品红线 | 简短说明不能完成的原因 |

用户可见回复不必展示内部英文枚举，但必须让用户理解实际覆盖。

### 5.4 最低有用回答

复杂任务的最低有用回答至少包含：

- 与用户问题直接相关的一个以上已验证发现；
- 当前口径和时间；
- 对用户有帮助的比较、判断或下一步观察点；
- 可能改变结论的关键缺口。

只有框架、模板、能力申请或“请提供数据”不算完成一次普通分析请求。

## 6. 系统改造范围

### 6.1 Workspace `AGENTS.md`

在“服务层事实工具”和“默认回复原则”中增加全局规则：

- 数据缺口只限制相关子结论，不自动终止整个任务；
- 优先完成可回答部分，再在末尾说明覆盖不足；
- 用户未明确要求系统建设时，不展示内部能力申请；
- “完整/所有/全市场”默认是目标范围，无法覆盖时允许诚实降级；
- 降级只能改变范围、精度和置信度，不能改变事实底线。

这项原则应放在 Workspace 的通用入口，而不是只放进某个概念复盘 Skill，否则无法覆盖未来长尾请求。

### 6.2 `capability-extension` Skill

将当前“四选一”模型改为两个正交判断：

1. 本轮请求如何完成：完整、部分、代理、代表性、框架或拒绝；
2. 是否需要持久能力：无需、Workspace 扩展、已有服务配置或系统能力缺口。

新增硬规则：

- 普通一次性分析优先于能力建设；
- 系统能力缺口不能取消本轮仍可完成的部分；
- `system_capability_request` 默认写入内部记录或只在用户主动询问建设方案时展示；
- 用户只要求分析时，不输出 YAML 扩展草案。

### 6.3 `service-capability-policy` Skill

把“缺工具时告诉用户不能读取什么”扩展为：

1. 标记受影响字段；
2. 检查是否有其他已暴露的结构化事实能力；
3. 对长尾问题使用已授权公开证据检索；
4. 判断是否存在可解释替代指标；
5. 完成不受影响的子任务；
6. 最后简述剩余缺口。

仍然禁止 shell、localhost、数据库和隐藏接口绕过。

### 6.4 领域 Skills

对 `observation-pool`、市场复盘、日/周/月复盘和公司研究工作流增加统一的部分覆盖约定，而不是分别发明不同降级逻辑：

- 保留候选或事实的来源范围；
- 排名必须声明排名宇宙；
- 部分数据缺失时继续分析其余维度；
- 不能把“无法全市场扫描”扩大为“无法提供任何候选或市场观察”；
- 报告过大时生成全量结构化附件，聊天只给重点结论。

### 6.5 服务工具返回契约

服务层不负责决定对话意图，但工具应尽可能支持部分成功：

```json
{
  "items": [],
  "coverage": {
    "requested": 100,
    "returned": 72,
    "failed": 28
  },
  "warnings": [],
  "missingFields": [],
  "source": {}
}
```

建议逐步补充：

- 返回范围和分页是否完整；
- 字段级缺失，而不是整次调用只返回错误；
- 数据日期、抓取时间和口径；
- 可重试、无权限、无数据和不支持的类型化区别；
- 替代供应商是否被使用。

这能让 Agent 知道“有72项可答”，而不是把部分失败误判为零能力。

### 6.6 内部缺口沉淀

长期建议增加服务级、脱敏的 capability-gap 事件，而不是让每个 Workspace 自己维护一套工程申请。事件至少包含：

- 请求类别，不保存客户敏感正文；
- 缺失的数据域或服务能力；
- 本轮覆盖等级；
- 是否仍交付了有用答案；
- 是否反复出现在多个用户；
- 对结果影响程度。

Platform 可按频次和用户影响排序，帮助决定先补哪个数据源或工具。该遥测属于服务层产品质量资产，不属于用户 Workspace。

第一阶段不必先建新表。可以通过现有对话、trace 和审计人工评估，等事件结构稳定后再设计确定性存储。

### 6.7 用户输出协议

新增禁止项：

- 普通分析回复中展示 `classification: system_capability_request`；
- 把 `current_status: not_active`、内部字段清单或部署要求直接发给客户；
- 只有能力限制，没有任何已验证发现；
- 要求用户确认一个内部建设草案后才肯提供一次性分析。

推荐格式：

```text
口径：以下基于当前可核验的公开数据，覆盖今日主要活跃概念，不等同于同花顺完整目录。

核心发现：...
重点方向：...
代表公司/ETF：...
趋势、原因与失效信号：...

覆盖说明：尚缺完整同花顺成分和统一 ETF 资金口径，因此未将结果表述为全量排名。
```

## 7. 实施阶段

### 阶段 A：行为规则纠正

范围：模板 `AGENTS.md`、`capability-extension`、`service-capability-policy` 和相关研究/筛选 Skill。

目标：不增加数据源和服务 API，也能让 Agent 在当前证据范围内先回答。

验收重点：

- 同花顺全概念案例不再只返回能力草案；
- 回复至少提供当前可核验的市场主线或代表性复盘；
- 末尾明确非全量口径；
- 不虚构全市场排名。

### 阶段 B：评测与审计闭环

建立少量真实长尾请求回放，不建设庞大的固定语义题库。每次变更后由 Codex结合工具调用、最终回复和审计判断：

- 是否存在“有数据却拒答”；
- 是否把部分覆盖冒充完整覆盖；
- 是否泄露内部能力申请；
- 是否给出最低有用回答；
- 是否把关键缺口放在合适位置。

稳定的硬约束再进入确定性测试，例如禁止用户回复包含内部能力枚举，或工具部分成功契约的结构测试。

### 阶段 C：工具部分成功与覆盖元数据

只对真实高频缺口逐项修改服务工具。优先完善全量/批量数据能力的覆盖统计、类型化错误和部分结果，不建设通用的任意数据网关。

### 阶段 D：产品缺口聚合

当人工审计已经形成稳定分类后，再增加服务级 gap 事件和 Platform 汇总，用真实客户频次指导数据采购与能力建设。

## 8. 现有 Workspace 的发布边界

模板修改只影响新建 Workspace。真实 Workspace 的 `AGENTS.md` 和 Skills 属于对应用户，普通代码发布不得覆盖。

对现有用户采用新原则时必须：

1. 对具体 Workspace 做只读差异检查；
2. 明确列出拟采用的文件和规则变化；
3. 逐用户、逐文件确认；
4. 在 Workspace 外备份原文件；
5. 应用后用真实但只读的长尾问题做单点验收；
6. 不借此覆盖用户自行演化的方法和其他 Skill 内容。

本原则属于投资助手的方法和交互行为，不应通过服务层消息分流、强制改写用户输入或最终回复后处理器实现。安全、scope、确认和审计仍由服务层强制。

## 9. 验收标准

### 9.1 行为验收

使用至少五类真实请求验证：

1. 全概念或全行业复盘；
2. 全市场选股但缺少部分专有指标；
3. 海外或长尾资产研究；
4. 要求完整财务/资金数据但只有部分字段；
5. 用户要求增加一个尚未支持的自动化能力，同时也要求先做一次分析。

每个案例必须满足：

- 有可信证据时，最终回复包含实质性发现；
- 开头或末尾能够理解实际数据口径；
- 未覆盖范围没有被描述为已扫描；
- 缺少一个字段不会取消其他可回答子任务；
- 事实、推断和不确定性仍然分开；
- 普通用户回复不出现内部能力申请结构；
- 没有通过隐藏接口或越权方式补数据。

### 9.2 反例验收

以下情况仍应拒绝或只给框架：

- 没有任何可验证的目标日期行情，却要求精确涨幅排名；
- 要求伪造与同花顺完全一致的名单；
- 要求保证收益或自动执行交易；
- 要求读取未授权用户、数据库或私有凭据；
- 代表性样本不足以支撑任何方向判断。

### 9.3 成功指标

建议在人工审计中观察：

- `gap_only_response_rate`：最终回复只有缺口、没有有用内容的比例；
- `useful_partial_rate`：无法完整满足但成功交付部分价值的比例；
- `false_completeness_rate`：部分结果被错误表述为完整结果的比例；
- `internal_protocol_leak_rate`：客户回复泄露内部协议或能力申请的比例；
- 用户是否继续追问分析内容，而不是反复追问“那你到底能做什么”。

第一阶段不要求为这些指标建立新数据库；先通过真实对话审计验证方向。

## 10. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 为了有答案而编造事实 | 真实性保持硬底线，排名必须声明宇宙和时间 |
| 限制说明过多，仍然影响体验 | 一句话口径优先，详细缺口放末尾 |
| 代理指标被误解为原始数据 | 明确命名替代口径，不沿用专有指标名称 |
| 所有请求都触发大规模搜索 | 保留当前查询预算和停止条件，先回答核心问题 |
| Agent 忽略用户明确的严格要求 | “必须一致/用于审计”切换为严格门槛 |
| 模板更新覆盖真实用户方法 | 逐用户、逐文件采用并备份 |
| 通过代码后处理强行补答案 | 语义行为留在 Workspace Agent；服务只提供事实和硬边界 |

## 11. 建议决策

建议采用以下产品定义作为当前共识：

> Invest Agent 的默认责任不是完整满足每个长尾请求，而是在不编造、不越权、不误导的前提下，最大化本轮对用户的实际帮助。平台能力不足应形成内部改进信号，但不能自动成为停止回答的理由。

优先实施阶段 A 和阶段 B。它们不依赖新增付费数据，能够直接纠正当前最明显的产品行为。阶段 C 和阶段 D 应由真实高频缺口驱动，避免重新走向为每一种客户请求定制系统能力。

## 12. 执行与验收交接

执行 Agent 应先对模板和一个明确授权的测试 Workspace 做最小修改，不触碰真实用户 Workspace。重点修改通用决策规则及 `capability-extension` 的二元分类，不新增服务层意图路由。使用“同花顺全概念复盘”及另外四个不同领域的长尾案例进行真实 ACP 验证，保留工具调用和最终回复证据。

验收 Agent 应优先检查两种相反风险：一是仍然因为局部数据缺口而整体拒答；二是为了显得有用而把部分或代理结果冒充完整事实。任何一项发生都不能通过验收。

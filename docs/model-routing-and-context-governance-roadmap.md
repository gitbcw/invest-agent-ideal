> 关联：[context-and-prompt-architecture.md](./context-and-prompt-architecture.md)（上下文分层现状）、[normal-chat-context-optimization-design.md](./normal-chat-context-optimization-design.md)、[evaluation-assets-registry.md](./evaluation-assets-registry.md)、[ai-system-governance-principles.md](./ai-system-governance-principles.md)。

## 0. 前提约束（owner 2026-08-27 对齐裁决）

1. **单模型战略**：业务先行阶段主要依赖 glm-5.3-flash 一个模型（两档深度别名，max 档 2026-08-28 裁撤），其余模型只做可用性兜底。「成熟产品支持切换模型」由现有的模型选择器 + provider 抽象保证，**不进路由**。行业共识「先用强模型走顺流程」在此适配为「先用一个稳定模型走顺流程」。
2. **业务拆解是地基**：路由（业务任务维度的判断）必须建立在业务工作流清单之上。地基文档为 [business-workflow-panorama.md](./business-workflow-panorama.md)（v0 起草→owner 纠正→定稿），各阶段优化工作引用其工作流编号。
3. **评估不全由 AI**：owner 抽检制——AI 只做客观指标与初筛，质量结论由 owner 每周抽检得出（详见 P1）。
4. **本文档从属治理上位原则**（[ai-system-governance-principles.md](./ai-system-governance-principles.md)），是其「评估反馈/服务护栏/可观测」在模型路由与上下文维度的展开。

## 0.5 输入吸收：前沿共识压缩

GPT 综述给出的框架（与 OpenAI/Anthropic/Google/Microsoft 公开工程建议一致），压缩为四条我们采纳的原则：

1. **四旋钮**：成熟系统的 Router 决定四件事——用哪个模型、思考多深、用不用工具、走什么工作流（单次/多步/evaluator/agent）。不是「任务→一个模型→答案」。
2. **Eval-driven routing**：不用直觉写路由，用真实 workload 的数据证明「low 档能否达到质量目标」，能就不升级；先最强模型建基线，再逐子任务降档回归验证。
3. **Start small, then escalate**：小模型先行 + 确定性校验，校验失败/置信度低才升级（schema 失败、工具失败、数据冲突、高风险请求）。
4. **确定性优先**：数学计算、指标、schema 校验、规则判断交给代码；LLM 只做理解/归纳/规划/语义判断/推理。优化目标是四维效用 Utility = f(质量, 成本, 延迟, 稳定性)，不是单维准确率。

以及一条 Anthropic 反复强调、与我们治理原则一致的红线：**从最简单的可组合架构开始，只在确实获得价值时增加复杂度**。

## 1. 现状定位：我们在哪

对照三阶段路由成熟度（规则路由 → 动态 Router → 自适应升级）与四旋钮，诚实盘点（✅已达标 / 🟡部分 / ❌缺口）：

### 1.1 旋钮一：思考深度 —— ✅ 刚跨入第二阶段

- 2026-08-27 上线**裁判模型路由 v2**（`src/services/thinking-depth-router.ts`，commit b28cc28）：glm-flash(low) 读版本化规则集判 low/high/max，交互轮与自动化轮分别有规则集，决策落 trace，fail-open low。
- 2026-08-28 **裁撤 max 档**（规则集交互 v3 / 自动化 v2，两档化）：依据 Z.ai Code Bench v1.0 官方数据（卡片 tool-glm-53-flash-三档…），Flash High→Max 准确率仅 +约1pp（28.0%→29.0%）而平均输出 token 从 ≈70K 翻到 ≈140K（比 GLM-5.3 Max ≈75K 更啰嗦）；实盘 8-27 上线至 8-28 max 零命中。裁判违规输出 max 时代码降档收敛到 high，计价别名保留供历史 trace 重算。
- 2026-08-28 **T-396 裁判翻转根因定位与修复**（commit 8c45c32）：8-27 实盘「同一持仓复盘任务 low/high/low/high 翻转」的根因**不是裁判模型不确定性，而是 runtime 层规则集错配**——automation 消息的 userChannel 兜底为 "api"，落进交互裁判分支，用交互规则集对执行文本二次裁判并覆盖 runner 判定；runner 层判定与确定性守卫（f497eeb）从未生效（hint 分支不可达死代码）。生产日志证据：automation 行判定始终 low，翻转全部发生在 runtime 层 user= 行（同日 4 high/5 low）。修复后交互裁判只服务真人消息，automation 只认 runner hint。裁判 temperature=0 下仍存在**条件性非确定**（8-27 摇摆 vs 8-28 连发 12×全稳，本机/生产位置一致，来源为上游时段性状态，调用方不可消除），故采纳**分层确定性**：契约任务（update/create）由守卫确定 low（守卫由「T-396 过渡机制」转正为确定性层，无移除条件——符合 0.5-4「规则判断交给代码」）；非契约自动化走 automation 规则集（v2.1 移除临时例句）；交互轮走交互规则集（真人消息短、翻转代价低：误 low 用户会追问）。评测工具：`scripts/thinking-router-determinism-probe.ts`（连发/间隔/生产位置/规则集覆盖四模式）+ 生产案例集（data/experiments/，gitignored）；规则集修订时跑一轮回归，跨时段翻转靠生产路由日志监测。
- 抽检：交互 13/13、生产自动化任务 3/3、叙述型 2/2 判对；规则集随 bad case 进化（改文档即生效，不碰代码）。
- 依据：两天的 eval 基线（120 层1样本 + 层2无限制对照），论文 F1-F8。
- **现状即「第二阶段动态 Router」的深度维度单旋钮版**。

### 1.2 旋钮二：模型选择 —— ✅ 按对齐裁决锁定为单模型

- owner 裁决：业务先行阶段恒用 glm-5.3-flash（两档别名，max 已裁撤），其余模型仅可用性兜底（现有自动链即此角色）；「可切换」由选择器+provider 抽象保证。
- 任务维度的模型选择（如速查类 qwen 更快）**降为 P5 后再评估**，不进入当前路线。

### 1.3 旋钮三：工具面 —— 🟡 自动化已裁剪，交互轮两段式发现已定稿（T-400）

- 自动化轮 2026-08-27 已做「授权即清单」裁剪（90→56 工具，输入 38.7k→24.7k token，全模型受益）。
- **交互轮两段式发现 2026-08-28 设计定稿**（[tool-injection-strategy.md](./tool-injection-strategy.md)，T-400）：常驻核心 ~21+mdt top5 + 目录工具 + 调度壳的渐进式披露；预期 38.7k→约 16-18k（降幅约 55%）。参照 Anthropic Tool Search（defer_loading 机制，官方数据：token 省 85% 且工具选择准确率提升 Opus 4 49%→74%）；调用方单侧实现（glm 网关无平台能力，目录+壳为等价物）。
- 确定性工具基础好：行情/技术指标/筹码均由 MCP 确定性计算（MACD/KDJ/BOLL 不是 LLM 心算）；工作簿追加走声明式 appendRows（服务端确定性提交）——这两点已符合「确定性优先」原则。

### 1.4 旋钮四：工作流 —— 🟡 单轮 agent 循环为主

- 自动化：三阶段结构（读绑定→工具→一次最终动作）+ 确定性校验（列数/JSON/scope guard）已在。
- 交互：单轮 agent 循环；无 evaluator 环节（分析型回答无事实/推断混淆检查——历史上出现过 BC-20260824-001 幻觉引用 bad case）。
- 升级机制：轮级兜底已有（首字看门狗+自动链换模型）；**结果级升级没有**（校验失败→同深度自纠 or 升深度的路径未建）。

### 1.5 Eval 基础设施 —— 🟡 有基线，无闭环

- 已有：可复现双层评测设施（论文 §9）、169 轮真实交互分类语料、评测资产注册表、回放批次（8-24）、coherence 探针。
- 缺：**持续闭环**——无冻结的金测集、无周期性回归、无按任务类型的质量 SLO（只有成功率/格式合规等客观指标，无叙述质量度量）。

### 1.6 四维效用现状

- 成本：单次对话 ¥0.0014-0.0098、自动化 ¥0.11-0.29，月度模型可估（论文 §6.3）。
- 延迟：交互 low 5-13s 可接受；深度档 16-80s 仅限用户显式或后台任务。
- 稳定性：自动化格式合规是主要失败面（F1）；网关渠道级参数是单点依赖（渠道配置变更影响全渠道）。
- 质量：客观指标可测，主观质量无盲评。

**总结论：我们处于「第二阶段早段」——深度旋钮已动态化且有 eval 依据，其余三旋钮和闭环还差。这正是做精做细的起点。**

## 2. 演进路线图（摩擦驱动，逐阶段入场）

### P1 业务地基与抽检闭环——入场判据已满足

**目标**：业务工作流清单定稿；路由决策可观测、owner 可抽检。

1. **业务工作流全景图定稿**（地基，先于一切优化）：v0 已起草（[business-workflow-panorama.md](./business-workflow-panorama.md)，源自 14 天日志 + 任务清单 + 方法库盘点），owner 逐条纠正后定稿。后续各阶段工作必须引用工作流编号立项。
2. **抽检材料（取代原「路由周报」提案）**：客观指标 SQL（决策分布、high/max 占比、时延/成本、格式合规率、用户👎/重生成率）+ AI 初筛的关键样本与 bad case 清单，供 owner 每周 10-15 分钟抽检下结论；结论反哺规则集。不做无人消费的自动化周报。
3. **质量 SLO v0**（按工作流类型）：自动化 = 格式合规 ≥98% + 数据来源交代 100%；速查 = 首字 <5s；深度分析 = 负反馈率 <10%。
4. bad case（含路由误判）走既有 bad-cases 模板。

度量：全景图定稿；抽检连续 4 周；规则集至少一次有据修订。

### P2 渐进式上下文：工具清单按需供给——入场判据已满足（owner 选定的首攻方向）

实测依据：交互轮全量 90 工具 = 38.7k token/轮，速查类（约六成交互）为此白白买单。

**落地形态 2026-08-28 修订（T-400 设计定稿，详见 [tool-injection-strategy.md](./tool-injection-strategy.md)）**：两段式发现——常驻核心集（流程必备 16 + 高频读 5 + mdt top5）+ 目录工具（自动生成，一次全量返回）+ 调度壳（继承审计/确认流/scope）。替代原「主题→子集映射」设计：静态核心集先落地（简单、缓存友好、调用画像支持），主题动态组集留作后续叠加（裁判模型扩展输出主题标签，待两段式稳定后摩擦驱动决定）。

1. 两段式实现与部署（常驻清单、目录生成、调度壳、提示词引导、回退开关）。
2. 金测集保护：上线前用交互语料抽样回归（各主题任务的工具可得性不变：常驻或目录可达）。
3. 多轮深度继承（追问不误判）：裁判输入带会话深度粘性标记（后续叠加）。

度量：交互轮平均输入 token ↓≥40%；工具缺失类 bad case 为零；追问误判率下降。

### P3 结果级自适应升级（evaluator + 重生成）——入场判据：P1 抽检显示存在「low 档内容不足」的稳定类别

1. **evaluator 环节（分析型回答）**：检查事实/推断混淆、引用数据真实性（对照工具返回）。历史依据：BC-20260824-001。
2. **升级路径**：evaluator 不通过或用户👎 → 同会话以 high 档重生成一次（带可见标记）。**契约型自动化不做深度升级**（论文 F1：深度加剧格式违约），其失败走同档自纠重试 + 错误反馈。
3. 用户信号自动进 P1 抽检材料，量化「升级率→质量」关联。

度量：深度分析负反馈率变化；升级触发率 <10%。

### P4 确定性层深化——入场判据：全景图定稿 + 出现「LLM 心算出错」类 bad case 或性能热点

**前置：业务边界先行。** 只对全景图中明确定义了量化边界的流程做确定性化（如控盘度评分是否编译为服务工具，取决于该流程在全景图中的口径是否已稳定到 V1.x 冻结）；业务口径还在迭代中的流程不做。

1. 方法库量化部分 → 确定性服务工具（LLM 只解释不计算）。
2. 数据质量预检（缺口标注、口径冲突）下沉到工具层。

### P5 治理定型——入场判据：共创期结束（用户量/任务量上台阶）

- 路由表从「建议」升「契约」；月度评审；SLO 与成本预算正式化；**此时再评估**任务维度的模型选择（含速查类是否引入更快模型）。

## 3. 不做清单（反范围）

- **不做任务维度的模型选择**（单模型战略，owner 2026-08-27）：glm/qwen 之外的引入、速查类换模型等，全部推到 P5 评审。
- **不做轮内多模型流水线**（单次请求内 small→medium→high 串联）：我们是有状态多轮系统，升级放在轮间/会话间更简单可测。
- **不做自主 multi-agent 编排**：Anthropic 共识 + 本系统治理原则一致——预设工作流优先。
- **不追求单维准确率**：一切调优以四维效用表述（质量×成本×延迟×稳定性），论文数据表即模板。
- **规则集不写成代码**：所有分类/路由判断的进化都发生在「给裁判模型读的文档」里（owner 2026-08-27 裁决）。
- **不做无人消费的自动化评估**：一切评估产物以 owner 抽检为出口（owner 2026-08-27 裁决）。

## 4. 落地节奏

- 每周：P1 周报（自动化）→ 人工/owner 过目 → 规则集修订（有据才修）。
- 每月：跑一轮论文 §9 复现矩阵 → 更新成本/延迟分布 → 路由表复核。
- 每阶段完成：本文档更新「现状定位」章节 + 提交记录。
- 阶段推进由**入场判据**触发，不按日历推进。

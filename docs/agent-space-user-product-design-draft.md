# 用户资产与待处理事项讨论索引

状态：讨论素材，不是设计稿；其中的对象命名、信息架构和触发策略均未冻结，也不授权实现或发布。  
关联：T-536、T-524 Agent Space、旧 `workspace-user-asset-transparency-refactor-plan.md`、自动化失败通知 T-479。

讨论纪律：既有重构契约是当前最强依据，不是不可修改的前提。若 GUI 产品讨论证明对象边界、生命周期、授权或迁移假设与用户可理解的管理模型冲突，必须指出具体冲突并回到相应契约修订；不得为了兼容旧设计而牺牲产品语义，也不得在无证据时随意推翻既有 scope、版本、审计和服务端授权边界。

## 1. 当前共识与待验证假设

不要把 Agent Space 做成普通用户的控制面页面。它是服务运行时的控制面，负责对象装配、版本固定、scope、审计和运行依据；普通用户不应管理其中绝大多数对象。

面向用户的产品应围绕两件事组织：

1. **我可以管理的长期资产**：资料、报告与产物、正式方法、自动化任务及其可见设置。
2. **现在需要我知道或处理的事项**：任务失败、等待输入、待确认的高影响变更、需要用户决定的冲突。

对话是创建、解释和提出变更的入口；网页是查看、比较、恢复和处理事项的入口；微信是同一事项的简短提醒。三者不应各自维护一套状态。

## 2. 第一原则：用户可管理性边界

“属于用户”不是“用户应直接管理”。一个对象只有同时满足以下条件，才应成为普通用户的一等管理对象：

- 用户拥有明确的业务归属和长期利益；
- 用户能理解其业务语义与改变后果；
- 产品能提供受控、可逆、scope 内的操作；
- 操作不等同于扩大权限、改变系统安全边界或替用户作高风险判断。

| 分层 | 对象 | 用户产品动作 | 不应暴露的动作 |
| --- | --- | --- | --- |
| 一等资产 | 上传资料、报告、自动化产物、正式方法版本 | 查看、筛选、比较版本、恢复、绑定到任务 | 文件路径、存储位置、校验实现细节 |
| 一等持续授权 | 自动化任务、计划、输入/输出引用、通知偏好 | 查看、暂停、恢复、修改明确配置、查看最近结果 | 调度锁、重试游标、队列 lease |
| 需要理解的结果 | 待处理事项、待确认变更、任务结果、采用状态 | 查看影响、处理、确认或拒绝、跳转到关联资产/任务 | 原始 trace、工具预算、内部错误堆栈 |
| 运行时控制面 | Agent 安装清单、方法绑定、asset grant、run-basis、工作状态、投递队列 | 仅在解释一次结果时给出面向用户的摘要 | 直接编辑、跨对象调度、人工拼装运行上下文 |
| 系统/管理员域 | 系统 Skill 发布、工具权限、跨 scope 数据、投递基础设施 | 无普通用户管理入口 | 发布、授权、跨用户查看 |

这条边界继承 Agent Space 当前不变量：资产、方法、Skill、任务和状态有不同的权威对象；Agent Space 不是文件库；服务层而不是 UI 或文本负责 scope、权限、审计和写入约束。

### 已确认：用户 Skill 管理边界

用户可在 GUI 中查看、创建或编辑自己的私有 Skill、比较版本、启停和安装。系统/市场 Skill 只允许安装、卸载或明确选择升级；用户不能直接改写其发布版本。任何 Skill 都不能新增工具、数据、scope 或持续执行权限。对话仍可作为创建和修改私有 Skill 的自然语言入口；GUI 提供可见、可比较、可恢复的资产管理界面。

### 已确认：正式方法/投资策略是一等资产

正式方法和投资策略不以“普通文件列表中的一条记录”作为用户产品语义。其内容版本可以复用用户资产的不可变字节和存储链，但 GUI 必须围绕方法体系展示采用状态、适用范围、版本 Diff、候选修改、历史/恢复、任务绑定与实际运行影响。多套方法体系可以并存；默认运行和具体任务只能使用明确采用或固定绑定的版本，不能从文件夹或名称模糊发现。

### 已确认：一个对象一个主管理入口

`我的文件` 保留为普通资料、报告、表格与自动化产物的一级资料库。正式方法与 Skill 分别在 `我的方法`、`我的 Skills` 中管理。一个底层内容版本可以被任务、方法、文件来源或结果详情引用，但用户默认只在其业务语义的主管理入口编辑；其他页面提供“查看关联内容/来源”的只读追溯，不能形成双重可编辑入口或分叉版本链。

### 已确认：现有自动化任务模块是任务主管理入口

不新建平行的“我的自动化”模块。现有 Portal `/automations` 在保留任务创建、暂停/恢复、运行历史与 scope 校验的基础上升级：任务详情应补齐用户目标、计划、方法/Skill/资料引用、交付、最近结果与关联待处理事项。`Commitment` 保持服务层的履约语义，在任务和待处理事项中以用户可理解的结果状态呈现，不作为与任务并列的首版管理对象。

### 已确认：全局待处理收件箱与领域模块联动

Portal 提供全局 `待处理` 收件箱，集中显示自动化失败、待确认修改、缺少输入和其他需要用户判断的事项，并承担未处理计数与网页端详情。事项不复制领域状态：自动化失败事项深链至现有 `/automations` 的相关任务或运行详情处理；自动化模块保留“需要处理”筛选与上下文，但不再是用户发现失败的唯一入口。微信只投影同一事项的简短提醒。

首版用户可见范围进一步收窄为**失败事项告知**：先可靠展示任务或交付发生了什么失败，并提供进入对话解释/处理的入口。用户可选择处理或暂不处理；不在首版向用户区分失败、待确认、缺少输入、改进建议等细粒度事项分类，也不要求用户手动完成“收口”。事项去重、恢复、归档、事实保留与审计是服务端设计责任，后续在实现契约中单独定义。

每张失败告知卡片首版只展示：失败的任务或交付、发生时间、用户可理解的直接影响、系统当前状态（例如仍将按计划尝试或任务已暂停），以及“让 Agent 解释并处理”的入口。不展示错误码、trace、重试次数、工具调用或内部版本标识；需要细节时由绑定该失败事实的 Agent 对话解释并提出方案。

### 已确认：通知偏好只管理提醒，不改变事实或授权

网页待处理收件箱始终保存完整事项，不因用户关闭提醒而丢失。微信是同一事项的简短提醒投影；用户可管理微信待处理提醒开关、静默时段及可提醒的事项类别。任务自身的结果交付设置与全局事项提醒偏好分开。通知偏好不得改变任务/run 事实、事项状态、自动化授权或失败记录；成功和自动恢复默认不主动提醒。

### 已确认：首版单 Agent，保留多 Agent 演进空间

首版以一个投资决策助手为用户心智模型，不提供独立的“我的 Agents”管理中心。用户通过 Skills、方法、资料、自动化和通知偏好管理该助手可使用的业务能力；安装清单、asset grant 和 run-basis 保持控制面。底座保留多 Agent、不同安装组合与任务绑定的能力，待出现可解释、可控且用户确有管理需求的多角色场景后再产品化。

### 已确认：内容版本与运行生效分离

资料编辑直接创建可恢复内容版本，不自动改变任务或外部行为。正式方法的新版本须经明确采用才影响默认运行；已绑定任务仍使用固定版本，除非用户明确改绑。私有 Skill 新版本须经明确安装/启用才影响助手。自动化修改形成新 task revision，计划、输入输出或交付变化仅从新 revision 生效。Agent 在对话中提出修改时先展示影响与 Diff；用户在 GUI 中主动执行保存、采用、安装、启用等动作构成明确操作。

### 已确认：关联按对象详情呈现，不建设全局关系图

用户通过对象详情了解与自身决策有关的来源、使用和影响：文件可追溯上传/对话/自动化来源与任务引用；方法可追溯采用状态和任务版本绑定；Skill 可追溯启用状态、方法引用和适用任务；自动化可追溯资料、方法、Skill、结果与事项。关系以可点击的“来源 / 被使用于 / 影响”呈现，不暴露或允许维护内部 scope、checksum、授权、run-basis 或全局 Agent Space 拓扑。

### 已确认：新工作空间是页面入口，旧右侧文件面板后续移除

当前聊天右侧名为“工作空间”的旧只读文件面板属于后续移除范围，不为其设计兼容、迁移或命名保留。新 `工作空间` 是 Portal 侧栏的直接导航入口，点击后打开完整页面；页面内以 Tab 组织用户可管理的语义资产模块，而不是以可展开侧栏分组或旧文件树呈现。它只是 GUI 信息架构，不是数据容器、文件根或权限边界。

首版工作空间暂定两个 Tab：`我的方法` 与 `我的 Skills`，默认进入 `我的方法`。`待处理`、`自动化任务`、`我的文件`保留侧栏直接入口；通知偏好在设置中管理。未来多 Agent 或其他模块只有在出现明确用户价值后才加入，当前不预设概览仪表盘。

`我的方法` 默认页为方法体系列表，不是长文本编辑器首页。每张方法卡片显示名称、一句用途、当前采用版本或未采用、最近变更时间、正在使用该方法的自动化数量，以及是否有待确认版本。详情页承载版本 Diff、历史、恢复、任务影响、关联资料与创建/编辑入口；默认先让用户判断有哪些正式策略和哪些正在生效。

`我的 Skills` 首版为两类列表，不做市场浏览或推荐中心。`我的私有 Skills` 显示用户创建或由 Agent 提议保存的能力及用途、当前版本、启用状态和最近修改；`已安装 Skills` 显示系统/市场来源中用户已选择使用的能力、安装版本及可选升级。详情页再展示版本、关联方法、适用任务和启停/安装；私有 Skill 编辑形成新版本，明确启用后才影响助手。

`我的文件` 保留现有资料库能力，以最小改动补充关联信息：文件来自上传、对话或自动化；被哪些自动化读取或更新；报告/产物关联哪次任务结果。方法或 Skill 的底层内容来源仅显示其主管理入口跳转，不在文件页提供第二个编辑入口或大规模重做 UI。

现有 `/automations` 不重建。任务详情在既有创建、编辑、暂停/恢复、运行历史和 scope 校验上补齐四块用户信息：任务目标；可跳转的关联方法/Skill/输入输出资料；最近结果中执行、产物和投递的分层事实；关联失败事项的简短摘要与待处理/问题对话入口。待处理负责告知和引导，任务详情是配置与处理任务的唯一入口。

### 待确认：Agent 自纠错的触发与动作边界

既有重构设计允许 Agent 在明确触发事件下自行提交 lesson/workflow 草案；“失败后找到可复用处置”是其中一类触发，并明确不要求每轮强制反思。因此拟议边界不是“只能在用户对话中提出改进”，而是：Agent 只能在一次已经存在的、受 scope 和授权约束的交互会话或自动化任务运行中选择提出草案；不得脱离用户对话或既有任务，另起全局的自我诊断/反思运行。

草案不改变后续默认行为，也不得直接修改方法、Skill、任务、通知偏好、权限或工具范围。用户可以在对话中审阅、解释和批准草案；批准后才按所属对象的版本与服务端动作契约生效。后台仍可按既有任务运行、服务层重试/恢复、记录 run/delivery 事实、更新事项和投递提醒。

当前实现差距：`AgentFact`、`AgentLesson`、`AgentWorkflow`、`AgentCommitment` 的领域服务、版本和批准机制已经存在，但模型工具表尚未暴露创建/修订 state candidate 的能力；当前 Agent 不能通过 Agent Space 将可复用纠错持久化为候选。这是后续设计与实现必须显式补齐的能力，不可把服务函数或隔离测试误称为已可用产品能力。

### 已确认：候选提议依附触发上下文，不制造额外噪声

对话中产生的候选直接在当前对话展示原因、影响和可选动作。自动化失败中产生的候选附着于同一失败待处理事项，作为 Agent 发现的可能方案，不另发第二条微信提醒。正常自动化运行中、不影响当前用户结果的候选进入低优先级“待确认改进”网页事项，默认不微信提醒。候选被拒绝后，除非有新事实或候选内容/适用范围实质变化，否则不得再次打扰。

## 3. 已有能力与产品缺口

### 已有：自动化失败事实与微信首条提醒

T-479 已在 scheduled run 终态后按 scope 记录失败和恢复：首个连续失败会入队一条微信通知，连续失败聚合，不通知 manual run；三次连续失败后任务进入 `needs_attention` 并停止继续调度。Portal 自动化列表已可筛选“需要处理”并查看运行历史。

### 缺口：没有用户事项的权威对象

现有 `push_jobs` 是微信投递队列，`automation_task_runs` 是运行事实，`needs_attention` 是任务状态。它们都不是“用户现在要处理什么”的可关闭、可恢复、可追溯事项：

- 网页端只能主动进入自动化页找状态，不会在统一入口收到详细事项；
- 微信和网页没有共同的事项 ID 与状态；
- 首次失败后的自动恢复当前还会再推一条“已恢复”，这不符合“成功不打扰”的新方向；
- 非自动化来源，例如等待用户补输入、待确认的重大变更、投递终态失败，无法共用同一体验。

## 4. 新的待处理事项模型

`attention_item` 是待讨论的候选领域对象，用于检验是否能把用户待处理事项与 push job、任务状态分离；它尚未成为设计决定。

### 4.1 最小状态与关联

```text
detected -> open -> acknowledged -> resolved
                 \-> dismissed (只用于不再需要用户处理的事项)
```

每个事项固定 scope，并至少关联：`source_type`、`source_id`、`task_id/run_id`（若适用）、用户可读标题/影响/下一步、严重性、首次发现时间、最后更新、resolution。技术原因保留受限详情，页面默认只显示服务生成的人话分类。

`dedupe_key` 按“同一用户可理解的问题”建立。例如同一个任务连续失败属于一个 open 事项，后续失败更新计数和最近时间；成功后自动标为 `resolved`，不另建成功事项，也不主动推送恢复消息。

### 4.2 统一投影，而不是两个通知策略

| 投影 | 何时 | 内容 | 用户动作 |
| --- | --- | --- | --- |
| 网页端信箱 | `attention_item` 创建或更新即出现 | 完整：影响、当前恢复状态、任务与资产链接、最近失败、下一步、详情 | 打开任务、补充输入、确认、暂停、重新运行等已有受控操作 |
| 微信 | 新事项首次进入 `open` 时 | 简短：发生了什么、是否自动重试、是否需要马上处理、回网页入口 | 打开对应事项 |
| 自动恢复 | 事项从 open/acknowledged 变为 resolved | 网页保留为已解决历史 | 默认不发微信“成功”消息 |

投递失败也是事项状态的一部分：微信未送达不改变网页事项存在；网页入口不依赖微信成功。微信的 `push_job` 只记录投递尝试和终态，不拥有事项生命周期。

### 4.3 自动化失败的第一条落地规则

默认将每个 scheduled run 的第一个失败终态写成 open 事项，显示“系统将继续按计划尝试”或“任务已暂停，需要处理”。后续连续失败合并更新同一事项；任务成功则解析为 resolved。manual run 失败是否产生事项，应按“是否影响持续授权或用户成果”判定，不能仅因它是 manual 一律忽略。

这取代 T-479 的“失败与恢复均微信推送”的用户表现，但保留其可复用的终态钩子、错误分类、幂等键、scope 和审计链。通知策略变化必须单独实施和回归，不在本文授权范围内。

## 5. 用户信息架构

普通用户不需要一级 `Agent Space` 或 `Workspace`。推荐四个入口：

```text
待处理
  └─ 失败 / 待确认 / 需要补充 / 已解决历史

我的资料
  └─ 上传资料、报告、自动化产物、来源、版本、历史与恢复

我的方法
  └─ 当前采用、并行体系、候选修改、Diff、历史、恢复、任务影响

我的自动化
  └─ 目标、计划、输入/输出资产、最近结果、暂停/恢复、关联待处理事项
```

“为什么这次这样做”不作为独立控制面，而是嵌入结果和事项详情：展示用户能据此判断的采用方法/版本、数据截至时间、缺失输入、结果与投递状态。run-basis、checksum、tool list、workspace injection 等仅供支持人员或在明确诊断模式下查看。

## 6. 从旧 Workspace worktree 继承什么，废弃什么

### 继承

- 当前内容、版本历史、Diff、来源、影响和恢复是用户资产的稳定体验；
- Agent 在对话中提出变更，网页提供查看、比较、恢复；
- 内容保存、持续任务启用和外部投递是不同操作，不能因一次文件编辑而隐式发生；
- 用户界面不暴露内部 candidate/approval 状态机，而是以“拟议修改”和其影响表达。

### 废弃

- 一个 `/workspace` 文件树承载方法、规则、记忆、任务和系统配置的对象模型；
- 从目录发现或按路径操作方法；
- 把 Agent 工作状态、Skill 安装和运行时装配当作用户需维护的资料；
- 旧 worktree 的代码、路由和迁移方案作为新实现起点。

旧 worktree 应保留为只读设计证据，直到本文确认的继承点被纳入新的设计决策记录；它不应合并或继续开发。物理删除须单独明确授权。

## 7. 参考产品：可借鉴的交互，不照搬对象模型

### Codex

当前无法从本地浏览器取得官方 Codex 文档（`developers.openai.com` 返回 403），因此本文不把未验证功能细节作为依据。可借鉴的产品原则是：用户围绕任务、对话和可见产物完成工作；底层 agent、工具调用、运行环境和协调状态默认退居幕后，只在排障或需要判断时展开。

### WorkBuddy

公开官网将主要路径组织为“新建任务、任务、工作空间”，并在任务中呈现 AI 的执行过程和最终文档/成果；技能、专家、连接器和自动化是可被配置的能力层。这验证两个原则：

1. 用户的主心智模型应该是目标、任务和成果，而不是模型装配；
2. 过程可以可审阅，但不应成为每位用户的日常管理负担。

对本产品的取舍：采用“任务及成果优先”和按需展示过程，不采用一个泛化的工作空间容器，也不把投资方法、受控自动化和用户资料降格为普通文件。

## 8. 设计顺序与非目标

### 先做设计，不进入代码

1. 冻结 `attention_item` 的来源、用户状态、去重、自动恢复和跨端投影语义；
2. 制定“待处理”用户文案、详情、动作和失败分级；
3. 以新对象边界重写“我的资料 / 我的方法 / 我的自动化”的对象、版本和关联设计；
4. 盘点已有 T-479、资产库、自动化 Portal 与 Agent Space 可复用的服务事实，形成分阶段实现契约；
5. 再决定 T-536 原型是否归档为内部样本，并创建独立实施任务。

### 非目标

- 不发布 Agent Space 页面给普通用户；
- 不重建或合并旧 Workspace worktree；
- 不在此阶段改 DB、通知、Portal、任务状态或微信投递；
- 不让用户直接编辑系统 Skill、权限、run-basis、队列或跨 scope 数据。

## 9. 下一轮需要确认的产品问题

1. 首次 scheduled 失败是否应立刻成为 open 事项，还是先给系统一次无打扰自动重试机会？本文暂按“失败终态立即创建”建议。
2. “待确认的重大变更”是否与失败事项共用一个信箱，还是保留独立确认中心但在待处理统一计数？本文建议共用事项基础对象、保留不同动作与文案。
3. 用户的“资料”首版是否包含研究/报告/表格三类，还是先只纳入已存在 user asset 与自动化产物？本文建议后者。
4. 一个用户是否真的需要在首版管理多个 Agent？本文建议不做一级入口，直到存在可解释且可控的多 Agent 业务场景。

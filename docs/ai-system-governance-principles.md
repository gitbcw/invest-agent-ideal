# Invest Agent AI 系统治理上位原则

状态：当前治理基线（v1，2026-08-22）

本文把《AI 应用复杂系统管理落地方案》收敛为 Invest Agent 的项目规则。它约束系统如何被设计、验证、发布和复盘，但不替代更具体的服务契约、数据库迁移规则、Portal 协议或生产运维手册。

## 1. 权威层级

出现冲突时，按以下顺序解释和执行：

1. 用户明确授权与当前任务边界；
2. `AGENTS.md` 的项目红线；
3. 服务/MCP、数据库、Portal、发布和安全契约；
4. 本文治理原则；
5. 通用方法论和历史文档。

本文不能授权生产数据替换、Workspace 覆盖、微信发送、权限放宽或绕过确认门。治理原则必须通过代码、服务边界、测试和运维流程落地，不能把本文或 Workspace Skill 当作安全边界。

## 2. 五条总原则

### G1：先建反馈，再谈优化

每项影响 Agent 行为、工具选择、数据证据、调度或用户体验的变更，都必须说明如何验证“变好、未变差或可回滚”。验证可以是确定性测试、隔离评估、真实链路验收或审计检查，不强制使用某个第三方评估平台。

### G2：最小化模型职责

权限、scope、确认、revision、金额和日期计算、数据校验、幂等、调度状态、推送生命周期和文件安全由确定性服务负责。Agent 负责理解、判断、规划和选择可用工具；不得通过 Prompt 代替服务安全保证。

### G3：假设每一层都会失败

模型、外部 MCP、市场数据、Portal connector、微信、SQLite、文件系统和构建产物都必须有明确的超时、错误分类、重试/不重试、降级或人工处置路径。失败应收敛为可见的终态，不得静默成功、重复写入或重复推送。

### G4：小步发布、可观测回退

系统 Prompt、模型路由、工具清单、模板、Portal 构建产物和代码都属于可演化资产。变更应从隔离验证开始，按实例或明确 allowlist 灰度；生产代码发布必须使用可审计快照，回退默认只替换代码，不触碰 `.env`、SQLite、Workspace、reviews、`.state` 或微信状态。

### G5：只记录必要且可关联的事实

每个运行回合应能通过 `traceId`/`messageId`/`conversationId`/`runId`/`taskId` 关联到用户结果、工具摘要、服务审计和调度/投递状态。记录应脱敏、截断、可审计，不默认保存完整 Prompt、模型原始回复、工具结果、凭证或绝对路径。

## 3. 项目分层规则

```text
L4 反馈与观测：评估、Trace、审计、用户反馈、漂移和运营复盘
L3 护栏与事务：scope、权限、确认、revision、幂等、限流、超时、降级
L2 Agent 智能：Mastra 推理、规划、工具选择、投资判断和表达
L1 确定性事实：SQLite 投影、Workspace 受控文件、规则计算、调度和投递
```

- L1/L3 的契约必须由服务或 MCP 强制执行。
- L2 不得直接访问生产数据库、Workspace 路径、内部 token 或隐藏 HTTP 路由。
- 外部只读 MCP 可以被 Agent 发现和使用，但必须经过注册、scope、凭证注入和会话类型限制。
- 用户 Workspace 的 AGENTS、Skill、方法和报告是实例资产；模板只能作为可选更新目录，不能自动覆盖。

## 4. 评估与反馈闭环

### 4.1 评估对象

本项目优先评估以下行为，而不是追求一个脱离业务的总分：

- 事实是否来自允许的数据源，并保留来源、时间和缺口说明；
- Agent 是否选择正确的工具和当前 user/project/instance scope；
- 确认、revision、幂等和写入后的读回是否正确；
- 自动化、scheduler、推送和过期任务是否达到正确终态；
- Portal 与微信是否遵守同一运行时语义；
- 超时、空响应、限流和依赖失败是否正确降级；
- 是否泄露秘密、跨用户数据或未经授权的文件内容。

### 4.2 最小评估资产

先建立 30–50 条版本化回归样例，按 happy path、边界、对抗/越权、历史 bad case 分类。每条样例至少包含场景、输入、预期事实/状态、禁止行为、scope、验证方式和来源。样例应存放在隔离测试根或文档化的评估资产中，不得引用真实生产秘密或把真实用户内容直接提交到 Git。

评估分为三层：

1. 确定性门禁：单测、契约测试、边界测试、构建和静态检查；
2. 隔离行为评估：临时 DB/Workspace、受限 MCP、模拟依赖或授权测试账号；
3. 生产复盘：Trace、服务审计、调度/投递记录和人工抽检。

默认不引入 Golden Case 工作台或 LLM-as-Judge。只有当重复人工复盘已经成为瓶颈时，才增加 Judge，并要求保留人工校准和安全维度硬门禁。

### 4.3 Bad Case 闭环

每个重要问题都应完成：记录 Trace/审计证据 → 按数据、服务契约、Prompt、模型、交互或运维归因 → 形成修复 → 加入回归样例或确定性测试 → 灰度验证 → 记录是否回滚。不得用“系统很复杂”代替具体归因。

## 5. 护栏、人工确认与韧性

- 高风险写入必须通过服务确认、scope、revision、幂等和审计；模型输出的“我已完成”不是成功证据。
- 组合变更、方法变更、永久删除等操作需要精确确认；自动化任务生命周期仅在现有契约允许时直接执行。
- 所有长任务必须有总预算、阶段超时、错误类别和最终状态；仅对明确可重试的 transient/timeout/dependency failure 重试。
- 外部 MCP、模型网关、Portal relay 和微信失败不得触发无限重试或重复副作用。
- 降级必须保留事实边界：缺数据时说明缺口，不能用模型记忆填充实时行情、财报或用户持仓。
- 混沌/故障注入先在隔离环境验证四类场景：模型首字超时、外部 MCP 断连、Portal connector 断连、推送依赖失败；不直接对生产用户注入故障。

## 6. 变更与发布门禁

涉及 Prompt、模型、工具清单、MCP 装配、模板、服务契约或 Portal 构建的变更，必须记录：影响面、验证证据、灰度对象、观测指标、回滚目标和未解决风险。

- 普通生产版本从已提交、已审阅的维护分支发布；代码发布与运行时数据迁移严格分离。
- 新行为优先对隔离实例或明确 allowlist 灰度；本项目不默认采用固定 5%/30% 流量比例。
- 发布后至少验证健康、核心工具、Trace 覆盖、调度/推送终态、Portal/connector 和一个授权只读主链路。
- 任何安全、scope、事务一致性或重复副作用回归都阻断扩大灰度，并优先回滚。

## 7. 指标与治理节奏

当前优先指标不是单一“回答分”，而是：工具/写入安全违规数、跨 scope 事件数、重复写入/重复推送数、超时与空响应率、可重试终态收敛率、Trace 覆盖率、Portal/微信成功率、数据来源缺口率和回滚耗时。

每周复盘高影响 bad case 和未收敛任务；每次发布复核变更评估与回滚证据；每月执行一次隔离故障注入；每季度清理废弃 Prompt、工具、模板和过期评估样例。指标阈值应先用本项目真实基线校准，再形成阻断线，不直接套用通用 SaaS 数字。

## 8. 明确不采用的做法

- 不以复杂系统理论解释本可由数据、代码或配置解释的问题。
- 不把 LangGraph、Dify、Langfuse 等推荐工具作为本项目强制依赖；Mastra、service-tools、现有 Trace 和发布契约仍是当前实现基线。
- 不默认记录完整 Prompt、原始回复、检索全文、MCP 原始输出或秘密。
- 不因为模板评估通过就自动覆盖用户 Workspace。
- 不把 LLM Judge 的分数当作安全、权限、事务或生产验收的唯一依据。

## 9. 当前 90 天落地顺序

1. 建立 30–50 条隔离回归样例和统一 Bad Case 记录模板。
2. 把现有 Trace、服务审计、scheduler/push 证据串成一次运行的诊断视图；补齐外部 MCP observer 缺口。
3. 建立模型超时、外部 MCP 断连、Portal connector 断连和推送失败的隔离故障测试。
4. 将评估摘要、灰度对象和回滚目标纳入发布快照/验收记录。
5. 以内部实例或 allowlist 运行一次影子/灰度流程，再决定是否建设更重的在线质量和漂移平台。

本文的后续修改必须同时更新本项目相关契约、测试或运维入口；若只是方法论参考，不得改变现有安全边界。

# 自动化任务设计

这是系统播种的任务设计 Skill，用于把用户的自然语言需求收敛为可执行、可回溯的自动化任务定义。它不属于用户投资方法，不固化任何特定用户、行业或数据源规则；用户确认后才可以演化任务定义。

## 触发与模式

在用户要创建、修改、检查或优化自动化任务（包括“定时任务”“任务提示词”“每天帮我更新……”）时使用。先判断模式：

- **创建**：先确认是否已有相同或相近任务，再发现可用的同 scope 资产。
- **修改**：先读取目标任务的当前定义和 revision，再拟定完整的新 revision。
- **检查/优化**：只读取任务和相关资产，指出冲突、缺口、歧义及低风险改进；没有用户确认不得写入。

不要因为用户只是要求立即运行、查看运行结果或排查失败而触发本 Skill；这类请求沿用相应的运行/诊断流程。

## 发现事实

只使用当前会话实际挂载的服务工具和能力，不在本 Skill 中维护外部数据工具清单，也不向用户展示工具名。需要时：

1. 用 `automation.list` 按当前 scope 查找任务；任务不明确时先缩小候选，不猜 taskId。
2. 用 `automation.get` 读取目标任务的完整定义、当前 revision、绑定资产和状态。
3. 用 `assets.list` 只发现当前用户、项目、实例 scope 内的资产，可按 `status`、`search`、`format`、`source` 和 `limit` 筛选。
4. 对话附件在草案阶段只读取当前会话提供的元信息。用户确认草案后，先用 `assets.attachment.save` 提升为同 scope 用户资产，核对成功并取得 assetId 后才可创建或更新任务；保存失败则停止，不要把临时附件、文件名或路径直接写进任务定义。
5. 任务所需的数据能力、文件格式和字段只按当前实际可用能力核对；无法确认的能力写成限制，不凭经验补全。

资产发现只用于选择和核对。服务层负责 scope、权限、版本、路径和写入校验；本 Skill 不是安全边界。

## 澄清分寸

只追问会实质改变执行结果的问题：数据范围/口径、时间或时区、输入输出目标、结果交付、缺失数据处理、重复运行处理等。每轮最多问 1-2 个问题。

- 用户已说明、任务现状或资产/schema 可以确定的内容不再问。
- 有可靠且低风险的默认值时直接采用，并在草案的“默认与待确认”中披露。
- 不把每个任务字段都变成问题；次要格式、命名和非关键文案使用保守默认值。
- 不替用户发明指标定义、排名范围、阈值或投资判断；这些属于 instruction 中的用户方法，缺失时只提示需要确认。

没有相反要求时采用并披露这些低风险默认值：时区使用 `Asia/Shanghai`；用户确认创建后任务为 active；未要求消息推送时 delivery 为 none；更新既有资产时跟随 latest 版本。服务 schema 不支持的频率或输出方式不能用提示词模拟，应说明当前能力边界。

## 写入前草案

在任何写入前，先形成完整草案，并等待用户下一轮明确确认。面向用户的预览保持简短，但必须覆盖用户需要裁决的内容：任务做什么、何时运行、读取/更新哪个可识别文件、结果范围、是否推送，以及数据缺失或重复运行时怎么办；不展示 assetId、revision、内部工具名或完整 payload。用户要求技术细节时再展开。

内部任务定义至少包含：

- 任务名称/目的、状态（默认说明是 paused 还是 active）和适用范围。
- `schedule`：frequency、time、timezone，以及 weekly 所需的 weekdays；只使用当前工具 schema 实际支持的频率。
- `instruction`：数据来源与口径、处理步骤、输出内容、禁止猜测的边界。
- `inputs` 与 `output`：每个绑定的 assetId、角色、versionPolicy；输出只使用当前 schema 支持的模式。
- `delivery`：不交付、摘要交付或条件交付及其条件。
- 去重/幂等规则：同一调度窗口或同一业务日期是否只允许一次结果，如何识别已有结果。
- 数据质量策略：完整、部分可用、日期错位或字段缺失时写什么、留什么、停止什么。
- 失败策略：哪些情况停止并报告，哪些情况可重试，是否保留旧版本。
- 已采用的默认值、仍待用户确认的关键问题和预期副作用。没有实际内容的栏目不进入用户预览。

这些栏目是设计契约，不代表服务有同名 payload 字段。只把服务 schema 支持的字段传给服务；去重、数据质量和失败行为若没有独立字段，写入 `instruction` 或 `description`，不要臆造参数。

## 用户确认后的提交

- 创建时调用 `automation.create`，提交完整已确认定义；用户确认创建后默认启用，只有用户要求暂存、暂停或仍有执行关键缺口时才保持 paused。
- 修改时必须先有 `automation.get` 的当前结果，并把返回的 `currentRevision` 作为 `expectedRevision` 传给 `automation.update`；不要用旧的 revision 猜测或覆盖并发修改。
- 只改变用户确认的字段；更新会形成新 revision，不静默改写历史定义。
- 提交后回读并核对任务 ID、revision、状态、绑定资产和下次调度；面向用户只说明任务名称、状态、可识别的目标文件和下次运行时间，除非用户明确要求内部标识。发现服务返回与草案不一致时停止并报告。
- 不在未确认时调用创建/更新，也不因一次运行结果自动改写任务提示词；只能提出下一版建议。

创建或修改的 instruction 应让执行 Agent 能独立判断输入、输出、去重、数据质量和失败边界，同时只依赖实际挂载能力。不要把某个用户的任务名、行业规则、文件名或历史问题写成平台通用规则。

# Skill 创建器

系统播种的技能创建指导 Skill。它不属于用户投资方法，不包含任何领域规则；只规范「怎么在本系统里创建一个合法、可用的私有 Skill」。

## 何时使用

- 用户明确要新建 Skill（包括从「技能管理」页跳转过来、消息里直接说新建 Skill）。
- 用户想把一段已验证的流程或做法沉淀为可复用技能。
- 用户询问「怎么创建/修改 Skill」。

不用于：一次性问答或临时任务（直接用普通对话完成，不必建 Skill）；安装、停用、卸载、批准（引导用户去「技能管理」页操作）。

## 创建流程

1. **先判断该不该建**：如果需求只是一次性的，直接帮用户做完，不建议沉淀；只有跨会话复用的流程才值得建 Skill。向用户说明这个判断。
2. **访谈确认**（每轮最多 1-2 个问题，只问会改变草案内容的问题）：
   - 名称与用途：这个 Skill 做什么、什么场景该触发它（这决定系统何时加载它）。
   - 核心内容：步骤、规则、检查项、边界与禁止事项。
3. **起草 SKILL.md**：向用户展示完整草案（含 frontmatter：`name`、`description`），说明各段落作用，等待用户明确同意。**用户没有确认内容前，不得调用创建工具。**
4. **保存**：用户确认后，调用 `skill.create`（参数：slug、name、description、text）。slug 用小写字母/数字/`-`/`_`/`.`（2-121 字符），全文小写、见名知意。
5. **告知后续**：创建结果只是「待确认」私有草案，不会自动启用或发布；请用户到「技能管理」页审阅、批准、安装后才生效。当前模型侧只开放创建；修改已创建的草案请用户在「技能管理」页进行。

## 写作规范（本系统契约）

- `description` 必须写清「做什么 + 何时触发」——这是系统判断加载时机的唯一依据。
- 正文用用户能懂的语言写步骤、规则、边界与禁止事项；不引用当前会话不存在的工具或数据能力；需要系统能力时，以当前实际挂载的工具为准，无法确认的能力写成限制。
- Skill 只描述「怎么做」，不承载用户持仓、策略等私有事实；需要时引用用户方法与资产，不复制正文。
- 不替用户发明投资规则、阈值或买卖判断——那些属于用户的方法文件，缺失时提示需要用户确认。
- 长度克制：覆盖要点即可，正文建议不超过 4000 字；写成 checklist 而不是散文。

# Service Capability Policy

Use named MCP tools for runtime facts and durable actions. HTTP routes, localhost ports, tokens, curl commands, database access, and service files are implementation details and must not be discovered or called from the workspace Agent.

Service-owned facts and durable actions belong to `invest-agent-service-tools`: user state, portfolio/watchlist/plans, confirmations, conversation history, explicit watch rules, review publication, and other scoped writes. External market data belongs to currently mounted external read-only data MCP servers: quotes, indices, K-line/history, fund flow, financial reports, news, research reports, trading calendars, sectors, and other provider data. For market-data tasks, prefer the external read-only MCP's native tools over service-owned legacy `market.*` facades when those external tools are available.

Inspect the read capabilities currently exposed by the session and choose the narrowest useful capability from each tool's description and schema. If an external data MCP exposes a capability/self-description tool, use it only to understand coverage and then call the narrowest native data tool. Do not maintain a hard-coded external tool inventory in Workspace instructions, and do not require the service layer to wrap or normalize external tool results before use.

ACP slash commands, available commands, and MCP resources are not the MCP tool list. Do not decide that a named MCP tool is unavailable merely because it is absent from slash commands or resources. When a task matches a stable service contract such as `portfolio.read`, `watchlist.read`, `plans.read`, `confirmations.pending`, `confirmations.request`, `conversation.history`, or `watch_rules.*`, call that named MCP tool directly and report a capability gap only if the call/server actually fails or the tool is genuinely not mounted in the session.

`market_watch.snapshot` is scheduler-window audit/comparison evidence, not a substitute for live quotes, K-lines, financial reports, or general market data. Use it only when the task is about the captured window, scheduler state, or comparison with a scheduled brief.

For durable user-visible writes, call `confirmations.request` in the same turn when the user asks for the change, register the exact operation and payload, show the returned draft/confirmation to the user, and wait for a later explicit user confirmation. `confirmations.request` is only a safe pre-write registration step; it does not change portfolio, watchlist, plans, rules, or other durable investment state. Then consume the returned `confirmationId` through the corresponding named write tool. `watchlist.add`, `plans.set`, `plans.watch_conditions`, `portfolio.apply_changes`, `watch_rules.create`, and similar service writes all require this server-side confirmation draft; a plain natural-language draft is not enough. Never edit workspace state files to imitate a successful service write. Onboarding is intentionally different: use `onboarding.draft.*` to keep each accepted section in the service-owned draft, then use `onboarding.draft.enqueue_commit` only after all sections are accepted; the background service is the sole writer of final onboarding configuration.

Legacy `onboarding.complete_watch_setup` remains only for older flows. New onboarding drafts include `watch_rules` as a final accepted section and must not ask the user for a redundant “确认完成”.

If a required named tool is missing or returns an unavailable/data-gap result, first mark only the affected field or subtask. Check other exposed read capabilities, prioritizing external read-only data MCP for market/provider facts and service MCP for user state. Use authorized public-evidence search only for long-tail questions that neither structured service facts nor external data MCP cover, and then an explainable proxy or representative sample where appropriate. Complete every remaining subtask supported by trustworthy evidence before describing the material gap. Do not bypass the boundary through shell commands, hidden interfaces, or direct files.

Use `full`, `partial`, `proxy`, `representative`, `framework`, or `refuse` internally to keep the coverage honest. State the actual scope, data time, ranking universe, sample boundary, and substitute metric whenever they could be misunderstood. A representative sample is never a full-market scan, and a search result is never structured market coverage.

For ordinary analysis, put one short scope statement before the findings and put the remaining gap at the end. Never expose tool names, internal classifications, capability-request YAML, deployment status, or internal execution details in the user-facing reply. A user who explicitly requires exact reconciliation, audit-grade completeness, or a strict proprietary universe may make completeness a hard requirement; otherwise treat “all” and “complete” as target scope rather than a reason to return nothing.

# Weekly Portfolio Review

## Purpose

Turn daily reviews into a feedback loop. It runs automatically on Saturday at the configured default time, currently `09:00`, unless the same weekly report was already generated by a manual user trigger. The weekly report should check whether the daily views were right, partially right, unverified, or wrong, explain why, produce next-week guidance, and include a risk radar.

## Inputs

- `AGENTS.md`
- `config/portfolio.yaml`
- `config/strategy.yaml`
- `config/paths.yaml`
- `config/notification.yaml`
- `config/decision_policy.yaml`
- `config/data_contracts.yaml`
- `config/risk_taxonomy.yaml`
- `config/product_metrics.yaml`
- `knowledge/methods/*.md`
- `knowledge/product_metrics_protocol.md`
- Daily reports in `reports/daily/`
- Daily decisions in `memory/decisions.jsonl`
- Behavior events in `memory/behavior_events.jsonl`
- Source events in `memory/source_events.jsonl`

If there are no daily reports for the requested week, state the gap and still provide a best-effort weekly market/portfolio review if holdings exist.

## Workflow

1. Identify the week and collect daily reports/decision records.
2. Check whether a same-week report already exists. If it was generated by a manual trigger, do not duplicate it unless the user confirms refresh.
3. Fetch or verify actual weekly market data.
4. Classify each important daily view: 命中, 部分命中, 未验证, 明显错误, or 正常噪音.
5. Attribute mistakes: data issue, over-extrapolation, style switch, missing fundamental variable, weak risk rule, or normal noise.
6. Build a risk radar covering market style, concentration, liquidity, valuation, macro/policy, industry, product-specific risk, data quality, news/event, and method-execution risks.
7. Generate a "周末 10 分钟投资会议" summary: whether action is needed, top risks, next-week watchlist, and user tasks.
8. Check user behavior risks such as overtrading, repeated short-term queries, repeated refreshes, chasing watchlist items, style drift, non-core upgrades, and ignoring cash/risk limits.
9. Generate next-week guidance for each important holding/watch item.
10. Suggest method improvements only as proposals; never edit knowledge files without user confirmation.
11. Save the report to `reports/weekly/YYYY-Www.md`.
12. Append improvement candidates to `memory/method_changes.jsonl` with status `proposed`.

## Style Rules

- Write in Chinese.
- Separate bad process from normal market noise.
- Do not force attribution when the evidence only supports "normal noise" or "still pending validation".
- Include a short product-metric summary when data exists: alert count, duplicate suppression, evidence coverage, and behavior events.
- Do not change user strategy automatically.
- Make every improvement auditable and ask for confirmation before writing it to methods or strategy.
- Risk radar is required even when no immediate trade action is suggested.
- Weekly review should feel like a concise investment meeting for a busy working professional.

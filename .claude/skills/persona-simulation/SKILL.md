# Persona Simulation — 用户画像驱动的产品体检

## Purpose

让 Claude 扮演特定用户画像,**基于真实代码路径**走完产品旅程,**挑出体验不合理的地方**,告诉用户为什么不合理,给改进建议,**直接在对话里输出**。

**默认契约**:
- 输出在对话里,**不落盘成报告文件**(除非用户明确要求保留)
- 用户没意见 = 同意按改进建议执行;有意见 = 用户直接说
- 不强制"逐条裁决"这种形式化流程

## 何时触发

用户说:
- "跑画像模拟"、"用老张视角走一遍"、"产品体检"
- "看看新用户用着怎么样"、"哪里会卡"
- 任何"打磨产品"、"体验审查"语义

也适合在大改动后(新功能上线、UI 调整、流程改造)主动跑一次,验证没破坏体验。

## 核心原则

### 1. 不评分,不堆报告

评分标准是主观的、费劲的、且没法代码化。**不要给时刻打星、不要给总分**。报告的价值不在分数,在于"挑出的不合理点准不准"。

### 2. 画像是"可执行的",不是"档案"

`docs/personas/<name>.md` 必须具体到 Claude 拿到就能演:看到推送 X 时会怎么想、什么时机流失、对什么样的引导反感。模板见 `docs/personas/README.md`。

### 3. 必须基于真实代码路径

走模拟前 Claude 应该:
- `grep`/`find` 验证提到的代码路径真实存在
- 不假设功能存在;不确定时先 ls 确认
- 每条不合理点的"现状"必须能指到具体文件:行号

### 4. 不合理点要 actionable + 给人看

每条不合理点 2-3 行内说清楚两件事:
- **现状**:一句行为描述(系统现在做了什么)
- **为什么对画像不合理**:画像视角的主观感受(一句)

改进建议单独分组写,对应每条给改法 + 工作量预估。

**给用户的输出不挂文件:行号**。文件:行号是 Claude 内部执行时给自己定位用的,用户看了是噪音——用户原话:"这个东西又不是给我读的,我要文件和行号,我知道它也没啥用"。需要执行时 Claude 自己 grep/Read 定位。

### 5. 默认执行,有意见再说

挑完不合理点 + 给完改进建议后,**不要追问"你裁决一下"**。用户的沉默 = 同意 = 直接按改进建议进入执行。用户有意见会直接说。

## 流程

### 1. 选画像 + 读画像

从 `docs/personas/` 选一个画像,通读 6 个维度(知识储备/互动偏好/投资风格/时间投入/信任度/流失触发点)。

### 2. 走完整旅程

按 7 个关键时刻顺序代入画像:
- T0 扫码绑定 → 首次对话 → 首次配置 → 首条推送 → 沉睡期 → 沉睡唤醒 → 闭环建立

每个时刻:
1. **设定场景**(时间 + 触发条件)
2. **走代码路径**(grep/ls 确认行为)
3. **代入画像**:这个画像在此刻会怎么想、怎么回、是否流失

### 3. 挑不合理点(核心)

从旅程中**只挑出真正不合理的点**,不要每条都凑数。一条不合理点要么是"会流失"的致命问题,要么是"价值密度低"的体验问题。**没问题的时刻不要硬挑**。

每条按三段式写(现状 / 为什么对画像不合理 / 改进建议)。

### 4. 直接在对话里输出

挑完不合理点 + 给完改进建议,**直接在对话里输出给用户**,不落盘报告文件。

输出格式:
- 简短开场("用老张视角走完了 7 个时刻,挑出 N 条不合理点,致命的 X 条")
- 每条三段式(现状 / 为什么对画像不合理 / 改进建议)
- 末尾给 P0/P1/P2 分档汇总
- **不追问"你裁决一下"**——用户沉默 = 同意 = 直接进入执行

## 跟代码改动闭环

挑出的不合理点(用户没意见 = 默认执行):
- 涉及 prompt/skill → 直接改 `.codex/skills/*/SKILL.md` 或 `src/prompts/*`
- 涉及代码逻辑 → 写进 `docs/ideal-refactor-plan.md` 或新建工作包
- 涉及产品设计 → 写进 `docs/personas/README.md` 的"待解决问题"清单

改完之后**重跑一次同画像**——改过的不合理点应该消失,新的不合理点可能浮现。重跑结果仍然在对话里输出,不落盘。

## 输出纪律

- **不评分、不打星、不给总分**
- **不落盘报告文件**——直接在对话里输出,除非用户明确要求保留
- **不追问"你裁决一下"**——沉默 = 同意
- **每条不合理点 2-3 行,几句话说清楚**:现状(一句行为描述,**不挂文件:行号**)+ 为什么对画像不合理(一句)。不要堆长引文、不要大段代码、不要分点罗列
- **问题和改进建议分两组写**:先列"问题"组(只描述现状 + 为什么不合理),再列"改进建议"组(对应每条给改法 + 工作量)。不要把问题和建议混在每条里,阅读负担重
- **不要 P0/P1/P2 大段分档汇总**——建议组每条末尾标工作量就够
- 跨时刻共性 1-2 条根因就够,不要列表格
- 全程用中文
- **狠**:确实流失级就明说"会流失",不要软化成"体验有待提升"
- **准**:不要凑数,没问题的时刻就不挑

## 边界

- **不实际跑系统**:基于代码路径推演,不真发微信消息、不真调 API
- **不替代真人测试**:画像模拟是快速迭代工具,产品上线前仍需真人验证
- **不堆画像**:同时维护的画像不超过 3-5 个,否则维护成本压垮价值
- **不评分**:评分标准主观且费劲,价值密度低于"挑不合理点"
- **不落盘报告**:默认对话里输出,用户没明确要求保留就别写文件
- **不强制用户逐条反馈**:用户没意见就默认推进,有意见自然会说
